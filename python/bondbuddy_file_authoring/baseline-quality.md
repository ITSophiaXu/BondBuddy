# 基于原稿更新的质量要求

本说明恢复原稿更新的质量要求，覆盖 task.md、旧知识或示例中“不运行额外检查”、按统一模板改写原稿的冲突表述。保持同一次 CLI 自主执行，不要求逐章重新调用模型，不要求用户逐项审批，也不把专业核验作为已有文件的下载门槛。

## 先确定本次实际底稿

读取 input.json。baseline_path 指向唯一实际编辑基线，materials 中 editing_baseline=true 的条目与之对应。先打开该原文件，核对原稿企业、版本、章序、目录、正文、表格及附属部分。有基线时必须在它的内容上更新，不能用知识模板或 scratch 中自行新建的文档替代；上一版成果作为基线时也必须使用指定的精确版本。原稿与目标企业不同，不把原企业事实当作目标事实，但适用的结构、条款和句式继续复用。

如果输入声明了原稿但文件未列入、文件无法读取或其身份相互矛盾，明确记录输入缺口，不能静默解释为“无原稿”。没有原稿时才按对应品种知识新编。PDF 要先按原页完整重建，保留目录、段落和表格对应关系；不可把读取失败当成新编许可。

## 全量检查，局部修改

沿原稿目录逐章建立 scratch/工作记录.md，记录每章实际读取和处理的范围，区分已更新、无需修改、缺资料未完成，并保留原文位置、新材料位置、单位、期间和计算口径。包括全部表格明细、页眉页脚、文本框及脚注；不要只搜索部分关键词、看前几行或用摘要替代完整内容。

先保留原文，再修改确有依据需要变化的数字、期间和事实。不为润色而全文重写、概括、合并段落；不需要更新的适用段落逐字保留。同企业缺少新证据时保留真实历史事实及原有时点，在局部批注说明缺口，不能把旧数换日期冒充新数。不同企业事实必须根据目标材料替换，不能沿用其财务、业务或状态结论。

默认保持原稿标题文字、编号、层级和顺序。目标知识用于逐项核对必要披露，不能仅因专家模板章节不同就重排原稿。跨品种或用户明确范围确需结构调整时记录具体要求、原位置和迁移对应关系，保留未受影响内容。不能机械限制字数或修改比例来规避真正需要的更新。

所有支持的 DOCX 更新在原包原位置进行，保留不相关 XML、样式、表格、图片和关系。受控模式使用固定编辑工具；直接编辑模式使用真实修订。新增期间时检查整张表及全文引用，工具不支持的列结构不能用空表、删表或改成摘要绕过；明确记录实际未完成事项。

## 同一次执行内复核与修正

有 DOCX 基线时，保存修改后执行：

```
/opt/venv/bin/python -B -m bondbuddy_file_authoring.baseline_review --input input.json --output scratch/baseline-review.json
```

受控模式会在 scratch 中从原稿和操作日志生成核验用双 Word，正式成果仍由 worker 定稿；直接模式检查实际输出的双 Word。检查使用输入指定的原件，不相信模型自行保存的 baseline.docx。查看每项 findings：接受修订是否得到清洁版，拒绝本轮修订是否还原实际原稿，清洁版是否残留修订、原附件是否丢失。失败时在本次执行内修正自己的操作或文件，再检查，不另开收费任务、不修改检查程序、不伪造通过。

逐章对照文字复用统计和完整原文，检查标题是否被替换、无需变化的说明是否被缩写、表格明细是否减少。机械检查通过不证明内容正确；仍需检查主体、期间、口径、重复引用和变动原因。原文保持也不意味着本期内容已经更新完毕。

工具不支持或环境不可用时如实记录具体未完成的检查和受影响位置，继续保存已形成的成果，不能用未执行检查冒充通过。已生成文件仍按现有下载方式交付；下载可用与原稿一致性、业务核验分别记录。在 output/delivery.md 写清实际基线、完成和未完成范围及核验结果，不将工作记录、内部编号或来源清单塞入正式正文。
