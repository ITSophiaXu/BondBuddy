# 内部功能验收与 daily bug bash

每轮使用同一个已启动、独立数据库和存储的测试环境。先固定候选代码和样本清单，再按案例分工。测试数据包不是生产任务恢复工具。

当前中捷、邹平两个更新案例尚未齐备，不能作为已覆盖或已通过。先使用标记 READY 的15个案例；两项补齐后再纳入轮换与发布检查。详见 [SOURCE-CAPTURE-GAPS.md](SOURCE-CAPTURE-GAPS.md)。

## 每日快速检查

1. 运行离线完整性校验，选择新目录展开案例。记录 commit、镜像、样本 manifest SHA-256、测试日期和执行人。
2. 至少检查一条更新、一条复核、一条项目问答；底稿与诚信核查轮换。当前更新使用新津；深交所和 PPN 待来源补齐后加入轮换，不能将缺失案例记成通过。
3. 由测试者在界面重新上传材料并填入 `input.json` 的业务字段。任务开始前核对所选原稿、目标期间、补充要求和选中的证据文件。
4. 按案例 README 的清单检查实际结果。长文档任务自然完成所需时间单独记录，不把快速检查结束时间当作任务超时标准。
5. 保存首轮结果和重试记录；发现问题登记缺陷，至少包含输入 hash、版本、run ID、最小复现步骤、预期/实际、日志时间和文件定位。修复后复测同一输入。

测试环境的模型额度和测试积分由环境负责人配置。真实模型和外部网站检查遵守当轮授权及预算，不能因准备了测试包就自动调用。

## 需要在隔离环境控制的故障场景

这些场景复用原件，改变测试环境条件，不改原生产账号和账务：

- 余额充足的正常任务；余额不足暂停；补足测试额度后恢复；取消与失败释放。
- 上传中断/重复上传、刷新/关闭浏览器、多次点击开始、任务完成后重新打开下载。
- 模型超时/限流/无效结构、网络短暂中断、worker 在检查点附近停止与恢复；使用环境提供的故障注入设施，不能中断生产服务。
- 两个隔离账号执行相同案例，检查项目、材料、结果和收费隔离；账号凭据不进入 Git。
- 新候选版本读取旧版本创建的草稿、暂停任务与成果；保留真实升级边界和兼容性结果。

## 发布前检查

在最终候选版本上覆盖全部三条更新、全部三条复核和七题问答；至少覆盖一组完整底稿目录与五个发行人的诚信查询范围。所有本批受影响的功能及历史故障案例必须复验。

报告分别列出通过、失败、未执行、受外部条件阻塞；列出真实/模拟边界。自动化测试通过、数据校验通过、用户实际验收和已部署必须分别记录。验收与发布继续按项目既有专门 chat 分工执行。
