## #12 upload reuse and capacity follow-up

Apply append-only migration `0018_m1_upload_reuse.sql` before this API. ## #17 durable queue foundation (synthetic test only)

Migration `0004_m1_durable_jobs.sql` adds one durable job per run, lease token/deadline, attempt count, JSON checkpoint and a provider-call attempt ledger. Migration `0006_m1_storage_lifecycle.sql` is the #8 append-only storage lifecycle follow-up. Migration `0007_m1_provider_result_reconciliation.sql` appends immutable, owner/project/job/run/attempt-bound provider result references and observations. Migration `0008_m1_username_password.sql` is the #7 login migration, `0009_m1_account_lifecycle.sql` adds account lifecycle, and `0010_m1_word_delivery_evidence.sql` adds append-only Word quality and Blob-delivery evidence. Apply migrations in filename order with `npm run migrate:api`; migrations are append-only. The API production entry point still returns `501 CAPABILITY_NOT_READY` for execute/cancel/resume. Only an in-process test that explicitly injects `enableSyntheticQueue` can submit a queued run; `enableRunStaging` retains the earlier paused fixture. Neither flag is read from the environment by the production server.

Submission takes a per-owner/request-key transaction lock, verifies the owner and immutable revision/hash, then commits run, job, first event and outbox together. Same key/same request returns the same run; a changed request returns 409. The worker claims by locking the run then the job with `SKIP LOCKED`, renews a tokenized lease, and writes each checkpoint, run event and outbox in one transaction. An expired lease is reclaimed with the same checkpoint. A potentially sent provider attempt must be persisted before any external call. On lease expiry, unresolved attempts pause the job for provider reconciliation and are never resent automatically. The internal #16 probe can preserve a schema-checked JSON result in the private Blob container, verify its byte size/hash, then atomically append its owner-bound reference, observation, #79 usage evidence, checkpoint pointer, run event and outbox transition. A resumed processor must load that pointer and recheck the Blob hash/schema before it can reuse the result. Missing or conflicting usage/result evidence stays pending; a measured supplier failure ends the run as failed without automatic retry; `confirmed_not_sent` permits a separately resumed new attempt. These are internal/test seams only: no production provider adapter or public reconciliation route is installed. Cancel and finish take the same row locks, so only one terminal result wins. Success additionally requires a passed, available owner Word artifact/version, immutable matching migration-0010 evidence and a bounded Blob readback with matching byte size/SHA-256. The worker has no real document generator, provider path or production processor and cannot be enabled in production.

The Word seam is `inspectDocx(bytes)` plus the trusted worker `promoteWordArtifact(pool, lease, bytes, blobs)`. Version `ooxml-docx-v1` accepts ZIP packages up to 64 MiB, at most 2,048 entries, 32 MiB per entry, 128 MiB total expansion, a 200:1 entry expansion ratio, 8 MiB per XML part and 32 MiB total XML. It rejects malformed/ambiguous ZIP structures, encryption, unsupported ZIP64/features, symlink-like entries, DTD/entities, macros, missing Word parts, bad content types, unresolved internal targets and missing relationship references. External relationships are limited to HTTP(S)/mailto hyperlinks. This checks package structure only; it does not render pages, evaluate bond terms, check redlines, antivirus-scan media, or establish financial/legal correctness.

Promotion validates before any Blob write. Rejected candidates get `quality_status=failed`, `delivery_status=revoked` and an immutable quality record; no object is uploaded. A valid candidate is written under a run/hash-derived private key, read back under the archive-size bound, then made available only after hash/size verification and a transaction that attaches evidence. Blob write/read/missing/hash failures are recorded as unavailable evidence and never permit run success. `queue.finish` repeats the bounded read and revokes the artifact with append-only failure evidence if those bytes have changed; artifact metadata and downloads also use the evidence byte-size bound and compare the stored hash before granting or returning bytes. The same candidate, validator version, owner and run resolve to the same artifact identity; an available promotion is replayable after worker restart without duplicating evidence. A subsequent retry revalidates the candidate and Blob. Operators should retry an active/recovered run with the same candidate bytes; a different candidate has a separate artifact identity. Do not manually set artifact/run status to `available`/`succeeded` or bypass the evidence table. Migration 0010 aborts if pre-existing `succeeded` runs need review and revokes legacy `available` artifact rows that lack evidence; inspect/reconcile those rows before retrying the migration.

`apps/worker/` is an independent Node process package. Its CLI exits unless `BB_SYNTHETIC_QUEUE_TEST=1` and `DATABASE_URL` are set. That test-only mode claims one job, records a synthetic checkpoint and closes it as failed with `CAPABILITY_NOT_READY`; it cannot simulate a real supplier or document generator. The exported `runOnce(pool, processor, leaseSeconds, blobs)` accepts a trusted processor returning `{kind:'word_candidate', bytes}` and sends those bytes through the shared validator, promoter, Blob readback and terminal gate. A void result, malformed candidate or absent Blob adapter fails closed. Terminating a process does not cancel the database job. The next worker waits for lease expiry, then resumes from its checkpoint. In production do not set the synthetic flag. A real processor must be installed only after #16 supplier request reconciliation, #79 durable operation/prompt/usage/error logging, professional content review and the Word delivery gate are integrated.

For local verification, use the PostgreSQL 16/Azurite instructions below and run `npm ci`, `npm run build`, `npm run check:contracts`, and the API tests with `BB_TEST_DATABASE_URL="$DATABASE_URL" BB_TEST_AZURITE_CONNECTION_STRING=UseDevelopmentStorage=true npm run test:api`. Run the worker integration test against a separate, fresh database: its real `runOnce` loop claims globally queued jobs and must not compete with fixtures left by another suite. For the local Compose database, create and migrate one with `createdb -h 127.0.0.1 -p 55433 -U bondbuddy_local bondbuddy_worker_test`, `WORKER_TEST_DATABASE_URL=postgresql://bondbuddy_local@127.0.0.1:55433/bondbuddy_worker_test npm run migrate:api`, then `BB_TEST_DATABASE_URL="$WORKER_TEST_DATABASE_URL" BB_TEST_AZURITE_CONNECTION_STRING=UseDevelopmentStorage=true npm test -w @bondbuddy/worker`. The tests use synthetic data and cover concurrent duplicate submissions, cross-owner denial, fresh API instance recovery, checkpoint/lease recovery, pending-call pause, provider-result reconciliation, valid and hostile DOCX packages, duplicate/restarted Word promotion, Blob mismatch/missing handling, owned artifact retrieval, cancel/finish races, event order, forced outbox rollback and isolated PostgreSQL/Azurite restore. Synthetic structural fixtures do not prove real provider integration, visual document quality, professional content correctness or browser-session acceptance. See [the provider result reconciliation runbook](../../docs/runbooks/provider-result-reconciliation.md) for the internal procedure and its production restrictions. The old Cowork and product prototype remain unchanged.

## #7 trusted session boundary

Historical SMS foundation (superseded by the #7 username/password decision and migration 0008): migration `0003_m1_auth_sessions.sql` adds normalized E.164 phone identity, one-time challenges, versioned required agreement acceptance, idempotent `user.registered` outbox event, and revocable sessions. Apply it after `0001`/`0002`; never edit deployed migrations. Existing #8 owner IDs were test-only opaque subjects and are not silently converted into phone accounts. A production data migration needs an explicit verified identity mapping.

`/api/v1/auth/sms/challenges` accepts mainland 11 digit or `+86` form. A challenge lasts five minutes, can be resent after 60 seconds, and allows five issues per phone per hour; a resend invalidates the old challenge. Five wrong codes invalidate a challenge. The response is the same for new and existing phones and contains no OTP. Limits are per normalized phone, so colleagues sharing an IP are not blanket blocked. The six digit OTP is held only by the SMS transport during delivery and HMAC hashed in PostgreSQL; configure a high entropy `BB_AUTH_OTP_KEY` through the runtime secret facility. A failed provider send rolls back issuance and returns a generic error. The transport must not log codes or include them in errors.

`BB_ALLOWED_ORIGIN` must exactly match the browser origin. `BB_TERMS_VERSION` must be the currently published, reviewed required agreement version; clients submit it at verification. Agreement acceptance is recorded once per user/version; marketing consent is not implied. Access and refresh tokens are random opaque values stored only as SHA-256 hashes. `bb_session` expires in 15 minutes; `bb_refresh` rotates on `/auth/refresh` and has an absolute 30 day lifetime. Both are `Secure; HttpOnly; SameSite=Strict` cookies. `bb_csrf` is a separate readable `Secure; SameSite=Strict` cookie; authenticated mutations require its `X-BB-CSRF` echo and exact Origin. Challenge and verify require exact Origin and JSON requests. `/auth/logout` revokes both tokens; old access, refresh, material and artifact reads then fail. A normal browser close leaves the database session and server jobs intact.

The SMS routes and transport have been removed from the production API. The following paragraph describes the old foundation only. The local integration test injects an in-process synthetic transport; no network route exposes it and it is not evidence of production SMS. `BB_AUTH_OTP_KEY` and `BB_TERMS_VERSION` alone do not enable sending. No gifted credits are created or displayed by this API. Account phone change, closure/refund flow and invitation attribution remain separate release work; the #7 Issue stays open for browser/TLS and release acceptance.

The prototype `product-prototype/lib/auth.mjs` supplied interaction behavior and timing defaults only. Its JSON account store, demo code exposure, demo sessions and credit grant were not reused. The #8 routes retain their owner predicates; their production principal now comes from the PostgreSQL session instead of a client header. In-process principal injection remains solely for existing #8 tests and is absent from the production entry point.

The merged #8 slice uses `@bondbuddy/contracts` and does not extend the old Cowork backend or change the prototype. It adds `db/migrations/0001_m1_owner_data.sql` and `0002_artifact_download_grants.sql`, a PostgreSQL migration runner, a private Azure Blob adapter, and owner-scoped Fastify routes. #7 now resolves a verified PostgreSQL session in the production entry point; all personal routes reject unverified client headers, query IDs and cookies. Mutations require the configured allowed Origin and CSRF echo.

`/api/v1/runs/execute` is disabled in production with `501 CAPABILITY_NOT_READY` until #17 queue execution and #79 logging are integrated. The explicit test-only staging option records a `paused` run, event, and outbox atomically to prove ownership/idempotency; it never queues a model call or claims completion. Recognition, preflight, conversation, project event delivery, cancel, and resume also return 501. Artifact retrieval only serves rows from a trusted delivery writer with `passed` quality, `available` delivery, owner match, and fresh hash verification. Metadata creates a five minute download grant bound to the owner and artifact version; download rechecks the session and grant. There is no public artifact writer in this slice. Input snapshots reject requirement message IDs until a trusted message repository can verify them; rule/template/reference versions stay null until released registries exist. No synthetic tests establish live #6/#8 acceptance.

## #9 account settings, sessions and closure

Migration `0009_m1_account_lifecycle.sql` is append-only. It adds a `closed` user status with `closed_at`, `bb_auth_sessions.last_refreshed_at` and `revoked_reason` (`logout`, `user_revoked`, `password_changed`, `account_closed`), the `bb_account_closures` record, and a `BEFORE INSERT` trigger on projects, uploads, material versions, input revisions and runs. The trigger takes a key-share lock on the owner row and rejects writes for a closed account. Owners without a `bb_users` row are unaffected, so existing synthetic test owners still work.

Routes (all require the PostgreSQL session; mutations require exact Origin plus the `X-BB-CSRF` echo):

- `GET /api/v1/account`: username, masked legacy phone, accepted/current agreement version, password update time, `self_service_recovery: "unavailable"` and `support_contact` from `BB_SUPPORT_CONTACT` (null until published).
- `GET /api/v1/account/sessions`, `DELETE /api/v1/account/sessions/{id}`, `POST /api/v1/account/sessions/revoke-others`: list own active sessions, revoke one (a foreign or unknown ID returns 404; repeating the call is idempotent), or revoke all but the current session.
- `POST /api/v1/account/password`: verifies the current password through the same account and account/source limiter as login, stores a new Argon2id hash and revokes other sessions. A wrong current password returns `403 PASSWORD_INVALID`, not 401, so the browser does not treat it as session expiry.
- `GET /api/v1/account/closure` previews active runs, counts, retained record classes and `local_exports: "not_affected"`. `POST /api/v1/account/closure` needs `password` and `confirm_username`, and returns `409 ACCOUNT_CLOSURE_BLOCKED` while any run is not terminal. Otherwise one transaction soft-deletes materials (0006 writes storage tombstones) and projects, revokes artifact delivery and download grants, revokes all sessions, deletes the password credential, marks the user closed, and records the closure and a `user.closed` outbox event. The username stays reserved.

Legacy phone identities have no password, so none of these routes offers them a takeover path. There is no self-service or support-operated recovery route. A manual recovery process needs a reviewed identity verification procedure first. After closure, the storage lifecycle purges unpinned material bytes. Materials pinned by immutable input revisions, artifact bytes and prompt snapshot bodies have no post-closure purge yet. M2 must replace `balance_status: "not_applicable_m1"` with real frozen/refundable balance settlement before closure. The integration test `account.test.ts` needs only `BB_TEST_DATABASE_URL`.

## Project material events (0011)

Only a successful upload completion emits the currently supported public event, `material.upload_progress`. It is a terminal persistence confirmation, not a stream of intermediate browser/network progress: `uploaded_bytes` and `total_bytes` both equal the byte length whose SHA-256 and content were rechecked from private Blob storage before the material row was written. The event, project-local sequence increment, completed upload, material version, and `material.persisted` outbox row commit in one PostgreSQL transaction. A repeated completion returns the existing material and does not create another event. A rollback also rolls back the sequence allocation. Migration 0011 seeds one equivalent recovery event for each latest, active material row created before this feature, using its persisted byte count and original persistence timestamp.

`GET /api/v1/projects/{project_id}/events` checks the authenticated project owner before reading or validating cursor input; foreign/guessed project IDs receive 404. `after` is the project-local monotonic integer sequence from `next_cursor` (omit it on the first request). Events are returned by ascending `seq`; the default page contains 50 events, and an optional `limit` is bounded to 1–100. `next_cursor` is null at the end, otherwise it identifies the last returned sequence. Event rows are append-only and remain internal to their owning project. The public mapper only returns the shared `ProjectEvent` schema and explicitly selects its safe payload fields.

Recovery lists only events whose material version is still active and whose upload remains completed. The owner-scoped material read separately checks that its private Blob object still exists; missing/deleted objects receive 404, and storage outages receive retryable `503 DATA_UNAVAILABLE`. The Web client reads current material records from these event IDs and omits 404s; if a recovery request fails it clears recovered rows instead of showing stale saved state. Historical project event rows are retained after deletion but no longer appear in the current-material event page. No parse-progress or historical-profile event is emitted in this slice.

`apps/web/tests/project-events.integration.spec.ts` is an actual browser flow with synthetic identity and material data. Set `BB_E2E_REAL_API=1` and matching `BB_E2E_TERMS_VERSION` while a fresh PostgreSQL/Azurite API is running on port 3000 to register/login, create/upload, close the browser context, log in again and recover the material through real API/Blob storage; it also confirms deleted material disappears from recovery. The default Web suite keeps its explicitly intercepted API tests as synthetic UI tests.

## Upgrade, restore, and deletion decisions

Apply migrations in filename order using `npm run migrate:api` against the target database before starting an API revision. Migrations are append-only; there is no automatic destructive down migration. Before upgrade, take a transactionally consistent `pg_dump -Fc` plus a coordinated private Blob snapshot, retain the application revision and migration manifest, and test restore to a separate database/storage account. Example local database round trip:

```bash
pg_dump -Fc "$DATABASE_URL" -f /tmp/bondbuddy-m1-04.dump
createdb -h 127.0.0.1 -p 55433 -U bondbuddy_local bondbuddy_restore
pg_restore -h 127.0.0.1 -p 55433 -U bondbuddy_local -d bondbuddy_restore /tmp/bondbuddy-m1-04.dump
# For the synthetic integration fixture only:
# If provider result refs exist, also point this at the restored Azurite/private container.
BB_TEST_AZURITE_CONNECTION_STRING=UseDevelopmentStorage=true BB_TEST_PROVIDER_RESULT_CONTAINER=bondbuddy-m1-12-result RESTORE_DATABASE_URL=postgresql://bondbuddy_local@127.0.0.1:55433/bondbuddy_restore node db/verify-restore.mjs
```

Restore also requires Blob objects corresponding to database object keys; PostgreSQL backup alone cannot recover file bytes. Reconcile orphan uploads and deletion tombstones before reopening traffic. To roll back an application release, restore both database and Blob snapshots into an isolated environment, verify schema constraints and hashes, and then switch traffic. Do not reverse an applied migration in place.

Upload sessions expire in 15 minutes and can be retried with matching bytes; `complete` is idempotent after registration. The API verifies size, SHA-256, declared MIME and bounded structural content before the first Blob write, then rechecks the private Blob at completion. `persisted` means these checks passed and bytes exist, not that parsing/OCR succeeded. See [`UPLOAD-SAFETY.md`](./UPLOAD-SAFETY.md) for supported checks, fixed parser/archive limits, stable error mapping, and the unscanned malware/release limitations. No antivirus service is integrated or claimed; scanner selection and production acceptance remain CTO release decisions. Deleting a material marks its current access deleted but keeps bytes pinned by old snapshots/runs. The physical purge worker, orphan Blob cleanup, backup deletion replay, retention periods and provider-side deletion evidence remain release decisions. Do not advertise an effective deletion deadline until these are configured and tested.

## #79 observability foundation (bounded synthetic slice)

Migration `0005_m1_observability.sql` adds append-only operation, snapshot reference, usage observation, structured error, and versioned internal event records. It extends the existing outbox with a claim lease and acknowledgement token. The migration adds no public admin endpoint. `apps/api/src/observability.ts` is the restricted internal service surface: a trusted caller must pass the authenticated owner and an operator/service actor ID for timeline and usage reads. Reads are recorded in `bb_log_access_audit`; neither these query results nor outbox payloads contain prompt bodies, OTP, Cookies, or secrets. Prompt content is held only in a private Blob object; `saveSnapshotRef` verifies its hash and stores an opaque key, redaction version, input revision/hash, and optional rule/template/model parameter versions. A production prompt writer and privileged plaintext retrieval flow are **not yet installed**. The private Blob container must be encrypted and access controlled in the target environment.

The API's existing run submission writes an accepted operation in the run transaction; a trusted, schema-valid request rejected before run creation is recorded separately with a safe error code. Production 501 rejection records the requested revision/hash only when the authenticated owner owns the project; a foreign project remains unlinked and receives the same 501 response. These fields describe the rejected request, not a verified input snapshot. User-initiated operation events have `actor_type=user`; queue and usage events remain system events. #17 queue transitions emit the shared `InternalObservabilityEvent` contract in the same transaction as run events and outbox. The trusted queue's potential-call method can attach a same-project prompt snapshot and model ID before an external request. Usage observations are append-only; duplicate source events are idempotent. `bb_call_usage` measures an attempt only when all reported non-null token dimensions agree. A conflicting attempt has status `conflict` and null token fields; while any conflict exists, `usageTotals` returns null token totals rather than a potentially wrong sum. An explicit reconciliation path is future work; raw observations remain intact. Failed attempts with agreed measurements count. Cached input and reasoning output are subsets of input/output totals. Unknown, pending, and conflicting usage are unresolved, never measured zero. This is not billing.

`claimOutbox` uses PostgreSQL row locks and expiring leases. A consumer must forward an event durably, then call `ackOutbox` with its lease token. A crash or forwarding outage leaves the row replayable; stale tokens cannot acknowledge a later lease. Forwarders must deduplicate on outbox `id` or internal `event_id`. A failed outbox insert rolls back its business event. This foundation has no external log forwarder or alarm sink yet, so production execution stays `501 CAPABILITY_NOT_READY`.

Internal operator use: invoke `queryTimeline(pool,{actorId,owner,projectId?,jobId?,traceId?,from?,to?,status?,errorCode?})` and `queryUsage(pool,owner,jobId,actorId)` or `usageTotals`. Callers must derive `owner` and `actorId` from trusted authentication/authorization, never an untrusted request parameter. The functions enforce owner predicates and write access audit rows. Direct database roles should be limited to this service; database superusers can bypass application authorization. No prompt body retrieval is implemented in this slice.

Synthetic test evidence covers owned and foreign production 501 rejection records, accepted run and queue events, user actor attribution, same-project snapshot binding at the database boundary, prompt metadata integrity and redaction, failed retry plus duplicate/conflicting usage, unknown/pending semantics, owner denial, access audit, stale outbox lease/replay/ack, and forced transaction rollback. Fresh migrations 0001–0005 and PostgreSQL/Azurite integration are required. ## M1 username/password auth (#7, migration 0008)

Set `BB_ALLOWED_ORIGIN` to the exact HTTPS browser origin and `BB_TERMS_VERSION` to the published required agreement version. `POST /api/v1/auth/register` accepts normalized username, password and agreement version; `POST /api/v1/auth/login` accepts username and password. Both set Secure/HttpOnly access and refresh Cookies and a readable CSRF Cookie. The browser must send the CSRF Cookie value as `X-BB-CSRF` on authenticated mutations and use the exact Origin. Do not log request bodies, Cookie headers or response Set-Cookie. Argon2id uses 19 MiB, 2 iterations and one lane. A single normalized account gets at most 10 failures per 15 minutes; one account/source pair gets at most 5. Sources use Fastify's trusted remote address, not arbitrary forwarded headers. No IP-only lockout is applied. Passwords must have 12–128 characters (max 512 UTF-8 bytes) and no control characters. Usernames are 3–32 ASCII letters/digits/underscores starting with a letter, then lowercased.

Behind Nginx, set `BB_TRUSTED_PROXY_CIDR` to the controlled proxy address or CIDR so source limits use the actual client address. Leave it unset without a trusted proxy; arbitrary forwarded headers are then ignored. Size this setting to the deployment network, never an open client range. Expired login-limit rows require periodic retention cleanup in release operations.

Existing phone-only users remain separate and cannot gain a password by choosing a username. SMS endpoints are removed. Migration 0008 is append-only. Password reset/recovery and account migration require #9; real browser/TLS and release verification remain open. Production execute still returns 501.
