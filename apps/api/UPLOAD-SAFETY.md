# M1 upload content safety (bounded implementation slice)

This note records the local, deterministic checks used by the Fastify material upload path. It is a format/readability gate before a material is registered, not OCR, malware detection, professional review, or full #8 acceptance.

## Accepted formats and upload behavior

The implementation follows the seven MIME types in `packages/contracts`: PDF, DOCX, XLSX, CSV, UTF-8 text, PNG, and JPEG. PPTX is not in that contract; a PPTX package presented as DOCX/XLSX is rejected with `415 MATERIAL_FORMAT_UNSUPPORTED`. No public enum, error code, migration, or UI contract changed.

The API checks bytes and their declared SHA-256 before inspection. Inspection runs in a parser worker with a 45-second deadline, 192 MiB old-generation heap, 32 MiB young-generation heap, and 4 MiB stack. One inspection runs per API process; additional inspections wait in a bounded queue and can receive retryable `503 DATA_UNAVAILABLE` when the queue deadline expires. A parser error, worker error, crash, or timeout fails closed. The first successful `PUT` is inspected before its Blob write; `complete` re-reads the private Blob object, rechecks size/hash and inspects it again before creating the immutable material version. Repeated `PUT` and `complete` requests keep their existing retry/idempotency behavior. OpenAPI declares the additive retryable `503` response for this capacity backpressure using the existing `DATA_UNAVAILABLE` code; no MIME enum or error code was added. A `persisted` material means these checks passed and bytes are stored; it does not mean parsing/OCR or business preflight passed.

## Deterministic checks and limits

| Format | Local checks |
| --- | --- |
| PDF | PDF.js must parse the document and every page operator list; encrypted files, unreadable pages, JavaScript actions, embedded files, form fields/XFA except the narrow single filled-Sig profile below, external/unsafe annotations and selected active-action markers are rejected. Maximum 1,500 pages; the signed profile is capped at 16 MiB. |
| DOCX/XLSX | ZIP directory, local headers, paths, duplicate names, compression method, expanded sizes, CRCs, XML parts, content types, main document part and internal relationships are checked. Password-protected CFB Office files and encrypted ZIP entries are rejected. Maximum 1,024 entries, 32 MiB per entry, 128 MiB total expanded data, 100:1 per-entry/aggregate compression ratio, 32 path segments, and 16 MiB per XML part. ZIP64, symlinks, recognized nested ZIP/CFB/RAR/7z/gzip/bzip2/xz/zstd/lz4/tar/CAB signatures, macros, OLE/ActiveX/custom UI/active external links, unsafe external relationships, Word `altChunk`/external field instructions, and spreadsheet external or active formula functions are rejected. A DOCX Word XML part may have an external relationship only when its type is exactly the OOXML hyperlink type and its target is a strictly checked absolute HTTP, HTTPS, or mailto link; inspection never follows the link. XLSX external relationships are accepted only in a referenced `externalLink` relationship part, with the exact `externalLinkPath` type and external mode; bounded targets are opaque metadata and are never resolved or fetched. Other XLSX external relationships remain rejected. DOCX external templates, images, embedded parts, relative hyperlink targets, local-file schemes, script schemes, ambiguous URIs and control characters remain rejected. Accepted links remain in the source document and could be opened later by a user. Declared part content types are normalized for case and parameters and checked independently of part filenames; this rejects SVG, HTML/XHTML, script, and MHTML types even when `[Content_Types].xml` maps them to a neutral extension such as `.bin`. Expanded parts also receive a bounded 8 KiB prefix check for leading SVG/HTML/XML markup or MHTML headers. Referenced parts with detected active payloads are rejected, including generic `application/octet-stream` image targets under neutral names; markup with an image relationship is rejected. Prefix sniffing does not prove arbitrary binary data benign, and is not a recursive or exhaustive file-type classifier. The nested-container check recognizes listed signatures at expanded part start and known archive-like part extensions; it is not recursive or exhaustive. |
| CSV | UTF-8 and quoted-field structure are checked with row/cell limits (1,000,000 rows, 100,000 cells per row, 2,000,000 cells total). Formula-leading `=`, `+`, `@`, and non-numeric `-` values are rejected after leading Unicode/ASCII whitespace and a UTF-8 BOM are handled. |
| TXT | UTF-8 is checked incrementally; NUL and binary signatures are rejected. |
| PNG | Signature, chunk ordering and CRC, dimensions, pixel limit, IDAT deflate stream, expanded scanline size, and row filters are checked. Interlaced/animated PNG is rejected. Maximum 16,384 pixels per dimension, 16 million pixels, and 64 MiB decoded scanlines. |
| JPEG | Signature, frame dimensions, and full decode are checked with a pixel and decoder-memory cap. Maximum 16,384 pixels per dimension, 16 million pixels, and 96 MiB decoder memory. |

The existing error contract is retained:

- `422 MATERIAL_CONTENT_MISMATCH`: bytes do not match the declared type or text encoding, or upload hash/size differs.
- `422 MATERIAL_ENCRYPTED`: a password/encryption marker is detected.
- `422 MATERIAL_UNREADABLE`: a required structure is corrupt or unreadable, or the parser fails.
- `415 MATERIAL_FORMAT_UNSUPPORTED`: the package contains unsupported/active content or exceeds a local inspection limit.
- `503 DATA_UNAVAILABLE`: both per-process parser worker slots are already occupied; retry the upload request.

## Release limits and scanner decision

No antivirus engine or signature database is installed or called. The API does not claim malware detection, exploit detection, safe-document certification, or comprehensive PDF/Office schema validation. Local checks do not scan decoded text for arbitrary malware, identify malicious image payloads, safely emulate every PDF viewer or Office version, or prove that a syntactically valid document is benign. PDF action extraction depends on the selected PDF.js parser surface; compressed or malformed features that it does not expose may remain undetected. CSV formula detection covers the comma-delimited syntax and formula prefixes listed above; it is not a spreadsheet sandbox. The worker's V8 heap limits do not cap all native or external memory allocations, so deployment-level memory limits remain necessary. The parser dependencies themselves remain part of the trusted computing base.

The production scanner, operating mode, integration boundary, scanner outage policy, supported formats, operational alerting, and live acceptance remain an explicit release decision. Until that decision is made and verified in the target environment, this slice must not be described as antivirus scanning or complete production content safety. Structural parser failures/timeouts are rejected, but the local structural gate alone is not evidence that a file is free of malware.

Verification covers generated synthetic controls and the authorized `rq-202509-01` historical DOCX by manifest hash through both memory and spooled-file inspection. PostgreSQL/Azurite exercises upload ownership, rejected-byte non-persistence, and retry/idempotency behavior; it does not mutate production data or prove production scanner integration.

## Passive XLSX external workbook references (#359, 2026-09-29)

An `externalLink` XML part may contain Excel/WPS `alternateUrls`, `relativeUrl`, extension metadata, multiple passive `externalBook` entries and multiple `externalLinkPath` relationships. A structural element allowlist, single-book requirement and one-relationship requirement rejected a legitimate workbook. These conditions no longer decide upload validity. The package must still have a well-formed, bounded XML `externalLink` root, the expected content type, a workbook reference to each link part and external-mode relationships of the exact passive path type. No target is opened, fetched or evaluated; the Python XLSX parser uses `keep_links=False`. DDE/OLE, active XML nodes, macros, unsafe relationship types, malformed ZIP/XML, resource-limit violations and executable formula functions still fail closed. Ordinary indexed `[1]` formulas remain unevaluated and cached results remain unverified.

The old exact-byte inspection exception remains disabled by default for transition. After the general path is deployed and the reported bytes pass again, set `BB_UPLOAD_EXCEPTION_ENABLED=0`, remove `BB_UPLOAD_EXCEPTION_SCOPE`, recreate the API container and repeat the upload verification. This is a configuration cleanup, not a schema migration.

## Restricted filled-Sig PDF profile (#420, 2026-09-29)

A PDF containing one Widget may pass only when both PDF.js and `signed-pdf-profile.ts` accept the **same original bytes**. PDF.js parses the page, annotation and operator list; the bounded low-level reader independently checks the PDF 1.x lexical objects, classic cross-reference offsets, dictionary keys, references and signature gap. The low-level reader is TypeScript compiled into the existing API inspection worker, so the deployment image needs no new binary or runtime package. It is an intentionally small admission profile, not a general PDF validator or a CMS verifier.

The initial profile accepts one page, one combined `/FT /Sig` `/Subtype /Widget` field, one signature value and one unambiguous classic xref/trailer. The only indexed objects are catalog, pages root, page, page content stream, Widget and its appearance Form XObject. Every indexed object's exact byte offset and header must match the xref table; only whitespace/comments may appear between objects. All six objects must be reachable through the expected links. Duplicate dictionary keys, including aliases made with `#XX` name escapes, unknown keys, unresolved references, extra/hidden objects, object streams, xref streams, hybrid xrefs, `/Prev`, multiple revisions, nonzero generations and trailing bytes are rejected. The parser caps signed PDFs at 16 MiB, 64 xref slots, depth 16, 64 keys per dictionary, 4,096 array items, 64 KiB string/hex data and 8 MiB per stream. The outer upload gate still caps all files at 100 MiB, 1,500 PDF pages, a 45-second worker deadline and bounded heap/queue. Any cap or parse failure returns 415 before Blob persistence.

The catalog allows only `/Type`, `/Pages` and inline `/AcroForm`; the AcroForm allows `/Fields` and `/SigFlags`. The one combined field/Widget allows only `/Type /Annot`, `/Subtype /Widget`, `/FT /Sig`, bounded `/T`, `/Rect`, `/P`, `/F`, `/V` and `/AP`. Its `/V` allows only `/Type /Sig`, `/Filter /Adobe.PPKLite`, `/SubFilter /adbe.pkcs7.detached`, `/ByteRange` and hexadecimal `/Contents`. `/AP` has one `/N` Form XObject. The page and appearance use empty `/Resources`; nonempty or recursive resource graphs are rejected. The page content and appearance streams have direct, exact `/Length` and are also parsed as page operators by PDF.js. This first version does not accept separate parent fields, rich appearances, additional pages, other form types, FileAttachment, XFA or active actions. Escaped action names and duplicate keys are interpreted lexically, not by substring matching. The existing raw marker scan remains defense in depth only.

`/ByteRange` must be four nonnegative safe integers `[0, contentsStart, contentsEnd, fileLength-contentsEnd]`; the excluded interval is the **exact lexical `<...>` token** of the `/Contents` value in that Widget's `/V` object. Empty/odd/non-hex Contents, overlap, out-of-bounds ranges and any later unsigned revision fail. The bytes, Blob object and SHA-256 are never rewritten. This checks only byte-range shape. It does **not** validate CMS data, certificate trust, identity, signing time or factual contents. A synthetic `<01>` fixture is only a structural control and is not a valid CMS signature.

`PUT` runs the gate before writing the private Blob. `complete` downloads, hashes and reinspects the Blob before the material version and parse job commit. Migration `0076_m1_signed_pdf_assessment.sql` adds nullable, immutable `bb_material_versions.signature_assessment`; the only nonnull value is `{status:"signature_unverified",profile_version:"signed-pdf-classic-v1",signature_count:1}`. The public `MaterialResponse.signature_assessment` is defined only in `packages/contracts`; it is returned by completion and owner-scoped GET, and cannot be supplied by the client. `null` for existing or ordinary material means **not assessed by this profile**, not unsigned or verified. Parse status remains separate: scanned pages and financial gaps can still yield `needs_confirmation`.

The authorized `qx-202606-02` original was outside this v1 profile and previously returned 415. The general multipage extension below now handles it; v1 remains unchanged.

UI seam: `product-prototype/public/project-workspace.js` at prototype commit `33e9988bcb828a498d155a61f6745da31c6ee4a2` displays upload status, server error and retry in the material row. Browser code is unchanged here. A later UI change may read `MaterialResponse.signature_assessment` and say the signature has not been verified, separately from saved/parse states; it must not present this as a verified signature or confirmed financial data.

## Multi-page signed audit reports (#420, 2026-10-06)

`signed-pdf-multipage-v2` admits passive reports with 2–1,500 pages and up to 1,500 signature-widget appearances, including a stamp object reused on several pages. The same 16 MiB, worker memory, queue and deadline bounds apply. PDF.js checks every page; pinned pdf-lib 1.17.1 reads the classic object graph without rewriting the upload. A parser subclass rejects duplicate dictionary keys (including escaped aliases), active names in all parsed revisions, object/xref streams and hybrid xrefs before dictionary normalization. Current objects, including unreferenced objects, are walked with limits of 20,000 objects, 200,000 values and depth 64. Signature appearances may contain passive images/Form resources; recursive Form resources are rejected. Other form types, blank signatures, JavaScript/actions, XFA, attachments, encryption and active content remain rejected.

The Widget allowlist is Type/Subtype/FT/T/V/F/Rect/AP/P/DR. Its signature value allows Type/Filter/SubFilter/ByteRange/Contents plus Reason/Location/ContactInfo/M/Name/Prop_Build. Each populated Adobe.PPKLite/adbe.pkcs7.detached signature has four nonnegative integer ByteRange values; its excluded interval must match the exact original hexadecimal Contents token, with nonzero contents capped at 64 KiB. Earlier signatures may end at earlier PDF revisions; the latest signed range must end at the uploaded file end. These are structural checks, **not verification of CMS, certificates, signing identity, xref/revision authenticity or whether changes were authorized by a signer**. No file hash, issuer or filename is allowlisted.

Migration 0090 extends the existing immutable assessment to v2 and a bounded positive signature count. It counts distinct signature dictionaries, not repeated page appearances. The authorized 6,960,431-byte qx report has 74 page appearances of four signature objects; its unchanged SHA-256 is `f6ab6dae2d70f09390915ea9d3eeb7a755df51d3307f1eb204ae1243ed971844`. Tests cover acceptance, exact Blob bytes, persisted assessment, owner isolation and one durable parse job, plus active/ambiguous/unsigned-revision rejection. All accepted signatures remain `signature_unverified`; material parsing and OCR remain separate.
