# BondBuddy 开发任务拆解：先 Web，后 Windows

需求基线：2026-09-22。完整计划包含 **5 个 milestone、5 个跟踪 issue、71 个可认领子任务**。最近核对发布 5 个 milestone、75 个 issue，见 [GitHub 发布索引](GitHub发布索引.md)。

第三里程碑已确认指募集书复核，复用第二阶段的积分和付费能力。

## 分阶段上线

| 阶段 | 目标 | 子任务 |
|---|---|---:|
| M1 | 网页版注册/登录与募集书更新上线 | 31 |
| M2 | 积分与付费功能上线 | 11 |
| M3 | 募集书付费复核功能上线 | 10 |
| M4 | 材料生成与用户问答上线 | 12 |
| M5 | Windows 应用上线 | 7 |

M1 为受控试用、平台承担成本（排期默认，不是长期免费承诺）；M2 接入真实积分付费并覆盖已上线的募集书更新；M3 上线复核；M4 上线材料生成和独立 QA；M5 才开发并发布 Windows 客户端。阶段按用户顺序上线，工程可按依赖提前并行。M1 的项目对话已包含真实追问与补充；M4 扩展独立专业 QA 与其他文书对话。

## Web 与 Windows 的边界

Web 阶段无需安装本地服务：材料必须经明确上传才能由服务端处理，按账号隔离、权限控制、加密与保留/删除策略保存工作副本。关闭浏览器不取消服务端任务；恢复登录可查看。具体保存期限与服务商保留条款在 M1-01 交付设计中落实。

M5 原文件、解析、缓存和任务检查点主要保存在本机，必要内容经平台网关发模型。Web 项目迁移为用户显式操作，不默认全量同步或删除云端副本。平台账号、钱包和账务一直作为统一权威。

## 认领与依赖

每条 issue 包含目标、范围、依赖、建议角色、可验证验收、交付物和规格链接。所有任务默认未指派；成员自行设置 assignee，权限不足可评论认领并由维护者分配。没有虚构工期和到期日。规则包按 11 个市场/品种或 DFI 安排分别拆分，方便行业专家与工程师并行；工程规则包的拆分不对应额外的用户入口。

建议首批并行认领：M1-01 架构、M1-02 短信、M1-08 文档解析、M1-11 模型接入、M1-14 规则发布规范、M3-04 数据采购与适配契约。M1-31 上传后识别历史稿市场/方式/报告期并输出难度依据，M2-02 的计价验收依赖该结果；公式与接口设计可以提前。现有任务不重编号，M1-30 发布验收包含新增的 M1-31。上线顺序仍遵循五个里程碑。

## 发布与维护

源数据及文档生成逻辑在 build-plan.mjs；修改后运行 `node build-plan.mjs`，将生成 plan.json 与 issues/ 正文。`node publish-issues.mjs --check` 仅作本地校验；不带参数仅远端读取与预览；`--apply` 才执行已获授权的发布。M3 未确认时必须显式选择 `--milestones=M1,M2,M4,M5`。发布前先将规格与任务草案推送到同一分支，发布器会读取全部现有 milestones/issues 排重。

GitHub 发布使用官方 gh 已登录账号，按稳定隐藏标识识别本批任务，创建原生父子 issue 关系并保存 published.json。每次变更后保存远端映射，最终核对全部标签、里程碑、正文和父子关系。不自动指派、不发额外邀请、不覆盖已有人工内容。网络/权限/审批失败时停止；不盲重试创建，重新发现远端标识后继续。

该清单补充并优先于 v1.1 的 Windows 首发安排；产品业务约束、大公募与 DFI、私有券商模板以及指定积分方案保持。
