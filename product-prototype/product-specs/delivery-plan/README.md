## 分阶段上线

| 阶段 | 目标 | 子任务 |
|---|---|---:|
| M1 | 网页版注册/登录与募集书更新上线 | 32 |
| M2 | 积分与付费功能上线 | 11 |
| M3 | 募集书付费复核与参考库推荐上线 | 12 |
| M4 | 材料生成与用户问答上线 | 12 |
| M5 | Windows 应用上线 | 7 |

M1 为受控试用、平台承担成本（排期默认，不是长期免费承诺）；M2 接入真实积分付费并覆盖已上线的募集书更新；M3 上线复核；M4 上线材料生成和独立 QA；M5 才开发并发布 Windows 客户端。阶段按用户顺序上线，工程可按依赖提前并行。M1 原稿选填、手填原/目标信息和企业关系；原对话区改补充要求，不设多轮聊天；M2 不含余额现金退款或用户消费记录页；M3/M4 对话按各自范围交付。

## Web 与 Windows 的边界

Web 阶段无需安装本地服务：材料必须经明确上传才能由服务端处理，按账号隔离、权限控制、加密与保留/删除策略保存工作副本。关闭浏览器不取消服务端任务；恢复登录可查看。具体保存期限与服务商保留条款在 M1-01 交付设计中落实。

M5 原文件、解析、缓存和任务检查点主要保存在本机，必要内容经平台网关发模型。Web 项目迁移为用户显式操作，不默认全量同步或删除云端副本。平台账号、钱包和账务一直作为统一权威。

## 认领与依赖

每条 issue 包含目标、范围、依赖、建议角色、可验证验收、交付物和规格链接。所有任务默认未指派；成员自行设置 assignee，权限不足可评论认领并由维护者分配。没有虚构工期和到期日。规则包按 11 个市场/品种或 DFI 安排分别拆分，方便行业专家与工程师并行；工程规则包的拆分不对应额外的用户入口。

原始任务索引（现有 assignee 以 GitHub 为准）：M1-01 架构、M1-02 账号、M1-08 文档解析、M1-11 模型接入、M1-14 规则发布规范、M1-34 统一日志契约及接入、M3-04 数据采购与适配契约。M1-34 为 P0 基础设施，设计从第一批启动，随模型/队列/已保存补充要求同步实现；交付验收依赖相关链路完成，首个用户更新任务开放前必须 ready。M2-03 复用其用量证据作收费归因，不延迟采集。M1-31 保存用户填写的原稿市场/品类/报告期及更新难度依据，M1-13 改为补充要求，M1-28 支持非同企业参考及无原稿编制；M1-32/33 建库推荐与维护移入 M3，M1-30 不再依赖。M1-26/29 保留真实修订/新稿交付。所有材料直接交 worker，财务读取核对在任务内进行，不要求独立财务提取服务。上线顺序仍遵循五个里程碑。

## 发布与维护

原始任务及当前范围覆盖位于 build-plan.mjs 和 scope-20260930.mjs、scope-20261001.mjs；修改后运行 `node build-plan.mjs`，将生成 plan.json 与 issues/ 正文。`node publish-issues.mjs --check` 仅作本地校验；不带参数仅远端读取与预览；`--apply` 才执行已获授权的发布。M3 未确认时必须显式选择 `--milestones=M1,M2,M4,M5`。发布前先将规格与任务草案推送到同一分支，发布器会读取全部现有 milestones/issues 排重。

GitHub 发布使用官方 gh 已登录账号，按稳定隐藏标识识别本批任务，创建原生父子 issue 关系并保存 published.json。每次变更后保存远端映射，最终核对全部标签、里程碑、正文和父子关系。不自动指派、不发额外邀请、不覆盖已有人工内容。网络/权限/审批失败时停止；不盲重试创建，重新发现远端标识后继续。

本清单按 2026-10-01 用户决定修订；旧发版历史不等于当前任务已完成。它补充并优先于 v1.1 的 Windows 首发安排；产品业务约束、大公募与 DFI、私有券商模板以及指定积分方案保持。
