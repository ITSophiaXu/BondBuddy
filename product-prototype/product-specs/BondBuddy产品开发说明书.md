## 00 产品边界与需求决策

### 0.1 产品定位

BondBuddy 是服务券商从业人员的债券文书任务软件。用户个人注册、充值，提交项目材料，完成募集书全文更新、专业复核、配套材料生成及债券 QA。按最新要求先做网页版，最后做 Windows 下载应用；产品将结构化项目信息与右侧多轮对话结合，持续维护项目事实和成果版本。

本版“首发市场/品种”指募集书更新或复核各自首次上线时的覆盖范围，并不表示五个里程碑同时上线。M1 上线 Web 注册/登录与更新，M2 上线积分付费，M3 上线募集书付费复核，M4 上线五类材料与独立问答，M5 上线 Windows。用户已明确付费复核在积分付费之后上线，详见[开发任务清单](delivery-plan/README.md)。

首发不以团队采购、机构审批流、协同编辑或在线 Word 审阅为前提。专业机构签发、投资决策、现场尽调和人工法律判断仍由有权主体实施；软件产出必须与实际取得的证据相符。

### 0.5 术语与责任

- 项目：长期保存的工作资料容器。创建、编辑、导入材料免费。
- 执行任务：用户一次明确执行请求对应的不可变输入快照、一次冻结和一个最终结算。
- 成果版本：成功输出及其来源快照；再次执行生成新版本，原成果保留。
- 事实：有主体、期间、口径、单位、来源和状态的信息；用户说法属于一类来源，不等于已审计事实。
- 规则包：特定市场、品种、有效期间的专业规则集合，经专业验证后发布。
- 模板：章节、字段、表格、样式与适用条件的版本集合，不包含可直接挪用的其他发行人事实。
- 平台内部参考库：无历史稿时后台获取结构参考的能力，普通用户不可浏览。
- “成功”：请求的成果通过交付检查且可供用户取得；不是模型返回了文本。

本文用要求 ID 连接功能与验收。供应商商品名称、精确字段、接口协议和法规有效版本未取得正式依据的部分列为接入条件，不以虚构接口或条号填补。

### 0.6 设计默认

M1 作为受控试用，平台承担成本并记录用量；这是为衔接 M1 与 M2 提出的排期默认，不是长期免费承诺。M2 开始真实钱包和收费，不追溯扣取试用任务费用。功能按已验收能力逐步开放，未上线功能不能用演示成果替代。

Web 项目及用户明确上传的材料按账号保存在平台工作区，保存期限、删除与备份清理必须在 M1 发布前落实；关闭浏览器不取消服务端任务，同一账号重新登录可继续查看。平台按账号限制并发，防止失控成本。

M5 本地项目不会自动跨设备同步。设计默认每设备同时运行一个大型文书任务，关闭窗口进入托盘，完全退出或系统关机保留检查点。用户可显式迁移 Web 项目或导出本地备份，不默认同步全文或删除云端副本。平台钱包始终支持跨端并发一致性。以上设计默认可经验证调整并记录变更。

## 01 Web 优先架构与 Windows 客户端

### 1.0 分阶段架构

最新交付顺序为先 Web，后 Windows。本章 1.1、1.4–1.7 的本机安装、存储、托盘与恢复要求在 M5 验收；M1–M4 不要求用户安装本地服务。共享业务规则、事实与证据格式、任务快照、模型适配、文档流水线和平台钱包从 Web 阶段建立，避免桌面阶段重写业务。

| Web 组件 | 责任与边界 |
|---|---|
| 浏览器 UI | 登录、项目表单、文件上传、右侧对话、状态与下载；不保存供应商密钥或权威余额 |
| Web API 与关系数据库 | 账号隔离、项目/材料索引、事实、对话、版本、权限和乐观锁 |
| 私有对象存储 | 已上传材料、OCR 页图、成果及模板；加密、授权下载、到期与用户删除 |
| 服务端任务队列与工作进程 | 解析/OCR、受控 Codex 执行、文档组装、检查点和崩溃恢复 |
| 平台网关与钱包 | 模型/数据代理和真实用量；M2 起冻结、结算、充值退款 |

Web 文件通过 HTTPS 上传，服务端确认写入和内容哈希后才成为可执行材料。原件、派生数据、日志和备份分别定义保留期限与删除规则；材料正文不进入普通遥测。用户已提交 prompt 及实际模型请求的必要内容按第 16.9 节存加密限权快照，普通日志仅持有引用，不能因为不记录普通正文而漏记 prompt。免费预检与付费处理边界沿用第 04、14 章，浏览器缓存不是项目唯一副本。

M1-34 统一可观测性在第一批设计，模型网关、任务队列、对话与材料服务共同传递 trace/job/call ID，并通过事务 outbox/可靠缓冲留证。从首个用户更新任务开放前，prompt、job 类型、token 用量、成功/失败及 error 可查询；日志管道、权限、用量去重和故障恢复未验收不得开启功能。M1 记录试用真实消耗，M2 才接积分账务。

关闭页面、浏览器断网或退出登录不等于取消任务。服务端继续运行，用户重新登录通过同一 run_id 和事件游标恢复查看；取消必须由明确操作产生服务端终态。工作进程故障恢复须先核对已发请求，不能盲重发。Web 不能使用“原文件只在本机”的说明。

Web 发布需有 TLS、受保护会话、CSRF/跨源控制、短期授权下载、文件校验、任务资源隔离、备份恢复、运行监控与回滚。具体部署地域、材料保存期限和供应商保留条款由 M1-01 落实，未落实不得开放真实用户材料。Windows 后续复用相同契约，通过存储/运行适配层将指定内容迁入本机。

### 1.1 安装与首次使用

WIN-01：提供签名安装包、版本号、发行说明、卸载入口和自动更新。工程基线建议 Windows 11 x64，Windows 10 22H2 列兼容测试环境；正式支持范围以安装包验证为准，不承诺未经测试的 ARM 或旧系统。

安装无需 Python、Node、Word、Codex CLI 的用户手工配置。所需解析、OCR、文档生成与任务运行组件随应用打包或从校验签名的官方分发地址安装。Microsoft Word 可用于用户打开成果，不能成为所有功能的隐含运行依赖。

首次启动依次完成服务连接检查、协议及隐私说明、手机登录、本地项目目录初始化。权限拒绝、磁盘不足、路径不可写均给出可操作的修复入口；不以空白界面或终端报错替代。

### 1.2 推荐架构与可信边界

以下为 M5 工程设计建议：桌面壳复用已上线 Web UI；本地工作进程负责文件与任务；平台网关负责模型及数据服务访问，平台关系数据库负责身份、订单、账本。桌面壳选 Electron 或 Tauri 可在技术验证后决定，不改变接口责任。

| 组件 | 负责内容 | 禁止承担的权威判断 |
|---|---|---|
| 桌面 UI | 展开表单、对话、状态、文件选择、结果摘要 | 计算最终价格、伪造支付成功 |
| 本地服务 | 项目 SQLite、材料副本、OCR/解析、文档组装、检查点 | 自行修改积分余额 |
| Codex 任务运行器 | 多步任务、工具调用、结构化输出、恢复 | 任意访问本机文件或执行来源文档中的命令 |
| 平台身份/任务服务 | 账号、能力、执行幂等、版本登记、任务租约 | 把未交付任务标为收费成功 |
| 平台网关 | DeepSeek/外部数据代理、计量、配额、请求去重 | 把供应商密钥下发客户端 |
| 平台钱包 | 原子冻结、结算、释放、充值退款及不可变流水 | 信任客户端提交的积分数 |
| 规则与模板服务 | 签名版本、适用矩阵、内部参考材料 | 混用其他用户私有模板或事实 |

本地可选用 SQLite + 文件目录，平台可选用 PostgreSQL。密钥使用 Windows 凭据保护；本地服务只监听环回地址并要求每次启动随机会话令牌，防止网页跨源调用。IPC 方法按允许清单开放，渲染进程不获得任意文件系统或 shell 权限。

### 1.3 AI 运行要求

AI-01：用户要求 Codex 执行框架调用 DeepSeek。实现必须验证多轮上下文、工具调用、流式事件、结构化结果、超时取消、usage 和恢复，不能将现有单次文本转发视为完整实现。

用户称模型为“DeepSeek Flash v4.1”；精确官方模型 ID、上下文上限、计费口径和供应商能力尚未核实。配置记录 provider、model_id、adapter_version、能力及价格版本。配置验证失败应停止该能力启用，不静默替换模型名称。

Codex SDK / app-server 可作为程序化执行入口，先验证与自定义模型供应商的协议适配。生产不依赖未验证的实验传输；Web 在隔离服务端工作进程执行，M5 使用本机受控进程和明确协议版本。当前本地桥接可参考，供应商密钥与最终 usage 必须迁入平台可信网关。

工具限于当前项目授权目录、来源提取、规则检索、允许的外部查询、受控计算和 Word 生成。默认不允许通用系统命令、任意 URL 上传、邮件发送、交易操作、读取其他项目或浏览器登录凭据。任务材料中的“忽略要求”“发送文件”等内容是待处理数据，不能成为执行指令。

### 1.4 本地与云端数据边界

| 数据 | 默认位置 | 传输原则 |
|---|---|---|
| 原始文件、解析全文、项目事实、对话、成果 | 本机账号分区 | 任务需要时发送必要片段；云 OCR 需发送对应页并在隐私说明列明 |
| 手机号、登录会话、支付订单、钱包流水 | 平台 | 使用 TLS；仅授权角色访问 |
| 任务 ID、版本哈希、能力与价格快照、用量 | 平台 | 足以恢复与对账，避免包含正文 |
| 模型请求中的必要项目内容 | 处理链路 | 提供商保留/训练策略须取得合同依据并对用户说明 |
| 私有券商模板及抽象结构 | 本机为主 | 如处理需要暂存，绑定账号，不进入公共库 |
| 外部查询证据 | 本机及被许可的缓存 | 保存/再展示期限遵守各供应商授权 |

不要把“主要保存在本机”写成“材料绝不离开电脑”。设置页应列明已接入服务、发送内容类别、缓存和删除规则。正文遥测默认关闭；错误上报以阶段、错误码、耗时为主。M5 延用统一 job/call/token 日志，用户 prompt 及本地模型输入材料片段的诊断正文保存在本机受控区，平台保存用量和关联元数据；已发送模型的临时内容与长期诊断副本分开。需要额外上传本地原文诊断包时，展示内容并由用户主动发送。

M5 模型代理链路的临时内容建议任务完成后 24 小时内清理；此为待供应商合同及恢复方案验证的设计目标，不适用于 Web 项目工作副本。Web 用户持续编辑与下载需要独立的项目留存策略。订单、账务与法定记录依实际法定期限留存，不能与项目正文共用删除策略。

### 1.5 运行、暂停和恢复

WIN-02：主窗口关闭默认进入托盘，任务继续；首次说明“退出应用将暂停本机处理”。不把睡眠或离线表现成任务仍在计算。

1. 启动后平台冻结成功，本地持久化 run_id、输入哈希和 reservation_id。
2. 每个可恢复阶段提交检查点，包括已解析内容版本、已完成请求 ID、生成结果中间版本。
3. 网络断开：停止新收费调用，保存状态，显示等待连接；已经发出的请求先查询结果，禁止无条件重发。
4. 完全退出/系统关闭：尽可能保存检查点；平台通过租约超时标记等待恢复，不直接收费成功。
5. 再启动先对账，再恢复同一 run_id 和冻结。用户取消则全额释放。设计默认暂停 24 小时后自动取消；此前站内提醒，可配置延长，不能无限冻结。
6. 取消与完成并发由平台原子终态决定；若取消已生效，迟到结果不得再扣分。

不承诺电脑关机后在云端继续处理本机材料。已在云端进行的单个请求可完成并缓存响应，整体任务需电脑恢复或被取消。

### 1.6 文件、更新与备份

项目目录由应用生成安全 ID，不直接使用用户输入拼路径。导入时复制到工作目录，保存原文件名及哈希；原文件不覆盖。切换账号不能看见前一账号目录清单。

导出项目备份包含材料、对话、事实和版本清单，用户选择目标位置；备份不含访问令牌或模型密钥。导入备份重新绑定本机账号，历史账单只读引用云端记录，不导入“余额”。

应用升级必须校验签名、备份本地数据库并支持失败回滚；运行中大型任务在安全检查点后升级，不强杀写入。卸载默认保留项目数据，另提供明确的删除本地资料选项。删本地资料不等于注销账号或退款。

## 02 注册登录与账号

> 2026-09-24 M1 决策：用户选择用户名密码注册/登录，短信供应商接入不需要。以下短信界面及验证码段落为历史原型，当前 M1 实现与验收以本段及 Issue #7 最新要求为准。用户名使用 3–32 位 ASCII 字母、数字或下划线，以字母开头，转小写后唯一；密码 12–128 字符，服务端仅存 Argon2id 哈希。注册记录当前协议版本和一次注册事件；登录失败统一提示，并按账号及账号/来源组合限制尝试。旧手机账号不会由同名新账号自动接管。人工找回按第 2.7 节定稿执行；旧手机账号不自动迁移，不开放无人核验的自助找回。


### 2.1 目标与范围

AUTH-01：个人券商用户通过真实手机验证码注册/登录，账户集中管理积分和充值订单。首发不要求用户自行开通模型账号，不要求为领取赠分上传身份证。手机号验证证明号码控制权，不能对外宣称已经完成自然人身份认证。

设计默认首发大陆 +86 手机号；其他地区号通过配置开放。若供应商不支持某地区，在发送前明确提示。

### 2.2 页面字段与状态

| 字段/操作 | 必填及校验 | 反馈 |
|---|---|---|
| 手机号 | 必填；区号与号码规范化；前后空格可清理 | 格式错误本地提示；服务端再次校验 |
| 获取验证码 | 合法手机号后可用 | 发送中、倒计时、失败可重试；不展示验证码本身 |
| 验证码 | 必填，按短信供应商定义的位数 | 过期/错误统一易理解提示 |
| 服务协议及隐私政策 | 必要同意独立展示，可打开全文 | 记录版本、时间；营销同意不能默认勾选 |
| 邀请码 | 可选，可从有效邀请链接带入 | 绑定前显示归因；首次有效归因后锁定 |
| 登录/注册 | 同一主按钮 | 号码不存在时创建，存在时登录 |

设计默认验证码有效 5 分钟、发送间隔 60 秒、连续错误 5 次使本挑战失效；具体供应商限制可更严格。账号、设备、IP 多维限流，同单位共用网络不得作为直接封禁依据。响应不泄露手机号是否已注册。

状态：待输入 → 发送中 → 待校验 → 校验中 → 已登录；发送失败、验证码失效、限流等保留手机号，不清空整个表单。生产环境禁止演示短信、万能验证码或页面回显。

### 2.3 注册成功与赠分

M1 原子创建 user 并保存注册幂等事件，不展示尚未真实入账的赠分。M2 启用 wallet、welcome_reward，按实际用户规则去重；同一验证码重复提交不重复赠分。欢迎积分 2,000，30 天有效，活动规则见第 14 章。M1 存量账号按 M2-08 的明确迁移规则处理，不能补写虚假历史账单。

首页展示“注册赠送 2,000 积分”和到期日，不承诺它足够完成某份募集书。赠分发放失败但账号已创建时，用户仍能登录，记录可恢复发放事件，显示“积分发放处理中”，不诱导重复注册。

邀请关系使用签名链接/规范化邀请码绑定；不得由客户端直接写 inviter_id。手机号、设备等风控标识最小化留存，注销后防重复领分的必要标识及期限应写入隐私规则。

### 2.4 会话与账号设置

AUTH-02：短期访问令牌 + 可撤销刷新会话，或同等安全的服务端会话。设计默认访问有效期 15 分钟、刷新会话最长 30 天；登出、手机号变更和高风险事件可撤销。Web 使用 Secure/HttpOnly/SameSite Cookie 和相应 CSRF 防护，不在 localStorage 持久化会话密钥；M5 令牌存入 Windows 安全存储。任何端都不把令牌写入日志。

设置页包含显示名称、绑定手机号掩码、当前版本、设备会话、数据服务说明、协议、联系客服和注销入口。Web 提供云端项目存储与删除说明；M5 增加本机项目位置和备份设置。券商名称在立项报告中按项目填写，不把其当作注册强制企业认证。

当前 M1 的账号找回和联系渠道变更以第 2.7 节为准；本节原有换号流程仅作为历史短信方案记录，不能仅凭新号码接管账号。一个账号跨设备使用钱包一致；Web 可访问该账号云项目，M5 本地项目仅存在创建或导入它的设备，除非用户显式迁移。

### 2.5 登出、注销及权益

Web 登出撤销当前会话，服务端任务继续且不能再用旧会话读取材料；登出前说明运行状态，可主动取消。M5 普通登出保留本机加密/隔离资料，下次登录恢复；运行任务需明确选择继续本机后台或取消。不因登出自动核销全部冻结。

注销前列出未完成任务、冻结余额、可退购买积分，以及云端项目和本机资料各自的处理选项。先处理任务与退款，再按留存策略删除云端正文与派生资料并关闭账号；法定订单/账务记录可按规定留存，其用途和期限须说明。活动积分不可提现；已购买未用积分按原订单比例退款。

账号注销不会自动删除用户自行导出到其他位置的 Word 或备份。删除本机目录时再次显示准确目录和涉及资料，避免误删用户源文件。

### 2.6 接口与验收

当前 M1 接口：POST /api/v1/auth/register、POST /api/v1/auth/login、POST /api/v1/auth/refresh、POST /api/v1/auth/logout、GET /api/v1/me。账号设置、改密、会话撤销和注销已接入 /api/v1/account 路由；人工找回按第 2.7 节定稿，恢复相关入口现已实现，按配置启用。请求/错误公共约定见第 16 章。

| ID | 场景 | 预期 |
|---|---|---|
| AUTH-A01 | 同一验证码重复提交 | 一个账号、一次欢迎赠分 |
| AUTH-A02 | 过期/错误验证码 | 不创建账号，不发积分 |
| AUTH-A03 | 修改邀请码后再次验证 | 已锁定关系不改变 |
| AUTH-A04 | 同单位多个真实用户同 IP | 不因共用网络一律封禁 |
| AUTH-A05 | 已登出令牌调用材料接口 | 被拒绝，返回安全错误 |
| AUTH-A06 | 注销时有冻结任务和余额 | 先完成状态与退款处理，账务可追溯 |
| AUTH-A07 | 协议更新或营销选项未勾选 | 必要协议版本可追溯，正常注册不绑定营销 |

### 2.7 M1 人工找回与身份核验（定稿 v1）

2026-09-26：按用户“自行定稿、简单一点”的要求，#9 采用以下流程。这里核验的是**原账号控制权**，不作自然人实名或券商资质认证。M1 由 Chris 或其指定的一名客服处理即可；复用现有客服渠道和受限工单，不建设多级审批或单独的客服系统。

#### 三步处理

1. **提交申请。** 用户通过产品公布的客服入口（`BB_SUPPORT_CONTACT`）提供用户名、遇到的问题和回复渠道。客服建立一条工单；未核验前统一回复“已收到申请，需要核验原账号归属”，不透露账号是否存在、项目或材料信息。收到申请不锁号、不改密、不结束现有任务。
2. **核验原渠道。** 客服从申请前已经核验、且与该 `user_id` 绑定的联系记录发起确认，例如原邮箱或原客服会话。对方在该旧渠道确认本次工单后才可通过。临时新填的号码/邮箱、姓名、单位、身份证照片、项目名、文件截图和材料内容都不能单独证明归属；不要求用户提交身份证或客户材料。
3. **用户自行设新密码。** 核验通过后，客服通过上述旧渠道发送一次性重置链接；链接 30 分钟有效，仅用于该账号本次改密。用户自行设置符合现有规则的新密码，客服不询问、不代填密码。重置成功后撤销该账号全部旧会话及未使用的重置链接，通知原渠道，并让用户重新登录；`user_id`、项目、材料和运行任务保持不变。

#### 没有旧记录时怎么办

**原渠道不可用，或从未绑定过可靠渠道，就不执行人工重置。** 客服说明无法确认归属，保留原账号和资料；用户可另行注册，但不转移原账号资料。客服认识申请人、申请人能描述项目，均不构成例外。旧手机号也不能仅凭一条新号码验证码迁移或合并成用户名账号；旧手机身份迁移不在本简版恢复能力内。

为使正常账号以后能够找回，首次绑定或变更恢复渠道需要用户**已登录且再次验证当前密码**，然后在新渠道完成一次确认；记录服务端确认的 `user_id`、渠道和核验时间。不得在忘记密码后补录一条“事前已绑定”记录。现有账号尚无这类记录时，明确提示暂不具备人工找回条件。

#### 实现只保留必要约束

- 重置链接由服务端生成，使用足够长的密码学随机值，仅存 token 哈希；绑定账号/工单/用途，过期或用过即失效。重复申请沿用未结工单，重新签发作废旧链接；复用现有账号及来源限流，不因申请次数锁住正常登录。
- 发链接须有指定客服权限及已通过的工单；链接不提供读项目、下载材料或登录能力。只有用户提交有效链接和新密码时，才在同一事务更新 Argon2id 凭据、消耗授权、撤销会话并写审计/outbox；任一步失败全部回滚。
- 每次处理只留工单号、账号内部 ID、事前联系记录引用、核验结论、客服身份、时间和结果；按现有受限记录保存策略处理。密码、重置链接/token、Cookie 和客户材料不得进入普通日志、GitHub 或仓库。核验工单也不发到公开 Issue。

用户提示统一为：“忘记密码请联系客服；需通过事先绑定的联系方式核验。无法核验时不能重置，原账号资料仍保留。”客服未配置或恢复功能尚未部署时，不显示可用的找回入口。

#### 最小验收与当前状态

| 场景 | 结果 |
|---|---|
| 旧绑定渠道确认本次工单 | 一名指定客服可签发链接，用户自行改密后重新登录 |
| 只有新号码、项目截图，或没有事前绑定 | 不重置、不迁移资料、不泄露账号信息 |
| 链接过期、重复使用、用于其他账号或客服无权限 | 拒绝；原账号不受影响 |
| 改密成功 / 事务失败 | 成功时旧会话全部失效、资料和任务保留；失败时凭据与授权一并回滚 |

**恢复渠道绑定、受限客服工具和用户重置页面/API 已实现。** 详见 [#9 运行与验收说明](../../docs/ACCOUNT-RECOVERY.md)。需配置客服入口并给指定账号授予专用客服权限才启用；确认码、链接与完成通知仍由客服通过原渠道人工发送。`self_service_recovery=unavailable` 保持兼容，不代表人工恢复不可用；不能以手工改数据库替代正式入口。旧手机身份不自动迁移。

技术依据：[OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) 关于独立联系渠道、单次限时 token 和重置前不改变账号的建议；30 分钟及单客服处理是本项目的简化决定。

## 03 首页与项目管理

### 3.1 导航与首页

HOME-01：主导航依次提供首页、更新募集书、复核募集书、材料生成、QA 问答；全部项目入口与账号/积分/设置保持稳定。普通用户端不出现募集书库、蓝图推荐、内部业务匹配结果。

以上是完整产品导航。M1 仅开放已验收的更新入口和项目内对话，M2 增加钱包/充值，复核及材料/独立 QA 分别按后续里程碑开放。未上线入口隐藏或明确不可执行，不显示虚假余额、成果或演示数据。

首页先展示用户的项目和可继续的工作，提供四个核心功能入口。推荐结构：

1. 顶部简短欢迎信息、可用积分和充值入口。
2. 四张任务入口卡，描述分别为全文更新、三维复核、五类文书、债券专业问答。
3. 运行中/待补材料的工作，可恢复至正确位置。
4. 最近项目与最近成果，展示类型、发行人、更新时间、状态。

不以宣传横幅、充值套餐或内部资源库占据主要首屏。统计区按 update、review、generation、qa 独立计数，不把 QA 和材料生成归为一个“生成”数。

### 3.2 项目列表与详情

| 项目属性 | 展示/规则 |
|---|---|
| 名称 | 可编辑；为空可由发行人+任务类型生成 |
| 类型 | 更新、复核、材料生成；QA 会话单独管理，可关联项目 |
| 发行人 | 已填/已识别全称，主体冲突需标记 |
| 市场与品种 | 识别或用户选择的当前值，不显示未经确认的猜测 |
| 状态 | 草稿、待补材料、处理中、等待恢复、已完成、失败、已取消 |
| 最近成果 | 最新成功版本、生成时间、下载 |
| 存储位置 | Web 云端工作区；M5 本机项目标明所在设备，不在本机的文件不可伪装可下载 |

列表支持名称/发行人搜索、类型及状态筛选、最近修改排序；空状态提供创建入口。工作进程与平台状态短暂不同步时显示“正在同步”，不以刷新将进行中任务变成新草稿。

项目详情左侧为结构化信息及材料，右侧为对话。完成后增加结果摘要、下载区、历次成果和账单入口。没有应用内逐条 Word 接受/拒绝 UI。

### 3.3 项目、版本、任务关系

PRJ-01：一次项目可以多次执行。每次执行锁定项目字段、材料文件哈希、对话需求版本、规则/模板版本及输出目标。编辑不改变已运行任务的输入。

运行时允许查看与编辑“下一版草稿”；明确提示“修改将在下一次执行时生效”。同一项目避免同时两个写作任务竞争“最新成果”，设计默认串行执行；跨项目云端钱包仍做并发保护。

用户在 Word 中自行修改后，如需继续处理，应导入该文件为新的输入基线，系统显示其与上次成果不同。不能认为本地导出文件被编辑后项目事实已经自动更新。

成功版本具有 v1、v2 等可读名称，并保存不可变 artifact_id、哈希及来源快照。旧版本不覆盖。下载失败可重试，重新导出同样内容免费；改变内容属于新任务或平台纠错。

### 3.4 项目操作

| 操作 | 规则 |
|---|---|
| 创建/重命名/修改字段 | 免费，自动保存；Web 提示服务端保存状态，M5 提示本机保存状态 |
| 复制项目 | 新项目 ID，可复用同账号材料解析；不复制冻结或消费记录 |
| 归档 | 隐藏默认列表，仍可恢复、下载 |
| 删除 | 先处理运行任务；分别显示云端或本机材料/成果影响范围，保留法定云账本 |
| 关联材料生成 | 锁定所选成果版本，不随原项目后续变化漂移 |
| 关联 QA | 显示项目范围，可切换；不自动把所有项目全文放入上下文 |
| 从失败恢复 | 区分系统重试同任务与用户新需求重新执行 |

材料与模板有共享引用时采用引用计数/依赖清单；删除一个项目不应破坏其他项目已锁定的材料和成果。已成功版本至少保留可重建的来源快照，用户主动清理时告知后果。

### 3.5 结果摘要规范

更新摘要：处理范围、实际新增/替换期间、章节变化、多品种联动、材料冲突与待核实项、成果文件。

复核摘要：三类已执行范围、问题数量与级别、未覆盖项、资料截止日/查询时间、报告和批注文档。

生成摘要：文种、来源募集书版本、模板/券商、完成章节、待确认项、成果文件。

M2 起所有结果提供最终积分消耗和可用余额；结算对账中时显示“成果已生成，积分结算处理中”，禁止显示猜测的扣分。M1 受控试用不展示伪造账务。摘要不披露内部参考库条目或他人文件名。

### 3.6 验收

HOME-A01：新账号空状态能直接进入当前已开放任务；已存在项目的账号首先能找到项目。

HOME-A02：筛选、刷新、应用重启后状态一致，四种业务计数不混淆。

PRJ-A01：修改运行任务的草稿后，当前成果仍对应启动快照；下次执行才采用新值。

PRJ-A02：复制、归档、删除、恢复不会重新收费或破坏其他项目。

PRJ-A03：Web 同账号跨设备可访问云项目与云账务；M5 不得显示不存在于该设备且未显式迁移的本地文件为可下载。

### 3.7 通用交互规范

设计默认宽窗口左侧表单约占可用工作区 2/3、右侧对话约 1/3，对话最小宽度约 320px；低于约 1,100px 时切换上下布局，保持字段顺序和输入不丢失。具体断点由设计稿与可用性测试定，不把侧栏压到不可读。

所有输入有可见标签，示例使用 placeholder 且不作为真实默认值提交。必填、可选、金额单位、时点、错误文字直接可见；不只依赖颜色、悬停或小问号。输入错误定位到字段，保留其他内容。

支持键盘焦点、清晰聚焦状态、合理 Tab 顺序及 Windows 显示缩放；错误/进度变化向辅助技术提示。对话 Enter 发送、Shift+Enter 换行可作为默认，中文输入法候选确认不得误发送。

长任务按钮防重复点击，但不锁死全应用；用户仍可查看其他项目、取消任务及保存下一版需求。删除资料、注销、真实支付等有实质影响的操作需清楚展示对象；普通保存、导航和生成前不添加无意义确认。

## 04 材料导入与证据处理

### 4.1 目标与固定分区

MAT-01：用户在明确的材料分区直接选择/拖入文件，不先选择“材料类型”下拉。Web 阶段是上传至账号隔离的服务端工作区；M5 桌面形态主要是导入本机工作区，只有真实发生网络传输时才称为上传。两种方式均需显示真实进度及保存状态。

| 功能/条件 | 分区 | 必需性与内容 |
|---|---|---|
| 更新且有历史稿 | 历史募集书 | 必需，本发行人基线文件 |
| 更新且无历史稿 | 相似募集书 | 可选，仅供结构参考 |
| 更新 | 审计报告 / 财务报表及附注 | 必需；覆盖任务所需期间，允许多文件组合 |
| 更新且无历史稿 | 上述财务材料中的年度审计及分业务收入附注 | 完整编制前须取得可核实的发行人业务基础 |
| 更新 | 募投项目与权证材料 | 条件必需，按用途提示 |
| 更新 | 其他项目材料 | 可选，评级、债务、授信、决议等 |
| 复核 | 待复核募集书 | 必需 |
| 复核 | 审计报告 / 财务报表及附注 | 必需 |
| 复核 | 其他核验材料 | 可选，用于核对已知差异或补充证据 |
| 生成 | 最新版募集书 | 默认必需；可改选已存在的项目来源 |
| 生成立项报告 | 券商模板 / 参考立项报告 | 无本人已存可用模板时必需 |
| 生成 | 立项规则或其他支持资料 | 依文种提示，不强制所有材料共用同一清单 |

募投材料提示包含可研、项目备案、土地及建设许可、基金备案、子公司股权投资方案和批准文件等。提示只列实际相关项，不要求每种用途上传全部权证。

更新任务的材料清单用于识别所需证据，不要求每个分区齐全后才处理全文。按2026-09-25用户确认，已有可用发行人材料时，即使缺当期附注、审计意见页或部分发行条款资料，也按现有材料执行全文更新；在相关内容及结果摘要标记“材料缺失／待人工确认”，不编造缺失事实。缺少可读历史基线等导致任务本身无法执行的情况仍需说明原因，详见第05章 UPD-GAP-01。

### 4.2 文件格式与容量

MAT-02：设计目标，普通材料支持 DOCX、原生/扫描 PDF、XLSX、CSV、TXT、PNG、JPG/JPEG。文件名不能决定格式，以实际内容识别 MIME/文件签名。

历史和待复核募集书优先 DOCX，以保留编辑结构和可识别的字体信息。首发目标允许 PDF 作为基线，但需明确：

- PDF 历史稿先重建带原页锚点的可编辑 Word 基线，再输出相对此基线的修订版和清洁版；说明重建限制，不能承诺保留源文件所有版式或宣称是原生 Word 的既有修订轨迹。
- PDF 复核中无法可靠提取的字体、字号、Word 域等标记未覆盖；不能判为格式通过。
- 扫描 PDF/图片支持属于 OCR 要求，不能据此声称任意排版均可高保真还原。

当前原型历史/待复核仅 DOCX，PDF 基线扩展列为新增实现。旧二进制 DOC、XLS、加密文件、宏文档需先转换或提供可读副本；不给出改扩展名的假修复建议。

初始容量设计：每项目最多 60 份、合计 500 MB、单份 100 MB，扫描件允许分卷；这是相对当前 80 MB 总限额的扩容目标，须压测后发布。单文件页数阈值设计 1,500 页，超过给出拆分入口。限制由服务端/本地统一配置，不能浏览器接受而后台静默截断。模型上下文不足采用分块，不截断尾部后宣称全文完成。

### 4.3 导入进度与错误恢复

Web 文件状态：selected → uploading → persisted → prechecking → ready；支持单文件重试与中断恢复，服务端校验大小、签名与哈希。M5 文件状态：selected → copying → imported → prechecking → ready；发生网络传输另有 transfer 状态。执行后两端均可进入 parsing → needs_confirmation / parsed / failed，不能混淆本机复制和网络上传进度。

每行展示文件名、大小、分区、实际字节进度、状态、失败原因、重试/移除。上传或复制到 100% 后仍未保存成功时显示“正在保存”；未知总量的 OCR 显示已处理页数，不编造百分比。总进度应说明按字节还是按页计算。

支持逐文件重试、取消未完成导入、批量添加。一个文件失败不要求重传其他成功文件。新文件完成持久化及哈希后才进入项目 material_revision。用户删除引用时保留运行中快照所需文件；执行中的源文件不能被物理改写。

### 4.4 预检与收费边界

上传/导入、普通无外部付费调用的提取、文件校验、计价估计免费。Web 预检在服务端，M5 可在本机执行。预检识别：文件可读性、主体线索、期间线索、材料分类、重复文件、必要材料是否存在、明显缺页和扫描情况。

用户选择“有历史募集书”时，上传后自动执行源信息预检，识别原市场、发行方式和报告期，详见第 05 章 M1-31。先用原生文本提取；扫描件或关键证据不足时，设计默认允许在限定页数/请求预算内使用平台承担成本的 OCR/模型辅助识别，缓存结果并记录 billable=false。超出预检预算仍不能确定时展示待确认、请求用户校正或补清晰材料，不伪造成功。此预检不冻结或扣取用户积分，后续任务也不补收该成本。

其余用户可计费的全文 OCR、模型解析或 embedding 建索引，仍属于用户点击执行后的内部阶段，并入该次任务计量；不得一上传就全量收费处理。执行前无法确定的非关键工作量可按文件页数/格式等估算预留；影响迁移定价的关键源市场/方式/期间尚未确定时，先补充或校正，不按猜测强行归档收费。执行时发现局部材料缺失，按第05章继续全文处理并标记受影响内容；只有实际无法形成可交付工作稿时，才按失败/澄清规则释放冻结、由平台承担该失败任务费用。不得把单个缺失项直接等同于整单失败，也不因有待确认项额外发起扣费。

“正在解析”必须区分免费预检解析与执行中的付费阶段；M1 成本由平台承担，不提前扣取尚未上线的积分。文件准备完成不等于财务数字已校验，不能在未读取时确认“资料齐全且准确”。

### 4.5 证据数据规范

每个证据锚点最少包含：

| 字段 | 定义 |
|---|---|
| material_id / content_hash | 原文件不可变身份 |
| locator_type / locator | PDF 页码及框坐标；DOCX 段落/表格/单元格；Excel 工作表/单元格 |
| literal_quote | 可回到原材料核验的原文，不只保存模型总结 |
| extraction_method / version | 原生解析、OCR、人工校正等方法 |
| confidence / uncertainty | 原始置信度、待确认原因、确认记录 |
| source_kind | 审计材料、用户补充、公开公告、商业数据、模板参考等 |
| observed_at / valid_as_of | 获取时间与该事实对应时点分开 |

DOCX 页码随字体、软件和打印设置变化，原生锚点采用段落/表格 ID，不编造静态页码。需要页码时使用带渲染版本的快照并标明来源。

事实键至少为：主体 + 合并/母公司/其他范围 + 指标/事项 + 期间起止或时点 + 币种 + 单位 + 会计/统计口径 + 数据版本。不同键的同名数字不能直接覆盖。

事实状态：extracted、verified、user_asserted、conflicted、needs_confirmation、superseded。模板中的公司名、金额、签字和示例永远不得进入发行人事实集合。

### 4.6 财务/OCR 工作流

OCR-01：保留原始图像、页序、方向校正信息、表格结构及坐标。处理跨页表头、合并单元格、负数括号、千分位、百分号、“—”与空白、小数点、人民币元/万元/亿元等。

1. 识别文件主体、审计机构、审计意见、报告日期、报表期间、合并/母公司范围。
2. 提取三大报表与附注，分开保存原字符串、标准化数值和单位转换。
3. 进行表内合计、报表平衡与跨表核对；勾稽通过不能反过来证明 OCR 每个数字正确。
4. 模糊数字、主体/列头错位、与其他材料冲突的值进入待确认队列。重要的发行规模、债务、收入、利润等不能用低可信值完成关键结论。
5. 对话里展示“小范围原页片段 + 识别值 + 所属期间/口径”，让用户校正或补高清材料。这是材料确认，不是首发未包含的 Word 逐条编辑器。
6. 保存校正者、时间、原值与新值；用户确认不能被记录为审计机构已经确认。

数值零、空值、不适用、未提供必须分开。负数不能因括号丢失变正；报表横向年度顺序改变时按列头识别，不按固定第几列。

### 4.7 冲突处理及缓存

同一事实有多个来源时，保留全部候选与来源日期。已更正审计报告可替代其明确更正范围内旧值；工商最新状态不能覆盖历史报表时点；用户口述不能静默覆盖审计事实。必要时追问究竟采用哪个有效版本。

缓存键至少包含账号、文件内容哈希、解析版本、OCR 版本、口径修正版本。相同文件改名或同账号跨项目引用，可复用成功提取结果；新增页或替换文件只处理增量。不同账号默认不共享私人内容缓存。

失败任务已产生的有效解析成果可缓存，但该失败任务成本由平台承担。以后复用这些成果不得倒补收失败费用。规则变更只重做受影响判断，不无故重复解析原文件。

### 4.8 验收

| ID | 输入/操作 | 预期 |
|---|---|---|
| MAT-A01 | 上传 3 份，1 份中断 | 2 份保留，失败文件单独重试；不扣分 |
| MAT-A02 | 同内容不同文件名再次导入 | 识别复用，无重复解析费 |
| MAT-A03 | 文件为旧 DOC 但扩展名 DOCX | 识别真实格式，提示转换 |
| OCR-A01 | 扫描表格中负数括号/小数点模糊 | 保留原页与不确定标记，不直接出确定结论 |

| OCR-A03 | 一页横排、跨页附注、年序倒置 | 还原页序/列头，无法还原明确阻断相关结论 |
| MAT-A04 | 引用中的页码或引文不存在 | 来源检查失败，不能当有效证据 |
| MAT-A05 | 超限/缺页/加密材料 | 预检说明具体问题，不静默丢失内容 |

### 4.9 Web 实现边界（2026-09-25，#12 后续切片）

当前 `apps/web` 已接入 #149 的持久化解析任务与历史稿识别查询。文件行分别呈现上传保存、解析任务和历史稿源信息；排队/执行中自动读取，暂停、失败、缺失记录或网络错误明确提示，可手动重新读取。历史稿原市场/方式、年度和中期报告期、报表口径、截止日、原文及不确定性单独展示，不写回本次目标。重开项目、刷新和重新登录均从账号隔离的服务端恢复；切换项目/账号丢弃旧请求结果。读取状态不会重新创建识别、执行全文更新或扣积分。

这不替代前文 MAT/OCR 的完整验收：#153 已提供持续 worker、OCR hook 和回填 CLI；#17/#35 仍需部署和旧材料回填/重启验证，#14 + #17 需在实际 OCR 环境验收上传处理链路；#76 + #8 需开放源信息校正并完成授权真实材料验收。OCR 未启用或引擎不可用时，扫描件显示等待 OCR，不能显示为识别通过；没有任务的早期材料显示“暂无记录”，不能无限显示排队。识别 DTO 当前仅支持原文摘录和版本关联展示，原页/锚点导航仍须相应证据接口支持。测试及阻塞责任详见 `apps/web/MATERIAL-PROCESSING-ACCEPTANCE.md`。

## 05 更新募集书

### 5.1 用户目标与主流程

UPD-01：用户提供既有募集书或仅提供发行人资料，系统依据目标市场、品种、报告期和发行安排，生成全文一致的募集书工作稿。有历史稿时在本发行人原文上修改并交付修订版；无历史稿时内部取得结构参考并编制新稿，相似募集书为可选材料，用户无需自行寻找。

主流程：创建草稿 → 填写项目信息和添加材料 → 可在右侧讨论补充 → 点击“开始更新” → 免费预检与后台冻结 → 解析及全文处理 → 质量检查 → 摘要和 Word 下载。

上线门槛：M1-34 的统一日志必须先行验收，受控试用也须能从用户 prompt/结构化输入、材料版本追到 job、每次模型调用及 token、最终 Word 或 error。右侧问答、免费预检、失败/取消/执行前拒绝均在记录范围内，不能等 M2 计费上线才采集，详见第 16.9 节。

不显示报价确认、更新范围选择或内部匹配说明。创建和编辑时保留草稿并指出输入、材料缺口；执行全文更新时按已有材料继续处理，局部缺失或不确定内容标记待人工确认，详见 UPD-GAP-01。余额不足时保留输入并提供充值，充值后需再次点击。

### 5.2 表单字段

所有选填分组默认展开。必填用于确定目标和开始任务，草稿允许未填。

| 分组/字段 | 必填/形式 | 规则与提示 |
|---|---|---|
| 项目名称 | 必填，单行，可自动建议 | 不作为发行人法定全称 |
| 发行人全称 | 必填，可从材料带入后校对 | 与审计主体不一致时追问，不能用简称错配 |
| 历史募集书 | 必填，只有“有/没有” | 不说明相似稿作为蓝图的实现方式 |
| 发行市场 | 必填，下拉三项 | 上交所、深交所、交易商协会；变更时重新检查发行方式 |
| 发行方式 | 必填，市场联动 | 在同一个下拉框中按已选市场展示下表选项 |
| 目标最新报告截止日 | 必填，日期/已识别日期建议 | 不能晚于已提供可用报表；期间窗口由规则确定 |
| 申报/注册总额 | 选填，数值+单位/未知 | 与本期规模分开；不得用 0 表示未知 |
| 本期发行规模 | 选填，数值+单位 | 不超过已确认总额；存在特定安排时列待核实 |
| 债券安排 | 选填，多行自由文本 | 提示规模、期限、利率方式、含权、各品种差异、回拨等 |
| 参与机构 | 选填，自由输入 | 单一主承销商填名称即可，多家补分工 |
| 评级与增信 | 选填，多行/材料 | 分清主体评级、债项评级、保证人评级；无资料不默认 AAA |
| 募集资金用途 | 选填，下拉+补充 | 六类用途，可增加其他用途行及金额；不得只允许单一用途 |
| 其他项目信息 | 选填，多行 | 客观信息；更多说明也可在右侧对话提供 |

| 已选发行市场 | 发行方式下拉选项 |
|---|---|
| 上交所 | 普通私募公司债、小公募、大公募 |
| 深交所 | 普通私募公司债、小公募、大公募 |
| 交易商协会 | PPN · 定向债务融资工具、MTN · 中期票据、CP · 短期融资券、SCP · 超短期融资券、DFI · 储架发行 |

先选择发行市场，再选择发行方式。DFI 是交易商协会下的发行方式选项，与 PPN、MTN、CP、SCP 在同一控件中展示；不设置独立入口、独立功能卡片或额外注册模式选项。切换市场时清除不适用的发行方式并提示重新选择，保留其他可复用项目信息。

目标财务窗口按有效规则、品种和申报阶段确定，不能将现有 annualCountFor 的私募两年/其他三年硬编码作为所有情况下的完整规则。前台不增加“更新几年”必填框；后台比较新旧材料确定真正变更的截止期 N。

#### 交易商协会发行方式的处理说明

UPD-DFI-01：发行市场为交易商协会时，发行方式包含“DFI · 储架发行”。切换市场后重新校验选择；保存、返回、重新打开项目及材料生成关联必须保留 nafmii-dfi。前台仅选择一次，不另问注册模式。

选择 DFI 后，继续使用已展开的“发行规模与债券安排”分组，不另建或改名为一套专属表单。申报/注册总额、本期发行金额和债券安排沿用通用选填字段。示例：“本次编制统一注册文件，覆盖 MTN、CP、SCP，各期金额、期限待定。”用户可在右侧对话补充注册申报阶段、已取得的注册通知、有效期、覆盖品种及承销商团分工，也可直接上传文件。不得为通过表单而强填一个虚构的注册额度或本期利率。

“其他项目材料”分区提示注册申报文件、已取得的注册通知、分期发行计划及承销商团安排。申报阶段尚未取得通知的，记录待取得；不得把“缺少通知”直接判成发行人违规或禁止创建草稿。

UPD-DFI-02：处理时区分统一注册文件与具体一期发行文件。注册阶段依项目资料描述覆盖范围和拟定安排；本期阶段按实际工具品种、条款和届时有效规则披露。识别原稿优先看封面、标题和注册文件，不能因 DFI 正文列有 SCP 就把整份文件识别为 SCP，也不能因中票正文引用 DFI 通知就改写成统一注册文件。

统一注册与分期发行安排、资金用途、风险、信息披露、持有人机制和参与机构须相互一致。覆盖多个工具不等于已全部发行；涉及 ABN 等复杂结构仍按独立能力/规则门槛处理。DFI 的首发要求不自动扩展所有被覆盖工具的上线范围。

### 5.3 资金用途与材料联动

| 用途 | 需要识别的信息 | 材料提示与处理 |
|---|---|---|
| 借新还旧 | 拟偿还债券/债务、余额、到期日、使用金额 | 债券存续清单、兑付安排；与一般有息债务用途区分 |
| 偿还有息负债 | 债权人/类别、余额、到期及拟偿金额 | 借款合同、债务明细，核验是否符合目标产品用途要求 |
| 补充流动资金 | 金额、业务需求、测算依据 | 不凭空写新增收入或项目投资 |
| 项目建设 | 项目主体、投资总额、进度、资本金、拟投入额 | 建议可研、备案、土地、建设许可等实际适用文件 |
| 用于投资股权 | 标的、持股安排、对价、支付阶段、批准 | 股权投资相关方案与协议，不默认归入某会计科目 |
| 用于基金出资 | 基金名称、备案、角色、出资承诺/实缴、投向 | 基金备案及出资文件，核对穿透用途与限制 |

混合用途逐项金额汇总，与本期规模、发行费用及“拟/不超过”等限定一致。用途未定时允许保存草稿；关键用途不能确认时不编造完整发行方案。

不询问“是否重大资产重组”或“是否设置投资者保护条款”。系统读取审计附注、交易资料和适用规则识别相关事项；存在重组线索但缺交易证据时追问具体资料。业务/资产增长超过或低于 50% 都不能单独证明发生或未发生重大重组。

### 5.4 多品种与机构的灵活输入

UPD-02：不预建“品种一、品种二”。提示示例：“拟发行不超过 10 亿元，3 年期；如安排多个品种，请补充每个品种的规模、期限、含权条款及是否可回拨。”

多品种文本解析后形成 tranche 列表，保留原输入。关键歧义在对话中追问，例如两档规模之和与本期规模冲突、某档期限缺失；用户无需为了通过表单先学数据结构。

每一档需能表达名称、金额或上限、期限/续期、利率类型、还本付息、赎回/回售/调息、增信、用途差异、发行对象及回拨关系。单品种可继承共用值；存在差异必须显式覆盖，不能把其中一档条款复制到所有档。

参与机构解析为 institution + roles + tranche_scope。单一承销商名称可作为主承销商，不能据此猜测它同时担任受托管理人、簿记管理人。多家仅在实际角色有依据时分类；联席主承销商可空。

修改发行规模、期限或品种后，必须检查封面、发行概况、风险、资金用途、偿债、评级增信、投资者保护、机构表等受影响位置。

### 5.5 有/无历史稿分支

有：历史稿为本发行人的输入基线，识别源市场、品种、期间、完整性和已有修订。旧稿结构完整但较旧，不自动判为不完整；PDF 格式难度进入解析，不改变历史稿身份。

#### 在历史原文上修订（M1-26、M1-29）

UPD-REV-01：有历史稿必须以用户上传原文为基线进行增删、替换与必要的章节重排，不从其他发行人募集书重写一份新稿替代修订。保留未受影响的文字、有效历史事实、样式、表格、编号及引用；跨市场/发行方式时按新规则调整结构，但保留变更与原稿的对应关系。

原件不可覆盖。已有修订的 DOCX 先在独立副本取得有效正文基线（包含既有插入，排除既有删除），保存基线哈希与原件对应关系；本轮新增修订单独记录。每个变更绑定原段落/表格单元格、前后内容、新证据和变更理由，不能只把文件命名为“修订版”，也不能把全文删除再插入来伪造逐处修订。

交付真实 Word 修订版和清洁版。用户在 Word 内接受全部本轮修订后，正文和表格与清洁版一致；拒绝全部本轮修订恢复有效基线。应用内仍只需摘要和下载，不增加逐条接受/拒绝编辑器。

历史稿为 PDF/扫描件时，先重建可编辑基线，保留原页定位，再输出相对此基线的修订版、清洁版及重建说明；这不等于原 PDF 自带 Word 修订或版式无损。关键原文/数字不能可靠还原时先补清晰文件或校正，不静默降级为无历史稿编制，也不将识别错误当作本次业务修改。

#### 上传历史稿后的自动识别与难度依据

UPD-SOURCE-01（M1-31）：用户选择“有”并上传历史募集书后，材料保存成功即自动识别原稿的发行市场、发行方式和财务报告期。M1 必须完成识别、校正、持久化及与本次目标的比较；M2-02 在此基础上接入积分估算与实际结算，不能等到收费阶段才补识别能力。

| 识别项 | 要求 |
|---|---|
| 原发行市场 | 上交所、深交所、交易商协会；其他或无法确定时保留原文和状态，不默认回退 |
| 原发行方式 | 沪深普通私募、小公募、大公募；协会 PPN/MTN/CP/SCP/DFI。仅写“公募”时结合发行对象识别，证据不足标待确认 |
| 原财务报告期 | 保存年度及中期的期间起止、截止日、最新截止日和合并/母公司口径；区分财务报告期、签署日和发行日 |
| 原稿完整性 | 完整/不完整/待判断及其依据，不按原稿年份较旧直接判不完整 |
| 依据与状态 | 原文锚点、材料版本、识别方法、字段置信状态、用户校正记录，均可追溯 |

从封面、发行概况、发行对象、报告期定义、财务章节与表头交叉核对，不能只读文件名或按正文第一个市场/品种关键词归类。标题为 DFI 的注册稿和仅引用 DFI 通知的中票发行稿须分别识别，仍沿用“交易商协会 → 发行方式”的界面层级。

历史稿材料区展示“正在识别原稿信息 / 已识别 / 待确认 / 识别失败”，并列出原市场、原发行方式、原报告期，支持查看依据、校正和重试。“历史稿识别结果”与“本次拟更新目标”分别存储和展示：本次目标由项目表单确定，不被原稿自动覆盖。原稿不属于本发行人、报告期定义与表格冲突或小/大公募无法区分时，先展示差异并追问；不能静默按高难度档计价。

M1 生成版本化的 UpdateDifficultyInput：原市场/方式 → 目标市场/方式的迁移方向、原稿完整性、原报告期集合、目标期间与新材料支持范围，以及保留/新增/替换/实质重述期间、估计 N 和依据。保留年度不重复计期，同一截止日的三张报表、合并/母公司和重复材料不重复计数。上传预检只能给出估计分类，实际新增/重述与最终 N 由执行阶段核定；积分仍结合真实有效用量，不能仅凭“跨品种”或“新增几年”给一个固定整单价。

| 例子 | 应形成的难度依据 |
|---|---|
| 原稿含 2022–2024 年；目标保留既有期间、仅新增 2025 年 | 旧期间保留，估计新增 1 个截止期，N=1，不按原稿三年加新一年计为 4 |
| 原上交所私募转深交所小公募，财务期间均不变 | N=0，仍记录市场/方式迁移及章节、条款调整工作 |
| 原稿含 2022–2024 年和 2025 年一季度 | 完整保存四个期间及最新截止日 2025-03-31，不把封面发行年份当财务截止日 |
| 同一 2024 年截止期在多个附件、三表和不同口径重复出现 | 分别保留事实口径，计价截止期去重；有实质重述时记录理由 |

每次识别绑定材料不可变版本；替换历史稿、补新材料、校正源信息或修改目标均使旧比较/估算失效，重算下一版，不改写已启动任务快照。识别结果按账号和内容哈希缓存；该免费预检如需受控 OCR/模型，其成本由平台承担，不能直接或在后续复用时补收用户积分。全文财务解析与更新仍由用户明确点击执行后启动，边界见第 04、14 章。

#### 无历史稿

没有：允许可选相似稿，发行人年度审计材料为必要事实基础。即使用户没有上传相似募集书，系统也必须从最近完整年度合并报表的分业务主营业务收入识别前三大业务，自动匹配采用相同口径的内部已验收参考文书并起草。缺少主营业务收入明细时不得回退使用营业收入或母公司收入，按第 15.2 节 LIB-01A 补证据/审核。M1-32 交付可用后台库与索引，M1-33 负责持续更新，M1-28 消费该能力；不能只有匹配算法而没有可用参考数据。匹配算法、歧义与无匹配处理见第 15 章。

用户主动提供的参考稿可以作为指定结构参考，经可读性、目标适用性与事实隔离检查使用；它不是本发行人历史稿，也不能作为发行人事实来源。自动匹配必须满足用户要求的前三大业务一致，不用“同行业大概相似”替代。

三业务名称经已审核的同粒度分类/别名映射后，按集合一致匹配，原收入顺位不同不自动排除；逐项金额、占比、年度、口径和来源仍保留。匹配后依据目标市场、发行方式、实际品种及文书阶段检查适用性，选择可用的结构与写法参考。事实和数字来自本发行人审计材料、其他证据及已记录的用户补充；按目标规则生成独立的新稿，不附相对参考企业的修订痕迹。用户上传相似稿不自动进入平台库。

这里的推荐是内部选择过程，前台不新增推荐列表、参考稿选择页、库搜索或索引维护步骤；项目状态只显示正常的材料处理与编制进度。库的身份、候选及内部匹配理由保存在后台追溯记录，不出现在用户成果说明里；本发行人的事实来源和实际规则依据照常提供。

若材料无法支持完整编制，解释实际缺口，例如“请补充最近年度分业务收入附注”；不向用户输出内部候选名单。内部参考能力不足时显示“当前资料组合暂无法完成编制，请联系支持”，不归咎于余额，不收费。

### 5.6 全文处理工作分解

下表是语义章节映射，不是所有品种统一的法定目录。实际顺序和强制字段来自对应规则包。

| 章节族 | 处理要求 |
|---|---|
| 封面、重要提示、释义 | 名称、期间、规模、市场品种、关键风险和术语全篇一致；签署日不自动等于生成日 |
| 发行概况与条款 | 读取共用及分品种安排，核对对象、金额、期限、含权和角色 |
| 风险因素 | 逐项核对风险是否仍存在及影响，不能仅因年份旧而删除；有重大负面证据不能隐藏 |
| 募集资金用途 | 用途、债务/项目清单、金额、许可及资金安排互相一致 |
| 发行人概况 | 名称、股权、实控人、治理、资质、子公司、重大事件按时点与来源更新 |
| 主营业务及经营 | 分板块收入/成本、业务模式、客户供应商、经营指标；不编造变动原因 |
| 财务会计信息 | 三表、附注、合并与母公司、审计意见、会计变化及追溯重述 |
| 财务分析 | 指标、变动、债务和现金流，原因须有材料支撑，避免金额增长直接写因果 |
| 偿债与信用 | 债务结构、授信、偿债安排、评级对象及报告日期 |
| 增信及保护 | 担保/抵质押条款、持有人机制、受托管理、承诺与触发条件 |
| 重大事项及关联关系 | 关联交易、或有事项、诉讼、处罚、承诺、重组与期后事项 |
| 信息披露、机构、备查 | 对应市场的披露安排、机构信息、备查文件与引用编号 |
| 目录、交叉引用与附件 | 标题、表号、指代、目录和页眉；不残留其他发行人的信息 |

跨市场/品种更新执行目录映射、发行对象及术语变化、条款和披露差异核验，不能全局替换“上海”为“深圳”后视为完成。N=0 的纯条款/结构更新仍可执行；全文扫描检查一致性，不虚构新增财务期数收费。

### 5.7 财务与事实约束

- 事实来源与可用性分别记录：有明确来源定位的未审计中期财务材料或本发行人历史稿，不因“非审计来源”一律排除；仅在主体/材料版本锁定、值与证据可靠、无未解疑义/冲突时使用。采用处标注来源与待核审计范围，不能写成审计机构已确认，不能把旧审计意见移用于新一期。
- 公式保存值、外部链接缺源、OCR存疑数字等保留具体不确定性。人工核对记录绑定原件hash、表页/单元格、期间/口径/单位、确认者/时间与依据；保存核对表或选择候选不自动清空不确定性、不改标已审计，也不启动付费更新。缺口按UPD-GAP-01继续处理。
- 报表数据用 Decimal/定点计算；内部精度与展示小数位分开，容差根据源文件精度推导。
- 资产=负债+权益按实际表结构；现金净变动计入汇率影响等列示项；净利润不能忽略少数股东等口径。
- 毛利率按收入和成本重算；整体毛利率不能平均各板块百分比。占比变动使用“百分点”与相对百分比的正确概念。
- EBITDA、有息债务、利息保障、受限资产等使用项目定义，保存公式、分母、财务时点和资本化利息处理依据。
- 工商实缴资本、注册资本与报表实收资本分开；主体/债项/担保人评级分开。
- 授信信息记录授信银行、截至日、总额度、已用/未用、币种；仅当口径相同才能检验总额=已用+未用。
- 材料中“未提供”不能写成“没有”；历史事件发生日期不得随报告期机械更新。
- 未解决的事实冲突不得写成确定性结论；材料缺失或条款不确定按 UPD-GAP-01 处理，继续更新有依据的内容并保留明确标记，不把只有占位符的文件当成已完成全文更新。

#### 缺失材料与待人工确认（2026-09-25用户确认）

UPD-GAP-01：全文更新过程中，依据用户已提供的材料处理全部章节；缺少当期附注、审计意见、发行条款依据，或局部内容存在歧义时，标记具体缺失和待人工确认事项并继续处理其他内容。多轮对话可以追问、接收补料，但不要求用户回答完所有局部问题才生成工作稿。

- 每个待确认项记录具体缺失/冲突、材料及原文位置、受影响章节/字段、需要用户补充的信息；应用内摘要和编制说明汇总，Word对应位置保留可见的“【待人工确认：具体事项】”等标记。修订版和清洁版均保留未解决标记，接受修订不代表事实已确认。
- 原稿信息如仍有历史依据可保留其原时点及原值；缺少当前证据时明确标记，不能默认为发行规模、期限、资金用途、参与机构等已经确认沿用，也不能仅替换日期将旧事实变为新事实。
- 缺失材料只能标记未提供，不能写成不存在相关事项、无保留审计意见、条款合规或金额为零；存疑数字不得参与产生无保留的派生结论，依赖该数字的分析同步标记。
- 全文处理须覆盖全部适用章节。有依据的内容完成更新，无依据部分说明缺口；不能因缺附注就跳过整个财务或风险章节，也不能用另一发行人或旧期间的事实填补。
- 用户后续补资料或确认具体值时记录确认人、时间、原值及新值，并生成新的输入/成果版本；本轮原件、证据与已交付版本保持可追溯。
- 此规则不把不可读基线、任务执行失败、损坏Word或未实现的市场规则冒充可交付成果；M1平台承担成本、M2既有计价和失败结算规则保持不变。

### 5.8 输出、质量检查与计费

必交付：可编辑募集书工作稿 DOCX、编制说明 DOCX、应用内摘要。历史 DOCX 交付基于有效原文的真实修订版和清洁版；历史 PDF/扫描件另交付重建基线，再交付相对于该基线的修订版和清洁版，说明版式限制。无历史稿交付独立新稿，不制造对其他发行人的修订轨迹。未实现可靠的原文修订不得以无修订新稿冒充有历史稿的成功交付。

成功检查包括文件可打开、全部适用章节已处理、表格可编辑、来源可回查、已确定的核心数值和条款一致、未泄露参考企业事实、目录交叉引用有效。按 UPD-GAP-01 已明确标记的缺失或待确认内容允许随工作稿交付，摘要同时显示“工作稿已生成，含待人工确认事项”；生成完成不表示业务事实已全部确认或达到正式申报条件。静默漏章、无标记缺失、无依据确定性结论或只有占位符的文档不能通过交付检查。

按第 14 章更新模型计量，N 为实际新纳入/替换/实质重述的期间，不是全文出现的年份。用户选择“没有”不需要确认后台历史可用性档位。内部必要自检不另收一次独立复核费；用户明确再做完整复核时才建立复核任务。

## 06 复核募集书

### 6.1 范围与输入体验

REV-01：复核一份已经写好的募集书，向用户明确展示三个范围：财务数据核对、合规与格式检查、公开信息核验。首发默认三类完整执行，不让用户填写一套新的发行方案。

必需材料：待复核募集书、相关审计报告/财务报表及附注。可选其他证据。项目名称可自动生成；发行人、市场、品种、披露截止日优先读取，只有无法可靠确定或相互矛盾时请用户校对。不强制资金用途、多品种、机构、评级等输入框；这些从募集书读取。

右侧对话收集已知差异、特别关注点和核验线索。例如“重点看新增借款是否披露完整”；用户补充不代表其他两类检查自动取消。明确要求只用本机材料时，改变任务范围并清楚说明公开核验未执行，不将结果命名为三维完整复核。

点击“开始复核”后按统一冻结流程启动。未开通必要数据源/规则包时，预检说明不能执行的能力；不得收完整复核费用后只交一段摘要。

### 6.2 财务核对

REV-FIN：以主体、期间、口径、币种、单位及版本为键，建立“募集书披露 ↔ 财务证据”映射。核对项目包括：

| 检查组 | 具体检查 | 结果依据 |
|---|---|---|
| 金额与期间 | 三表、附注、正文引用、报告期标题、上年同期 | 原材料锚点、原值、披露值、标准化差异 |
| 单位与符号 | 元/万元/亿元、外币、千分位、负数、比例 | 换算公式、源精度、符号 |
| 报表勾稽 | 合计、资产负债权益、现金流净额等 | 实际表结构及完整列示项 |
| 指标 | 资产负债率、毛利率、现金流、债务及保障指标 | 项目适用定义、输入证据、计算和舍入 |
| 变动分析 | 变动金额/幅度、百分点、比较基期、异常波动 | 复算值；变动原因需独立依据 |
| 披露口径 | 合并/母公司、重述、会计变化、审计意见 | 审计报告及附注，原文引用 |
| 多处一致 | 财务表、摘要、风险、经营、偿债相同事实 | 各处位置清单，不只改第一个命中 |

资料缺失、不确定 OCR、来源冲突分别呈现，不将数字“看起来合理”作为通过依据。会计余额时点与最新债券存续金额不同不必然是错误，先建立还本付息/新增发行/重分类等桥接。

### 6.3 合规与格式核对

REV-REG：按目标市场、品种、发行对象、申报阶段、规则生效日与过渡安排选规则包。大公募、沪深及银行间各有独立适用性矩阵。

每条规则包括 rule_id、来源原文/条款/版本、生效区间、适用条件、要求字段、检查方法、证据、例外与结论。规则未核实或未覆盖时结果为未覆盖/待人工判断，不能作为确定违反法规的结论。

检查维度：

- 文件组成、必需章节与应披露事项是否存在，披露是否充分需结合适用性与事实。
- 发行条件、资金用途、发行对象、条款、增信、投资者保护和机构职责是否自洽且符合有效要求。
- 重大风险、关联交易、诉讼处罚、重组、对外担保等有证据事项是否适当披露。
- DOCX 的字号、字体、层级、段落、表格、页码、目录和引用；用实际样式/继承链计算，不只查直接属性。
- 版式渲染、换页和复杂视觉效果若不能可靠验证，明确列人工检查；主题字体缺少实际字库时不伪造确定字号/字体结论。

字体格式有两类：有效规则明确要求，以及用户/机构模板要求。结果必须标识类别，不能把偏好字体写成监管强制要求。

#### DFI 的合规核对

发行方式可选择 DFI · 储架发行，但不增加额外必填表单。通过上传募集书、注册文件和补充说明识别是统一注册文件还是具体一期文件。核对适用注册条件、通知与有效期、覆盖工具、额度（文件有约定时）、分期发行披露、承销商团及实际机构分工。阶段不明则列待核实，不能自行认定已注册；注册阶段尚未确定的本期条款不能一律判为遗漏。

具体一期按实际工具适用规则核验，全文财务和公开信息核验范围保持不变。未取得现行协会原文或注册文件的相关结论标为未覆盖/待补，不能套交易所格式要求，也不能宣称 DFI 合规已通过。

### 6.4 公开信息核验

REV-PUB：围绕发行人及任务相关主体查四类信息：

| 方向 | 要核对的事实 | 数据路径 |
|---|---|---|
| 工商与控制关系 | 名称、统一社会信用代码、股东、实控、登记变更、存续状态 | 启信宝适配、官方登记/公告，字段按授权 |
| 债券与信用 | 存续债券、发行/兑付、债项评级、违约和重大信用事件 | Wind、企业预警通及官方债券披露 |
| 诉讼处罚与风险 | 案件、执行、处罚、失信及相关公告 | 获授权服务与官方来源交叉核对 |
| 重大事项 | 公告、资产交易、控制变动、重大经营事件 | 官方公告、专业数据、联网搜索 |

这是目标能力分工，非对三家供应商现有 API 字段的核实声明。具体产品、接口、字段授权与再展示许可须按第 15 章完成联调。

先解析主体唯一标识，不能仅凭同名命中。保存查询词/主体、渠道、查询时间、事实时点、证据 URL/允许保存的摘要、来源可靠性及授权范围。媒体传闻与公司公告分层；转载不算独立第二来源。

“未检索到”只描述本次查询结果，不等于“无诉讼/无处罚/无违约”。材料截止日至查询日的新事项要区分报告期事实和期后信息；生成日不能取代所有法定时点。

### 6.5 结果模型

每个 finding 至少包含：

| 字段 | 内容 |
|---|---|
| 位置与原文 | 募集书文件版本、章节、段落/表格锚点、原句 |
| 维度 | financial / compliance / public |
| 结论状态 | 明确错误、来源冲突、待补证、待人工判断、未覆盖 |
| 严重级别 | P1 / P2 / P3，与结论状态独立 |
| 依据 | 财务证据、计算链、有效规则、公开记录及日期 |
| 差异与影响 | 实际不一致、影响章节和判断范围 |
| 建议 | 修正值/建议措辞/需补材料；无法确定时不强填 |
| 置信与限制 | OCR 不确定、来源局限、未执行检查 |

检查执行记录另含通过、不适用；每条“不适用”须有适用性依据。P1 设计定义为影响关键财务/发行条件/重大披露的高优先级，P2 为重要一致性或充分性问题，P3 为文字格式等一般问题。严重级别不能伪装为监管定性。

去重以同一事实及错误原因聚合，多位置保留列表；不同期间或不同规则不能机械合并。输出问题总数、检查覆盖数和未覆盖数，不以“没发现问题”显示 100 分或保证合规。

### 6.6 执行覆盖与成功标准

一个外部查询失败后可以继续其他检查，以取得尽可能完整的证据；最终必须按请求范围判定能否成功：

- 核心三维流程实际完成，个别事实因公开来源没有披露而列待补证，可交付有效复核报告。
- 必要供应商整体不可用、必要规则包缺失、财务证据无法读取等导致整个关键维度未执行，不认定完整复核成功；释放冻结并保留诊断性中间结果。
- 不能因一家失败就悄悄取消该范围。备用来源覆盖等价且授权允许时可继续，报告记录实际来源。
- 用户主动选择较小范围后，是另一次明确执行的新任务；不能后台自动缩小已接受任务以收款。

专业复核有问题并不意味着任务失败。任务成功是准确完成约定检查、清楚交付问题与覆盖情况，不是得出“全部通过”。

### 6.7 交付与对话修改

必交付复核报告 DOCX，包含范围/版本/时点、摘要、问题明细、核验依据、未覆盖清单。DOCX 输入时另提供批注版募集书，批注锚定原位置并保留原正文；PDF 输入给报告和可回查页码，不假装产生原 Word 级批注。

应用内仅展示摘要、主要问题、覆盖限制和下载，不要求逐条接受/拒绝。对话可以解释某条问题或补证后重新复核受影响项；明确新执行形成新结果版本。平台引用/计算错误的修复免费，同一需求下不重复收费。

默认完整复核按 R05，不能再累加其包含的 R01–R04。用户主动要求独立第二轮/差异复核的计费按实际任务和规则区分；内部质量检查不另算一项。

### 6.8 验收

| ID | 场景 | 预期 |
|---|---|---|
| REV-A01 | 数字少一位、单位从元误写万元 | 精确定位、换算差异与来源齐全 |
| REV-A02 | 不同时间的工商/审计资本数据 | 区分字段与时点，不误报简单相等关系 |
| REV-A03 | 查询无记录 | 标注查询范围，不得写确定“无” |
| REV-A04 | 私募规则被用于大公募 | 适用性检查阻止，不能通过 |
| REV-A05 | 样式有继承字体、无法解析主题字体 | 可验证部分检查，其余明确未覆盖 |
| REV-A06 | 商业数据渠道超时，关键公开维度未完成 | 不能标完整成功收费；保留已完成证据 |
| REV-A07 | 报告发现重大问题 | 正确完成核验仍为成功交付，不因负面结论退款 |
| REV-A08 | 补充新审计版本后复核 | 来源与报告生成新版本，不覆盖原结果 |
| REV-A09 | DFI 注册文件与单期发行文件 | 按阶段检查注册及发行要求，未定本期条款不一律误报 |
| REV-A10 | DFI 缺有效正式规则或注册依据 | 对应事项待核实/未覆盖，不显示合规已通过 |

## 07 材料生成通用流程

### 7.1 页面结构

GEN-01：左侧展示文种、募集书来源、模板和补充资料；右侧为“补充说明与写作要求”。对话窗口与更新募集书一致，支持多轮解释、追问及改稿；不把聊天输入变成另一套隐藏的必填表单。

首发五类文种：立项报告、主承销商核查意见、法律意见书、推荐函、募集说明书摘要。摘要含私募、公募变体，公募根据小公募/大公募路由。财务分析专题、行业研究、尽调专题、问询回复暂不作为独立模板上架；QA 的轻量分析仍可用。

默认选中“上传最新版募集书”，第二项为“关联募集书项目”。有明确选择的未完成草稿保留其来源；不能每次进入强改为系统推荐项目。

### 7.2 字段与来源

| 字段/区域 | 规则 |
|---|---|
| 材料类型 | 必选；设计默认一次一种，可由明确多文书请求进入组合任务 |
| 募集书来源 | 上传 DOCX/PDF 或选本账号项目的具体文件版本 |
| 关联项目列表 | 显示发行人、品种、版本、更新时间、是否为完成更新稿 |
| 立项券商 | 立项报告必填全称，其他文种按对应机构角色补充 |
| 摘要类型 | 私募/公募，优先按原稿建议；与原稿不符需说明 |
| 模板 | 展示系统适用模板或本人券商模板版本；允许上传更新 |
| 补充材料 | 固定分区；按文种提供建议，不使用材料类型下拉 |
| 对话 | 写作重点、读者、语气、篇幅、事实补充、核查线索 |

优先引用所关联项目的已完成更新稿，采用接受修订后的有效正文。若选择未完成项目或原始稿，明确显示实际来源，不能暗示已通过更新或复核。关联动作生成快照，后续原项目变化不自动污染正在生成的材料。

用户只提供“请按上一份写”但尚未选择来源时，应追问来源文件；不能从其他项目随意取事实。

#### DFI 来源上下文

关联 DFI 项目时保留 scope=nafmii-dfi 及注册安排；上传最新版募集书时识别文书标题和注册背景。注册阶段、覆盖工具与本期实际发行条款须分开传入模板，缺少阶段依据时列待确认。立项报告、核查意见、法律意见及推荐函按用途选适用模板；不能将交易所公募摘要直接作为 DFI 的注册必备文件。DFI 背景只决定处理要求，不证明企业具备注册资格或已完成签署。

### 7.3 模板对象与私有模板复用

每个模板包含 template_id、version、owner_scope、document_type、market/offering、broker_id、适用日期、章节树、占位字段、表格列、样式、校验规则、示例文本隔离标记及来源授权。

owner_scope 为 platform 或 user；user 必须绑定 user_id。用户上传的券商模板默认仅本人复用，同券商其他用户不可查询它的名称、内容或匹配结果。

立项报告首次使用某券商时必须提供模板或已写好的参考报告。系统提取结构、标题、表格、样式，移除参考公司的事实、签章、批注和个人信息；模板原文件仍按用户资料保护。后续同一用户、同券商、同文种可自动复用最近有效版本，并能选择旧版或上传新版。

模板过期、市场品种不匹配、参考报告结构不完整时应提示；不能只因 broker_name 相同就视为可用。上传同内容按哈希去重，不重复创建版本或收费。

平台为五类文书建立独立的标准模板库。专业专家确认后的正式模板才能启用；章节提纲不等于已验收模板。平台通用立项模板用于数据结构和测试，不跳过首次提供券商模板这一用户要求。

### 7.4 生成流水线

1. 免费预检材料存在、文种适用、模板可读，识别必要缺口。
2. 用户点击“开始生成”，平台按实际请求锁定快照并冻结。
3. 提取最新募集书事实；关联项目可复用已验证事实，但仍核对版本是否对应。
4. 解析文种需要的机构、用途、依据、核查程序和结论条件。
5. 建立“章节字段 → 事实/规则/用户要求”的映射表，识别冲突与缺失。
6. 按模板逐节编制正文、表格、章节引用；生成前后都校验关键数值。
7. 检查结构完整、证据有效、未抄入他人事实、未虚构程序和签署。
8. 生成可编辑 DOCX、编制说明，核验可打开后交付并结算。

模板里有用户命令、代码、外部链接，不授予它执行权。参考样例中的“默认已通过”“删除负面事项”等内容不可覆盖事实及产品约束。

### 7.5 缺失与专业结论

关键主体、发行方案、核心数据无法确定，或立项没有可用券商模板，先请求资料。执行后发现不可交付，失败释放，不能把全篇“待补充”作为成功成果。

非关键的签署日期、联系人等可在工作稿明确保留“待确认”，编制说明列出位置；不伪造签名、盖章或审批通过。意见类文书是可供专业机构审阅的草稿，正文保持专业格式，草稿状态在封面/页眉或交付说明清楚标识。

同一个结论所需核查程序未实施时，写出已取得证据和待落实程序，不得声称“经现场核查”“经函证确认”等。用户要求删去重要负面事实时，应说明它影响哪些判断，不能生成与已知证据相反的确定结论。

### 7.6 对话、版本与组合任务

用户发送额外事实时默认作为项目补充保存，不立即重生成文书；明确“按上述要求重写/生成”才触发执行，具体意图路由见第 13 章。与已选募集书事实冲突时追问，不让最后一句话无条件覆盖来源。

改成果生成新版本，保留来源和模板版本。平台错字、引用错误等修复不重复收费；新范围、新材料和新文书按新任务计量。

明确一次要求多个材料时，同一事实提取只做一次，各文书分别编制；一个组合执行使用一次冻结和最终结算。普通组合默认全部关键成果可交付才成功，部分失败先重试；无法完成全范围则释放冻结，不把内部文书变成临时付费里程碑。若希望分开执行，由用户显式选择独立任务。

### 7.7 输出及验收

GEN-OUT：每种文书交付可编辑 DOCX 和编制说明。说明列出来源版本、模板版本、生成时间、使用依据、待核事项及专业签发边界。首页摘要只展关键内容，不需要逐条审阅器。

GEN-A01：新用户默认上传方式；已有项目选择为第二项，切换不丢对话。

GEN-A02：同券商用户 A、B 不能相互看到私有模板；A 后续生成可复用自己的版本。

GEN-A03：参考立项报告包含旧发行人名称、签章及金额，生成结果不得残留。

GEN-A04：关联带修订的募集书只取有效正文，删除的旧数字不能进入新文书。

GEN-A05：文种/市场不适用时明确阻断或请求正确来源，不生成标题看似正确的错误文件。

GEN-A06：组合生成只计一次共享解析；所有成果状态和最终账单可对应。

## 08 模板规格：立项报告

标识：TPL-INIT｜计价 G01｜首发必需｜适用：券商内部立项工作稿

### 8.1 使用目标及输入

将最新募集书、发行安排及已完成尽调信息，组织成指定券商的立项报告，供项目组内部审核。系统不能替券商决定是否立项或虚构已通过内核/立项会议。

必需：最新版募集书或关联项目、立项券商全称、本人可用的该券商模板/参考报告。建议：该券商立项规则、尽调清单、业务部门要求、项目方案和新增风险资料。

可在右侧补充项目团队、拟申报节奏、重点风险、内部称谓、篇幅要求。项目人员名单、推荐立项意见及业务安排来自用户或正式文件；模型不能自行补出人名和审批日期。

### 8.2 章节与字段映射

券商模板决定实际顺序；以下语义模块必须映射到模板。确实不适用的项记录理由，不能强行新增与券商模板冲突的正文。

| 章节族 | 必须处理的事实/分析 | 输出形态与依据 |
|---|---|---|
| 封面与项目摘要 | 券商、发行人、项目名称、市场/品种、规模/期限、报告版本 | 封面及摘要表，拟定安排保留“拟/不超过” |
| 项目背景与承揽 | 项目目的、客户关系和推进节点 | 用户提供事实；未提供不写成长期合作 |
| 发行人基本情况 | 存续、股权控制、治理、资质、主要子公司 | 募集书与有效工商/公告对应时点 |
| 业务与行业 | 前三大业务、经营模式、区域/客户集中、变化 | 收入成本分板块表，行业判断附来源及日期 |
| 财务与偿债 | 三表摘要、债务、现金流、审计意见、授信及指标 | 各期同口径对照；计算列附公式及来源 |
| 发行方案与用途 | 申报/本期规模、各品种、增信、用途、偿债安排 | 条款及用途表，分清已确定和拟定 |
| 尽调情况 | 已收集材料、执行程序、发现和资料缺口 | 程序—证据—发现矩阵，不虚构访谈或实地核查 |
| 立项条件核对 | 券商内部准入条件、负面事项和例外 | 逐条规则、适用性、证据、结果和处理人 |
| 风险与措施 | 发行人、财务、结构、用途、信用及执行风险 | 风险描述、证据、拟措施、待落实事项 |
| 立项申请 | 建议方案、附带条件、未决事项 | 供项目组确认的申请措辞，不写成审批决定 |
| 附件及签署 | 材料清单、数据来源、必要内部表单 | 签署角色按模板保留，不填假签章 |

### 8.3 专用表格

项目基本情况表：发行人、统一社会信用代码（有来源时）、券商、市场、发行方式、规模、期限、评级对象、增信、用途、拟时间安排。

主要财务表：年度/中期、合并范围、资产/负债/权益、营业收入、利润、经营现金流、项目定义的债务和偿债指标。不能把中期直接当全年，年化需显式公式和说明。

立项条件核查表：

| 字段 | 要求 |
|---|---|
| rule_ref | 券商规则名称、版本、原条款 |
| applicability | 适用/不适用及理由 |
| evidence | 对应项目资料与定位 |
| assessment | 满足、存在差异、待补证、待人工判断 |
| action | 要补充的资料/拟采取的措施/负责人（仅用户提供） |

风险表应体现风险为何与该项目相关，不只复用通用套话。缓释措施未落实时用“拟”，不能写已完成。

### 8.4 规则缺失与模板差异

未上传券商立项规则时可以根据已取得模板和项目证据生成报告，但必须明确“未取得完整内部准入规则，内部条件核对待项目组确认”。不得用其他券商准入门槛代替。

如果模板本身含明确内部阈值，保存其版本与来源，标记为机构要求；不能升级为市场监管规定。模板中的历史案例是示例，不是本次项目事实。

财务、负面事项或必要发行方案缺失到无法形成有效报告时阻断；联系人/拟提交日期等可在编制说明列待确认。模板结构无法解析时要求可读副本，不自动换平台通用模板交付。

### 8.5 质量与验收

TPL-INIT-A01：同一发行人使用两家券商模板，结构和内部核查表正确变化，事实不变化。

TPL-INIT-A02：规则中明确门槛不满足，报告列差异及待落实事项，不输出“全部满足”。

TPL-INIT-A03：只有模板没有内部规则，仍能形成有用工作稿，明确规则核对限制。

TPL-INIT-A04：未提供现场尽调记录，不出现已访谈/已现场核查的陈述。

TPL-INIT-A05：首次上传自动保存本人模板；再次生成可选择原版或新版，不影响旧成果。

输出为“发行人_立项报告_券商_版本.docx”及编制说明；文件名应做安全字符处理。使用同券商有效模板对应 T=1，不因重复上传新文件名增加模板难度。

## 09 模板规格：主承销商核查意见

标识：TPL-UW｜计价 G02｜首发必需｜交付性质：供主承销机构审阅的核查意见草稿

### 9.1 输入与事实边界

必需：最新版募集书或关联项目、适用市场/品种、出具意见的主承销机构。机构可从材料提取，冲突时确认。

建议：尽职调查报告或程序记录、财务证据、公司决议、募集资金用途证明、信用与重大事项资料、机构模板、相关监管问询及回复。仅募集书不能证明承销商已履行外部核查程序。

多家主承销商需按实际职责确认共同出具还是分别出具，不能自动把所有参与机构列为同一意见的出具方。单一承销商无需补联席名单。

### 9.2 结构与证据

| 章节 | 内容与判断 | 证据/输出 |
|---|---|---|
| 文件身份、目的与范围 | 对哪一发行人、哪一期/哪次申报、何种产品出具 | 封面、定义、核查范围及材料截止时点 |
| 核查依据与方法 | 法规/自律规则、机构要求、已实施程序 | 规则列表与程序证据，未实施程序单列 |
| 主体资格与治理 | 设立存续、股权、治理、必要资格与授权 | 工商/章程/决议/募集书的时点一致性 |
| 发行条件与条款 | 适用条件逐条核验、募集书与方案一致性 | 条件核查矩阵，含例外及待判断事项 |
| 财务与偿债 | 关键财务、审计意见、债务、现金流与偿债来源 | 已有财务证据和计算，不代替会计师鉴证 |
| 用途与项目 | 债务偿还清单/项目手续/股权或基金投资 | 用途核查表及必要许可、程序状态 |
| 信息披露与重大事项 | 业务、关联交易、担保、诉讼、处罚、重组、风险 | 与公开数据/支持资料交叉核对 |
| 增信及投资者保护 | 合同条款、保护机制、受托/持有人安排 | 相关文件及目标规则，不能缺依据添加承诺 |
| 发现、整改与意见 | 主要发现、整改证据、未完成事项及意见 | 有条件/待核的结论由真实证据决定 |
| 签署与附件 | 出具机构、人员角色、日期、材料索引 | 不生成虚假执业签名、印章和生效日期 |

### 9.3 核查矩阵契约

每一项必须能回答：“检查了什么、基于哪条要求、用了什么证据、做了什么程序、发现什么、还有什么未完成。”

字段：item_id、rule_id、requirement、applicability、procedure_required、procedure_performed、procedure_evidence、factual_evidence、finding、pending_action、draft_conclusion。

procedure_performed 只从用户提供的真实程序记录获取。模型阅读材料可记录为“材料核对”，不能变成“主承销商已现场走访”。

存在待补证时，结论不能写“经全面核查不存在任何重大问题”。可以形成其余有依据的意见草稿并清楚列明限制；如果关键发行条件无法判断，不能交付整体肯定结论。

### 9.4 市场与文种适配

沪深私募、小公募、大公募和银行间分别匹配核查要求；大公募新增发行对象/条件分支必须来自已核实规则。不得仅从现有小公募模板复制段落。

文件名称、收件/报送对象、申报环节、机构职责以实际适用模板为准。银行间项目不能保留交易所挂牌的固定措辞。法规引用的日期和效力需与任务快照对应。

DFI 项目区分统一注册核查与本期发行核查，按证据记录承销商团、成员及实际牵头/联席分工，核对注册文件、覆盖工具和本期安排的一致性。不得根据填写了某机构名称就宣称它已完成尽调；注册阶段与本期执行程序的缺口分别列示。

### 9.5 缺失处理及验收

TPL-UW-A01：无现场尽调证据，只生成资料核对描述和待实施程序。

TPL-UW-A02：核查矩阵每项结论可回查来源，缺规则不能写符合该条规则。

TPL-UW-A03：主体评级与债项评级不同，准确引用对应对象。

TPL-UW-A04：两家承销机构但只有一家程序记录，不能自动代另一家作程序声明。

TPL-UW-A05：用途文件与募集书用途冲突，意见列冲突并请求确认，不一边保留冲突一边下全部符合结论。

输出 DOCX + 编制说明；其中专业草稿状态明确，核心数值/机构/品种与源募集书一致。不得把软件内部复核报告直接改标题作为主承销商核查意见。

## 10 模板规格：法律意见书

标识：TPL-LEGAL｜计价 G03｜首发必需｜交付性质：供律师审阅的法律意见书草稿

### 10.1 目标与必要输入

基于项目事实和有效法律依据形成可编辑的法律文书工作稿。软件不能签发法律意见、冒用律师或律所名义，不能把来自募集书的自述自动称为已独立核查。

必需：最新募集书或项目、发行人、目标市场和品种、对应适用模板。出具律所、承办律师、法律意见用途可由资料提取或在对话补充；未确定的签署信息明确待确认。

建议支持材料：主体登记/章程、股权控制资料、内部决议及授权、外部批准/注册文件、重大合同、担保与资产权属、项目许可、诉讼处罚、律师已完成程序记录。模板应告诉用户哪些事项尚缺资料，不要求一开始填写所有法律事项问卷。

### 10.2 章节映射

| 章节族 | 应处理的法律事项 | 来源及结论要求 |
|---|---|---|
| 标题、致送与释义 | 项目身份、用途、发行人、机构和关键定义 | 避免复制旧发行人/旧律师事务所 |
| 出具依据与声明 | 委托关系、审查范围、所获材料、法律依据 | 不虚构委托和独立核验；已有原文声明需与事实相符 |
| 主体资格及存续 | 设立、登记、存续、组织形式、资格 | 有效主体资料，名称变更与日期可追溯 |
| 股权与治理 | 股东控制、章程、治理机构及人员 | 登记/决议/章程相互核对，不仅靠财务附注推法律结论 |
| 批准与授权 | 内部决议、授权额度、有效期和外部程序 | 拟申请、受理、注册完成等阶段不能混用 |
| 发行条件及条款 | 按市场品种的适用条件、条款合法性 | 逐项规则和事实映射，缺证据保留判断 |
| 用途与相关项目 | 偿债、补流、建设、股权/基金用途法律事项 | 相应许可、合同、批准和用途限制 |
| 主要资产及债务 | 权属、担保、受限、重大合同及或有责任 | 区分资产账面值和法律权属证明 |
| 关联、重组及重大事项 | 关联关系、交易、重组、诉讼、仲裁、处罚 | 审计线索结合交易及官方/授权记录 |
| 信息披露核对 | 募集书涉及法律事项的陈述是否一致 | 明确核查范围，不对未核验全文作无条件保证 |
| 结论与条件 | 支持的意见、限制、待落实条件 | 不生成无事实基础的绝对肯定意见 |
| 签署与附件 | 日期、律师、机构、核查材料/法规清单 | 真实签署由机构完成，软件不填假章 |

### 10.3 法律判断数据模型

每项判断包括 issue、fact_evidence、legal_basis、applicability、procedure_evidence、analysis、conclusion、limitations。事实与法律依据分别引用；同一结论必须有可解释的推理连接，不能只列一个法规名称。

法条引用须核对名称、条号、原文、效力日期和适用范围。不得编造现行法、引用未生效草案作为生效规则，或把专家经验当强制法条。

同一法律事件要区分历史发生、持续影响、已解决和未知状态。例如诉讼撤诉、执行终结和债务清偿是不同事实，不能自动互相替代。

### 10.4 缺证与生成边界

无公司决议证据时不得写“已取得合法有效内部授权”；无权属证书时不得由资产负债表推断权属无瑕疵；未发现公开诉讼不能写“发行人不存在任何诉讼”。

专业草稿可包含清楚标注的待核事项，但主体/发行方案等核心事实缺失或关键篇幅仅有占位符时，不满足收费交付。必要时先追问材料而不是连续输出模板空壳。

用户要求“使用某律所的行文习惯”可以改变风格；用户未提供真实程序及签署授权，不能借该要求生成已签发状态。

DFI 项目须区分注册申报意见与具体一期发行意见的用途，分别核对注册适用条件、授权及决议、覆盖工具、有效期间和本期条款。尚未取得注册通知的不得写成已经注册；各阶段程序是否完成以文件证据判断，不能因 DFI 名称生成确定的合法合规结论。

### 10.5 验收

TPL-LEGAL-A01：审批文件只有受理通知，生成文本仍为受理阶段，不写注册已完成。

TPL-LEGAL-A02：审计报告有资产但无权证，不生成“合法拥有全部资产且无争议”的结论。

TPL-LEGAL-A03：规则版本已被替代，适用性检查触发重新核验，不静默沿用。

TPL-LEGAL-A04：公开查询无结果，正文保留检索范围与待补证，不绝对化不存在。

TPL-LEGAL-A05：法条名称/条号/引文不匹配，来源检查阻止该结论交付。

交付 Word 草稿与编制说明，说明集中列未取得的法律资料、尚未实施程序及需要律师确认的判断。

## 11 模板规格：推荐函

标识：TPL-REC｜计价 G04｜首发必需

### 11.1 目标与输入

依据最新募集书和有证据的核查情况，形成向适用受理主体提交的推荐函草稿。它是围绕发行条件与机构推荐意见的简洁文书，不能变成营销宣传或保证发行成功的承诺。

必需：最新募集书/项目、推荐机构、目标市场与发行方式、推荐事项。收件方、申请环节、推荐机构角色可读取材料；无法确认时在对话追问。建议：机构模板、已完成核查意见、尽调记录、相关批准文件及待落实事项。

机构是主承销商不自动代表它有权在任意市场使用同一推荐函；文件适用性需规则/模板确认。

### 11.2 章节与具体内容

| 章节 | 写作要求 | 校验 |
|---|---|---|
| 标题与收件方 | 使用适用模板名称、发行人/项目和收件主体 | 不残留旧交易所或错误申报环节 |
| 推荐事项 | 本机构身份、拟推荐的发行事项及依据 | 只引用真实委托及职责，不虚构任命 |
| 发行人与发行概况 | 业务、规模、品种、期限、用途、主要保护措施 | 与源募集书和多品种安排逐项相符 |
| 推荐依据 | 适用条件、财务偿债、授权、披露和核查概况 | 有证据的摘要，不新造财务指标 |
| 主要风险及落实条件 | 对推荐判断重要的未决事项与措施 | 不能为了精简删掉重大负面事实 |
| 推荐意见 | 依现有证据提出供机构审核的意见及必要条件 | 未满足条件不写无条件“完全符合” |
| 附件与签署 | 按模板需要列文件、机构、日期及签署角色 | 不伪造签章；日期与其他文件一致 |

篇幅默认按模板，可在对话要求简洁或扩展依据；减少篇幅不能删掉改变结论性质的限定语。

### 11.3 条件与例外

模板中固定的“已履行全部尽职调查”等语句必须与实际证据核对；没有程序记录时改为准确描述并列需机构确认的内容。模型不能把生成推荐函本身视为已经履行推荐审查职责。

跨市场转换重新确定收件方、用语及事项范围；不得直接替换地名。私募、小公募、大公募不同发行对象和申请事项依实际规则写入。

推荐依据缺失至无法提出有效意见时先索取材料；签署日期等非关键空缺可在草稿标注待确认。专业人员需要最终签发不等于所有输出都失败，需根据工作稿的实际完整性判断。

DFI 项目按统一注册或具体一期的实际用途选择协会适用推荐文本，名称、申报对象、推荐范围、承销商团及签署主体须与项目文件一致。注册安排不是已完成发行事实；阶段不明时先标明待确认，不套用交易所上市推荐函。

### 11.4 验收

TPL-REC-A01：沪转深，收件方、申请事项、规则依据均适配，无旧市场残留。

TPL-REC-A02：多品种不同期限，推荐函不将两档合为同一期限。

TPL-REC-A03：有重大未决风险，简短版本仍保留必要条件。

TPL-REC-A04：仅募集书无尽调记录，不宣称已履行全部核查程序。

TPL-REC-A05：缺出具机构/推荐事项时追问，不自动选择软件平台为推荐人。

输出推荐函 DOCX 和简短编制说明，沿用 GEN 通用的版本、来源与结算规则。

## 12 模板规格：募集说明书摘要

标识：TPL-SUM｜私募 G05 / 公募 G06｜首发必需

### 12.1 产品定义与适用性

从一份明确版本的最新版募集书提取核心内容，生成忠实、可编辑的摘要。摘要不引入原稿没有的新发行承诺、财务事实或绝对性结论，也不能通过删减隐藏重大风险。

首发支持交易所私募与公募摘要模板，公募按面向专业投资者/面向普通投资者分支。是否为特定申报环节必备文件、对外发布形式及篇幅要求由适用规则确认；不宣称每一种私募债都存在同一法定摘要要求。

用户选择摘要类型与原稿发行方式不符时，先确认是不是选错来源或拟转换发行方式。摘要功能只摘要，不能暗中完成整份募集书的品种转换；明确要求转换需按更新任务处理。

### 12.2 章节与字段

| 章节 | 必含语义 | 一致性检查 |
|---|---|---|
| 重要提示及文件关系 | 摘要与全文的关系、所用版本、重要事项 | 不用“已获批准”替代尚未完成程序 |
| 主要风险 | 对投资判断重要的信用、经营、财务、条款及重大事项 | 从全文对应段提取，保留限定和风险强度 |
| 本次发行概况 | 名称、规模、品种、期限、利率方式、发行对象、含权、还本付息 | 保留拟定/上限、分品种差异 |
| 发行人概况 | 主体、控制关系、治理与主营业务 | 主体一致，名称变更不混用 |
| 财务及偿债 | 有关期间核心数据、指标、审计意见、债务与偿债安排 | 列头、合并范围、单位、公式及审计状态一致 |
| 资金用途 | 用途、金额、项目/债务对象与重要安排 | 用途合计与条款一致 |
| 增信及保护 | 增信、受托/持有人机制、关键约定与信息披露 | 不能摘要成比全文更强的保证 |
| 发行机构与备查 | 机构及实际角色、备查资料和查阅方式 | 不编造机构联系人、地址或未提供网址 |

摘要章节树及必要要素由已验证模板控制，不机械按原稿每章等长压缩。

### 12.3 私募与公募分支

| 变体 | 专门处理 |
|---|---|
| 私募 | 保留发行对象、非公开安排、转让/投资者资格等适用限制；不写面向不特定公众宣传措辞 |
| 小公募 | 保留面向专业投资者的条件及适用公开披露信息；不改成普通投资者可参与 |
| 大公募 | 独立确认面向普通投资者相关要求、重要提示、风险与发行条件披露；不能沿用小公募投资者限定 |

投资者范围的精确措辞以源募集书和有效规则为准，产品的简写标签不能直接作为法律文件正文。

### 12.4 摘要生成约束

每条核心数字/条款和重大风险建立源段落或表格锚点。正文可以改写，但数值、日期、主体、否定词、上限和条件不能改变。源稿已有明显内部冲突时先提示；不默默替它选择一个数，更不能把“尚待核实”压缩为确定事实。

审计意见类型必须完整保留，不将带保留意见或强调事项的描述缩成“审计报告已出具”。审计对象、担保人和评级对象不可因压缩而混淆。

源稿缺少关键风险或核心发行条款时，不能以生成摘要的名义补造事实。可告知需先更新/补齐源稿。用户要求极短摘要导致无法保留必要内容时，说明必要长度和保留项，提出简版说明与完整摘要的区别。

### 12.5 验收

TPL-SUM-A01：包含“不超过”、回售权和不同期限，摘要完整保留其条件。

TPL-SUM-A02：同一源稿选择公募但原稿为私募，先处理类型冲突。

TPL-SUM-A03：要求把篇幅减半，仍保留重要负面事项、审计意见和发行对象限制。

TPL-SUM-A04：摘要每项核心数据可定位至所选源稿版本，不从其他版本混入。

TPL-SUM-A05：大公募分支有独立专业验收样例，不以小公募测试通过代替。

交付摘要 DOCX + 编制说明。内部质量检查含逐项源稿一致性校验，不能额外收费为一遍完整专业复核。

## 13 QA 问答与项目对话

交付阶段：M1 必须实现更新项目内的真实多轮补充、追问与继续修改；M3 扩展复核对话；M4 上线独立 QA 和材料生成对话。积分结算自 M2 启用，共享上下文隔离与工具安全要求从 M1 执行。

### 13.1 两个入口、同一任务能力

CHAT-01：独立 QA 适合债券专业问题、材料解读、财务分析、公开查询和轻量起草；项目右侧对话服务当前项目的补充信息、解释、追问与改稿。两者复用身份、事实、证据、工具和积分服务，但各有明确上下文范围。

QA 首页展示输入框、附件、可选关联项目、最近会话和少量真实示例。Web 不默认读取全部云项目，M5 不默认读取全部本机文件；仅用户选择的附件与项目进入可用上下文。项目对话顶部显示当前项目、所用材料/成果版本和正在执行的任务。

用户不需要编写专业提示词。可直接说“授信总额 50 亿元，已用 20 亿元，截至 6 月末”或“把偿债分析写得更简洁”。系统追问年份、币种等必要信息，不把字段缺失隐藏起来。

### 13.2 支持范围

| 意图 | 能力与交付 |
|---|---|
| 专业知识问答 | 概念、发行规则、会计/财务解释；区分一般解释与适用法规结论 |
| 项目材料解读 | 定位原文、解释指标、列资料缺口，附文件与位置 |
| 财务分析 | 明确期间口径后计算，返回公式、输入来源、结果及限制 |
| 公开查询 | 按已授权供应商/官方信息查询，列主体、日期、来源与覆盖 |
| 轻量起草 | 段落、说明、短函、措辞调整，保持事实依据 |
| 文书执行 | 明确要求全文更新/复核/生成某文书时路由到对应执行任务 |
| 产品帮助 | 余额、状态、导航、规则说明，免费 |

首发不扩展为通用电脑自动化、Excel/PPT 全功能代理、自动发邮件或投资交易。超出任务范围给出准确能力说明，不以泛化“深度思考中”占用收费任务。

### 13.3 发送、保存和执行的语义

CHAT-02：对话中的“发送”是用户请求执行本轮意图，不是单纯按字数计费。系统分类成本由平台承担，收费依据是实际任务。

| 用户消息 | 行为 | 计费 |
|---|---|---|
| “补充：公司授信总额为……” | 保存为用户提供的事实，追问必要时点/单位，显示已记录 | 保存及纯澄清免费 |
| “请解释为什么这一项有差异” | 基于证据进行专业回答 | QA 对应档位；平台自身错误修正免费 |
| “把这些信息用于下一版” | 更新下一版需求，尚未要求生成时说明已保存 | 不因编辑资料直接收费 |
| “按这些信息重新生成报告” | 明确执行新文书版本，后台冻结后启动 | 对应文书任务；不再弹报价确认 |
| “怎么更新募集书” | 回答方法 | 普通 QA，不启动全文更新 |
| “请把这个项目全文更新到 2026 年 6 月” | 校验项目及材料，路由 update | 按更新任务，不伪装成廉价短问答 |
| “继续” | 结合当前明确待继续事项；有歧义则澄清 | 不自动启动未知范围 |

右侧区可有“保存补充”和主任务按钮；用户明确发送执行请求时不强迫再点第二个价格确认。响应中展示已创建的任务卡及状态，避免用户不知已开始执行。

开始任务前的必要追问、无结果检索、纯拒答、客服问题不扣任务积分。问答有效答复中合理的不确定性与纯拒答不同：有证据的分析即使结论为“不能确定”，仍可能是完成了用户的分析请求。

### 13.4 上下文与冲突管理

消息对象保留 role、content、attachments、project_id、artifact_version、intent、fact_refs、created_at 和修订关系。编辑/删除先前说明只改变后续上下文，不改写已运行任务快照或账单。

新事实与结构化表单冲突时：

1. 先区分新安排与旧事实、不同期间与不同主体。
2. 如用户明确改变目标安排，更新下一版草稿并记录差异。
3. 如是对审计/公开事实的争议，保留两方证据，追问有效文件或口径。
4. 未核实用户补充以“用户提供”入库，不自动标为已验证。

会话摘要用于减少重复上下文，同时保留原消息、决策和来源引用。不能为了节省上下文丢弃尚未解决的冲突，或把“拟”总结为“已经”。

### 13.5 执行中追问与新增材料

同一输入范围内的术语澄清可作为附加 clarification 事件继续原 run，冻结不变，并保存用户答复；不能重写原输入哈希。

用户上传新材料、变更报告期、改变目标品种或要求另一套成果时，创建新输入版本，需要用户明确再次执行。当前任务若因原资料缺失无法交付，应结束为缺材料失败并释放；已经完成的可靠解析可复用。界面可提示“资料已补齐，点击继续生成”，该点击建立新任务，不倒收失败成本。

纯系统暂停/断线恢复沿用同一任务和冻结。不要把运行恢复与用户更改范围都称为“重试”，接口必须区分。

### 13.6 回答和工具输出

专业回答优先给结论或无法判断的原因，再给简要依据。财务答案列数值、单位、期间、口径、计算和出处；规则答案列适用市场、版本、生效日期、条款与链接；查询答案列数据截至日及实际查询时间。

引用要能够定位，不以模型生成的 URL 或虚假页码冒充来源。官方原文、供应商返回、上传文件、用户补充、模型推断使用不同来源类型。模型的推断不可展示为数据库原始结论。

工具调用通过允许清单，界面只显示“读取材料/核对数据/查询公开信息”等业务进度，不展示隐藏推理、内部系统提示或供应商密钥。流式输出中断不标记成功，避免收费后只留下半段文本。

QA 会话可以导出文本；明确请求生成正式 Word 文书时遵循对应文种规范。已有回答另存/下载免费。

本轮按实际意图独立分类 Q00–Q07，不能继承上一轮最高系数。对话关联大公募项目不代表“下载在哪里”也应加大公募系数；特殊因素仅作用于实际相关工作。

## 14 积分充值与结算

交付阶段：本章在 M2 上线，首先接入已上线的募集书更新，随后被 M3 付费复核、M4 材料生成/QA 及 M5 Windows 共用。M1 受控试用只记平台成本，不显示虚假积分账本，也不追溯扣费。

真实调用日志及 token 采集在 M1-34 完成，先于首个用户更新任务；M2-03 只在其上增加计费归因、费率和账务关联。运营总消费保留成功、失败、重试及平台承担的真实成本；“不可向用户计费”不等于删除用量日志。prompt/job/call/usage/error 与账务的关联及去重规则见第 16.9 节。

权威业务基线：[BondBuddy 详细积分方案](references/BondBuddy详细积分方案-v1.1-来源快照.md)，proposal-2026-09-22-v1.1；[配套参数](references/积分参数-v1.1-来源快照.json)。原文及参数尚属未完成真实成本校准的方案，本文将其作为用户指定的目标要求。

### 14.1 用户体验与不变量

BILL-01：准备材料/需求 → 点击执行（QA 为发送）→ 后台检查与冻结 → 自动执行 → 成果和本次消费。没有用户报价页、复杂度确认、预算授权或执行中追加付款。

创建项目、保存补充、文件上传/导入、普通预检及历史募集书源信息识别、费用估计、已成功成果下载和相同内容重新导出均免费。源信息识别所需的受控 OCR/模型调用由平台承担并标记 billable=false；复用结果不能补收该费用。只要能力已开放、材料可执行、数据授权具备，积分准入为“可用余额 ≥ 本次内部冻结额 B”，不要求月费订阅，不按积分来源限制外部数据能力。

| 条件 | 行为 |
|---|---|
| 可用 = B 或可用 > B | 原子冻结并启动 |
| 可用 < B | 不启动、不扣分，保留输入并提供充值入口 |
| 成功实际计量 A < B | 扣 A，释放 B−A |
| 成功 A ≥ B | 最多扣 B，超出由平台承担 |
| 失败或用户取消 | 全部释放冻结 |
| 系统重试/重启恢复 | 复用同一任务与冻结，不重复收费 |
| 充值到账 | 不自动启动过去失败的执行请求 |

### 14.2 计量与内部预留

设 C 为依据供应商真实 usage 与锁定单价计算的人民币模型计量成本：

~~~text
C = Σ(token分类数量 × 每百万token单价) / 1,000,000
标准token = C / 10 × 1,000,000
基础积分 = C × 100
A = ceil(Σ业务C×100×K业务
       + Σ首次解析C×100×K解析
       + Σ成功且有授权的外部服务采购成本×100×1.20)
E = 内部估计的业务积分 + 解析积分 + 外部服务积分
B = ceil(E × 内部预留系数)
P = min(A, B)
~~~

10 元/百万标准 token 是换算基准，不是 DeepSeek 的真实报价。内部预留系数初始普通 1.20、复杂 1.50，仅影响冻结，不乘进实际收费。估计缓存 5 分钟，启动时检查输入版本并重新校验余额。

计量使用定点/高精度整数，任务汇总后仅一次向上取整。缓存输入已包含于总输入时先拆分，推理 token 已包含于输出时不得再加。一个成本事件只能归属一个阶段，OCR 外购费不能又算模型解析成本。

平台冗长提示、无效检索、系统重试和错误循环浪费记录实际采购成本，但 billable=false。正常有效上下文与用户任务调用可计量。缺少可验证 usage 时进入结算对账，不能用估算直接扣分。

### 14.3 四类任务系数

#### 更新

M2-02 必须读取 M1-31 产生的 HistoricalProspectusProfile 与 UpdateDifficultyInput。以历史稿识别的原市场、原发行方式、原年度/中期报告期为 source，以用户本次项目目标为 target；原稿完整性、迁移方向、实际变更期间分别进入历史档、M、N，J 按目标结构确定。不得从文件名、上传年份或目标下拉框反推历史稿类型。

内部估算锁定源材料、识别/校正版本、目标修订和新财务材料版本。上传后的 N 为估计值，实际计价 N 以已完成的新纳入、替换或实质重述截止期核定；source/target 的差异只是难度因素，最终 A 仍依有效真实用量计算。关键源字段待确认时先校正，不能猜定高系数收费；修改源信息、目标或材料需重算未执行估计，已执行快照保持不变。

N 是实际新纳入、替换或实质重述的不同截止期。原稿保留的年份、同一期三张表、合并/母公司和重复材料不重复计期。

CREDIT-SOURCE-A01：历史稿已有 2022–2024 年且仅新增 2025 年时，N=1；相同报告期跨市场/方式时 N=0，按有依据的实际迁移处理结构工作。CREDIT-SOURCE-A02：收费记录可以追到原稿市场/方式/期间证据及对应目标，上传后平台承担的识别成本不计入用户 A。

| 历史状态 | N=1 | N=2 | N=3 | N=4 | N>4 |
|---|---:|---:|---:|---:|---|
| 本企业完整稿 | 5 | 10 | 15 | 20 | 5N |
| 本企业不完整稿 | 8 | 13 | 19 | 25 | max(8,ceil(6.25N)) |
| 其他企业参考稿/可用内部参考 | 25 | 30 | 45 | 60 | max(25,15N) |
| 无本企业稿也无可用参考 | 35 | 40 | 55 | 70 | max(35,15N+10) |

K更新 = min(200, 历史及期间基础 × M迁移 × J目标结构 × S范围 × C特殊事项)。

N=0 的纯条款等改动基础 K=3，再按实际迁移/目标因素；无历史完整编制不能走 N=0。没有本企业历史稿 M 固定 1；内部自动找到结构参考时按 peer 档，不额外收模板获取费。

M 从版本化矩阵取得，区分方向。普通目标 J=1，大公募 J=1.15。S 的 financial=1、full_facts=1.2、restructure=1.35 互斥；产品前台默认全文更新，由后台按实际工作分解选档，不让用户选范围。跨市场正常章节映射或无历史稿不自动一律乘重构档。

特殊事项 C 上限 1.75，只作用于有证据且实际受影响的工作项；多品种、担保、重组等不能把整单全部成本无差别加成。额外主体加成也计入共同上限，不按普通子公司个数收费。

#### DFI 注册安排的计费路由

DFI 不是第十五个独立工具费率，保留原积分方案“注册安排不能作为新增发行品种重复收费”的约束。目标数据保留 arrangement=dfi 与实际覆盖/本期工具，不将法律品种偷偷改为 MTN。选择 DFI、保存注册信息和上传文件本身均免费；仍为一次点击对应一次冻结、一次结算。

当前产品增加内部路由版本 dfi-v1：注册层面的目标结构系数 J=1；源或目标为 DFI、尚未确定具体工具间迁移时 M=1，不虚构跨工具迁移系数，也不按覆盖 MTN/CP/SCP 的数量倍乘费用。历史稿状态、实际处理期间、工作范围、模型用量及外部费用沿用统一方案；复核与材料生成同样不叠加 DFI 注册附加费。分类快照保留 target/source=DFI、arrangementPricing 和 pricingBasis，便于回查。

当前代码在源/目标 scope 不同的情况下仍按既有启发式选 restructure；这不是独立 DFI 附加费，也不表示上线已完成工作项级分类。生产版本须按实际重组范围判断 S；已确认的具体工具间实质迁移，按该工具矩阵作用于对应工作项，注册标签不再收费。此段是 DFI 新需求的实现路由补充，不改写用户指定的积分方案来源快照或原有十四类参数。

CREDIT-DFI-A01：DFI 自身更新、交易所稿转 DFI、DFI 转具体工具，以及无历史稿的 DFI 编制均能生成有效计费快照；不得因原矩阵无 DFI 列报“无法识别品种”。CREDIT-DFI-A02：仅增加覆盖品种名称，不增加一份品种费；同一模型调用和同一解析事件不得重复计量。

#### 复核

R01 格式=2；R02 文内一致=4；R03 财务证据=6；R04 规则条款=6；R05 完整复核=10；R06 差异=5；R07 局部问题=3；R08 完整复核加独立第二轮=15。

#### 材料生成

G：立项 8、主承销核查 12、法律意见 15、推荐函 5、私募摘要 6、公募摘要 7。

### 14.4 钱包、批次与过期

钱包显示可用、冻结、累计消费、购入/活动积分、近 7 天到期；流水支持任务及订单链接。积分使用先未过期活动批次（最近到期优先、同日先到账），后购买 FIFO。

购入积分不设有效期，活动积分按批次到期；两者均支付已开放任务的模型、解析和外部服务费用。授权限制属于服务能力，不是要求额外“付费积分”门槛。

正常冻结期间活动积分过期，当前任务仍可完成；未用部分释放保留原到期日。平台故障导致释放时已过期的，至少补偿 7 天。用户自行取消的释放不当然延长原有效期。

到期前 7 天、1 天站内提醒，避免同批多设备重复提醒。设备时间不能改变过期或活动日界，平台统一使用北京时间。

### 14.6 退款、纠错与发票

可退人民币 = 原订单净实付 × 未使用且未冻结积分 / 该订单初始购入积分。

例：500 元购入 52,500 分，消费 10,500，剩余 42,000 可退 400 元。退款按原路、按累计金额分配到分，末笔消化舍入尾差；不得同一积分退款两遍。

申请退款先原子锁定该批可退额度为 refund_pending，防止同时执行任务又退款；渠道失败则解锁。订单部分退款、全退、支付撤销与任务退分使用不同事件。冻结额度先处理任务后再确定可退数量。

平台交付错误修复免费，必要退分回到原来源批次；原活动积分已过期且因平台问题退回的按补偿规则延长。活动积分不提现、不变现金负债。

设计默认首发提供发票申请入口和人工处理状态；自动开票、对公采购不是已确认首发核心能力。需记录抬头/税号/开票内容和实际可开金额，退款与红冲关联。正式开票主体、税率、凭证口径由运营财务上线前落实，不能用“人工处理”规避依法应提供的凭证。

库内收入画像优先读取该募集书对应最新完整年度的财务/业务分部披露；不足时由运营关联同一发行人的相应审计报告/附注。目标项目画像从用户提供的审计报告/附注提取。两个来源都须有完整合并口径主营业务收入排名依据，不能只截三行就认定是前三；营业收入、注册资本、总资产、毛利润、地域/客户分类不能替代分业务主营业务收入。母公司与合并、不同年度、不同业务分类层级不能混排，冲突进入审核。

业务名称映射到经过行业审核的同粒度分类代码；保留原始标签和映射依据。只允许有依据的同义归一，不用宽泛的“城投”“制造业”等标签代替具体三业务。候选与目标的年度可以不同，但各自必须为确定的完整年度、口径可比且来源有效，新旧程度参与排序。第三名并列、只披露两项、混合“其他”、分部重复或缺收入金额时不自动标 complete。用于本次匹配的收入占比以该主体同年度合并主营业务收入总额为分母，不能用前三项之和代替总额；原文其他分母的占比另行保留并标明。

最低索引能力为市场/发行方式/实际品种/文书阶段/可用状态过滤，以及分类版本下的三业务集合等值检索；原始收入顺位另存，不要求两个发行人三项收入排序相同。索引和来源数据库可用常规数据库实现，向量相似度仅可用于运营发现候选，不能替代完全一致的入选条件。业务代码、收入年度和分类词典升级均生成新画像/索引版本。

首次建库流程为：取得原件及来源 → 文件哈希/主体去重 → 正文解析及 OCR → 分类与全部业务收入抽取 → 人工核对证据 → 发布不可变版本 → 验证索引可查询。原文件、可读正文和元数据分别保存但以同一版本关联。允许只登记来源线索或不完整索引，但这些记录不能进入自动推荐。

建库交付包含真实首批参考稿、数据字典、导入清单、审核记录和覆盖矩阵；按首发的六类沪深公司债组合、PPN/MTN/CP/SCP 及 DFI 记录至少一个已审核可用版本，并取得可匹配业务样本验证无参考附件编制。披露不足、来源不可取得等真实空白必须显示为发布缺口，不能用演示条目或一份稿件冒充全覆盖。业务覆盖会持续扩大，不承诺首批覆盖所有企业的三业务组合。

项目上传的历史稿、相似稿、审计报告以及用户券商模板默认只在个人项目/授权范围内使用，不能自动沉淀为其他用户可用的库内容。项目匹配请求形成的业务画像也不是可分享的募集书库记录。

#### 15.2.2 项目匹配契约与新稿质量（M1-28）

输入为目标主体、年度业务画像与证据、目标市场/方式/实际品种/阶段、规则版本和可选用户参考。先核验输入完整性，随后过滤已审核、可读、未替代且使用范围有效的库版本；三业务集合必须一致。适用性不是简单加分：没有已验收目标章节映射的跨市场/方式候选应排除，不能选中后套用不相干发行规则。

#### 15.2.3 持续增量维护（M1-33）

LIB-03：配置允许使用的公开披露/授权来源适配器，并保留人工或批量运营导入通道。后两者使用同一入库、审核和发布流程。来源配置记录获取方式、使用范围、更新周期、限流、增量游标和最近成功时间；实际来源访问及更新能力需验证，不承诺未经核验的接口或自动全网覆盖。

调度流程为发现新增/变更 → 保存来源元数据及原件指纹 → 幂等入库 → 解析/分类/重算业务收入 → 审核 → 原子发布正文、画像和索引。无变化跳过，抓取/解析失败按任务记录重试，断点续跑，死信/长期未更新告警。新募集书披露新的完整年度或修正业务收入时产生新画像，不能沿用旧前三项而不复算。

文书状态区分待处理、待审核、已发布、已替代、已撤回、失败；支持元数据纠正、补正文、替代、撤回与回滚。内容哈希及来源文书版本去重，不能把同一发行人不同年份或不同工具合并成一份。审核前不能出现在推荐集合，原子发布失败保留旧可用版本；迟到旧处理任务不得覆盖新版。

被替代、撤回或使用权失效的版本退出新的匹配并使缓存失效。普通资料更新不改写已运行任务和历史成果的版本快照；若发生授权撤回等禁止继续使用的情况，后续读取重新检查，按保留政策隔离/停止，而不是以已锁定为由继续分发。回滚也需重新核验使用范围，并原子恢复文书、业务画像与检索索引的一致版本。

运营页面提供待审、失败、陈旧条目、来源状态、各市场/方式/品种/三业务组合覆盖、未命中汇总及重跑/回滚入口，记录操作者和原因。未命中统计尽量只存标准业务代码及计数，项目名称、上传审计原件和公司敏感数据不得自动暴露给库运营。告警/维护任务均在后台，不让普通用户操作建库或更新索引。

### 15.3 行业规则包

RULE-01：十个具体首发市场×品种组合，以及 DFI 储架安排，均需有效规则和样本覆盖。现有主要知识集中在交易所尤其上交所私募；大公募不能直接复用小公募包，银行间不能用八条通用方法冒充正式规则库。

每条规则应具备：

| 字段组 | 最少字段 |
|---|---|
| 身份/来源 | rule_id、版本、发布机构、文件名、官方 URL/文件哈希、条号、准确原文 |
| 效力 | 发布/生效/失效日期、过渡条款、后继版本、验证人/时间 |
| 适用性 | 市场、品种、投资者范围、申报阶段、行业、特殊事项 |
| 执行 | 必要输入、公式/判定逻辑、例外、检查器版本、证据定位 |
| 输出 | 通过/不适用/问题/待补证/待判断/未覆盖，严重级建议 |
| 验收 | 正例、反例、边界、来源冲突处理与专家确认 |

法规、自律规则、参考模板、机构内部准入、专家方法、窗口指导、示例必须标明不同效力。来源含疑问、批注、机器转录或未核实阈值时只作研究线索，不直接启用硬拦截。

规则更新流程：发现官方变更 → 获取原文及指纹 → 判断差异和过渡期 → 专家复核 → 回归样本 → 发布签名包 → 通知受影响未执行项目。历史成果保留当时依据，不能后台改掉后假装一直使用新规则。

#### DFI 适用包

DFI 随首发验收，但按“统一注册/储架安排 + 文书阶段 + 实际工具”选择规则。分别维护注册适用条件与文件、有效期及变更、覆盖工具、分期发行披露、承销商团、具体一期工具条款的来源和效力。不将统一注册一律理解为必须有固定注册额度；有无额度及其限制以适用规则和实际文件为准。

当前内部知识摘录 S019:1505 涉及统一注册与实际发行工具分离、注册阶段额度及分期确定条款；S019:1493 涉及承销商团。两者仅作为待核查线索，不替代协会现行原文；境外发行人规则不能直接推广给境内企业。正式规则、发布/生效时间、适用主体和样本均经专业确认后发布规则包。

内部参考库可保留 DFI 注册与实际工具元数据；仍需满足同一发行人审计口径下前三大业务匹配。参考稿出现多个工具不等于实际发行多个工具，也不放开未验收的复杂产品。

## 16 数据模型、接口与状态机

本章为新版本目标契约，不表示现有 /api 路由已符合。客户端与平台均需版本化接口；现有代码迁移可用适配层，不能让旧 quote/confirm 成为新流程的用户前置步骤。

### 16.1 边界与通用约定

M1–M4 浏览器通过 HTTPS 调用 /api/v1，项目、上传材料、事实、对话与成果保存在账号隔离的服务端工作区。M5 客户端 UI 通过受保护的本地 IPC/环回接口调用 /local/v1，本机处理能力使用相同业务契约。身份、钱包、用量、任务租约与供应商密钥始终由平台管理。

下表“本地”是 M5 的存储归属；在 Web 阶段对应对象统一由平台数据库/私有对象存储持久化。对象增加 storage_origin（cloud/local）和 workspace_id，M5 本地对象另有 device_id；跨端关联不能仅按 project_id 假设文件已存在。模板私人作用域无论存于云端还是本地都绑定 owner。

所有 ID 为不可推测标识，所有对象绑定 owner_user_id；每次读取/关联/导出重新校验。客户端提交的用户 ID、价格、系数、余额和 usage 不可信。路径只能用授权文件句柄/材料 ID，不能接受任意绝对路径交给模型。

时间存 UTC ISO-8601；活动日转换 Asia/Shanghai；金额人民币分，数值/成本定点十进制；空值、0、未知、不适用分开。修改使用 revision/If-Match 乐观锁，冲突返回 409 并保留用户输入。

分页使用 cursor；接口错误返回 code、message、retryable、field_errors、correlation_id。普通运行日志不带材料正文或访问令牌；用户已提交 prompt 必须保存于加密限权的 PromptSnapshot，通过引用与任务日志关联，不能用“日志无正文”省略用户要求的 prompt 记录。统一规范见 16.9。

#### 历史稿识别与难度输入契约（M1-31）

HistoricalProspectusProfile 的 source_market/source_offering 是上传历史稿的识别值，与 Project.market/offering 的本次目标含义不同。reporting_periods 至少逐项保存 start/end、年度或中期标记、报表口径和来源，latest_reporting_cutoff 从有依据的期间集合推导；签署日、发行日另存，不能替代。无法判定小/大公募、源市场或报告期时，规范值可为 null，同时保存 raw_value 与 uncertainty，不能填一个默认品种。

识别状态为 queued → analyzing → ready / needs_confirmation / failed；ready 表示源信息具备依据，不表示整份募集书或财务数据已复核。每个候选值带 evidence_refs；用户校正标 user_asserted，保留前值、理由、操作者、时间和校正版本，不伪装为模型识别或审计确认。

上传持久化事件按 owner + material_version + extractor_version 去重，替换文件后迟到的旧识别结果不得覆盖新材料。更新草稿读取所选历史稿版本的 profile；本次目标不被源值自动改写。UpdateDifficultyInput 同时绑定 profile_version、目标修订、财务材料版本和适用规则版本，任一变化使未启动估计失效。执行时锁定该输入，actual_N 和实际分类以追加工作记录给出，不改写原估算证据。

M1 识别与差异比较不需要钱包，保存平台承担成本的预检事件；M2-02 消费同一契约生成 M/J/N 与计价快照。源字段待确认不能悄悄当成完整可信定价输入；估计和实际须分字段。

#### 原文修订与内部参考库契约（M1-26/28/29/32/33）

有历史稿建立 RevisionBaseline；DocumentChange 与有效基线位置对应，导出修订版接受全部本轮变更的有效正文/表格必须与清洁版一致，拒绝全部回到基线。已有历史修订和 PDF 重建过程单独追溯。无历史稿建立 ReferenceSelection 并输出新稿，不把参考稿设为用户的修订基线。

库记录是平台后台作用域，不能套用普通个人文件下载接口。owner 授权继续适用于项目侧业务画像/用户参考稿；库内画像仅可由授权来源的建库流程产生。market/offering 沿用项目枚举，instrument/tags 分别表达实际工具/品种标签；DFI 的 arrangement 与 issuance_instrument 仍分开。业务索引键包含 taxonomy_version 与排序去重后的三个标准代码，但原始收入顺位另外保留；不到三项、并列待判、缺证据或口径不可比时不得生成 exact 键。

按第 15.2 节 LIB-01A，目标画像和候选画像均须有审核证据支持 `accounting_scope=consolidated`、`revenue_basis=main_business_revenue`。存储/契约中的其他枚举用于保留原始事实，不构成自动推荐资格；不能因为双方都标 `operating_revenue` 就认为符合业务要求。该限制在目标画像校验、候选筛选、服务端选择锁定及重放校验中保持一致，证据随不可变画像版本固定；已有画像不得直接改标签升级。具体 schema 和代码验收由 #77/#78/#33 落实，本次需求确认不代表已完成生产校验。

入库处理状态为 discovered → parsing → classifying → pending_review → published，另有 needs_evidence/failed；已发布版本可变为 superseded/withdrawn。正文或索引字段变化生成新版本，审核和发布操作带 revision 防止并发覆盖，发布时原子切换有效版本集合。只有 published 且使用范围有效、正文及三业务证据完整的条目可匹配。

任务服务内部匹配返回 status（exact/needs_evidence/needs_review/no_match/unavailable）、候选与理由、选定文书/画像/词典/索引快照。用户端只得到正常编制进度和可操作缺口，不得到后台记录、文件名、候选清单或匹配分数。内部 reference_id 不可作为普通账号读取库文件的授权凭证。

持续采集按 source_id + source_document_id + content_hash 幂等；元数据校正产生新修订。重新解析、收入年度或排名变化触发新画像和索引发布，迟到旧结果不能覆盖新版。任务锁定版本不因正常扩库而变化；读取仍需核验当前使用限制，授权撤回按政策处理。不得绕过退役状态从缓存命中旧版。

### 16.4 执行与账务状态

~~~mermaid
stateDiagram-v2
    [*] --> preparing
    preparing --> rejected: 缺材料/能力/授权或余额
    preparing --> queued: 试用授权或原子冻结成功
    queued --> running
    running --> awaiting_input: 原范围澄清
    awaiting_input --> running: 澄清答复
    running --> paused: 执行进程不可用或本机退出
    paused --> running: 对账后恢复
    running --> validating
    validating --> delivering
    delivering --> settlement_pending: 已交付但用量待对账
    delivering --> succeeded: 已交付并完成结算
    settlement_pending --> succeeded: 可验证结算或平台承担
    running --> failed
    validating --> failed
    delivering --> failed
    awaiting_input --> failed: 新材料不可缺少
    queued --> cancelled
    running --> cancelled
    awaiting_input --> cancelled
    paused --> cancelled
    failed --> [*]
    cancelled --> [*]
    rejected --> [*]
    succeeded --> [*]
~~~

图为主路径，所有未终结运行阶段均需处理取消、超时及不可恢复失败，包括 validating/delivering；实际转换表以服务端实现，不能只实现图上画出的边。Web 浏览器离线或关页不导致运行暂停；暂停指工作进程/必要服务不可用。M1 无账务冻结，成功只记录交付与平台成本；后续收费阶段才进入账务结算。

rejected 不产生有效冻结。failed/cancelled 全额释放。awaiting_input 仅在现有范围内澄清可继续原 run；新材料或范围修改生成新版本、新 execute。settlement_pending 保持成果可用，但不显示已扣分；对账超时政策见第 14 章。

账务状态独立为 reserved、settlement_pending、settled、released。成功可为零计量；失败不允许 settled。取消已经成功结算的任务返回 ALREADY_TERMINAL，后续走纠错/退分，而不是再次释放整笔。

派生项目状态使用最新运行记录，但最新成功成果永远独立保存；失败新版本不会把旧成功成果隐藏。

### 16.5 幂等、快照和租约

execution_request_id 按账号唯一，同一键同一内容返回同一 run；同一键不同 input_hash 返回 IDEMPOTENCY_CONFLICT。网络重发不能生成新 UUID；用户新的主动执行才创建新键。

输入文件列表、目标字段、需求消息版本、规则/模板/模型/费率均锁定。解析前尚不确定的历史状态或期间可以记录估计分类，用于 B；实际归类依据以同一规则版本的已完成工作记录追加，不能把保守高估当实际收费。实际扣分仍受 B 保护。

工作进程 lease_id、lease_expiry、last_event_seq 由平台控制；同一 run 不能有两个有效工作进程。恢复前核对 provider_request_id，避免把已完成但响应丢失的请求再次收费。

支付回调、用量、结算、退款、活动分别有独立幂等域。不能将“相同提示词”作为所有任务的去重依据，因为不同来源版本可能是不同任务。

LOG-01：从 M1 首个募集书更新任务对用户开放前，包含受控试用，统一日志采集、查询、告警、权限和恢复必须真实可用。日志是任务与模型调用的基础设施，不能推迟到 M2 充值收费时实现。M1-11 接入模型调用，M1-12 接入任务状态，M1-13 接入已提交对话，M1-34 统一契约、持久化、后台检索及验收；M1-30 据此控制发布。后续复核、生成、QA 和 Windows 复用同一规范。

#### 16.9.1 记录范围和关联

“全部使用日志”指已提交业务操作、执行及异常的完整链路，不是录屏、键盘监听或未提交草稿采集。注册/登录/登出、项目创建与修改、材料上传/删除/识别、prompt 提交/修订、预检、执行/取消/恢复、成果交付/下载均有事件。页面进入、按钮提交和前端异常可由客户端上报，服务端成功/失败另行记录；上传记录开始、保存/失败、取消及必要进度摘要，不逐字节写日志。

| 关联字段 | 含义及边界 |
|---|---|
| event_id / schema_version | 唯一事件与字段版本；重复投递只入一次，后续修正追加事件 |
| operation_id / request_id | 一次用户意图及各次 HTTP 请求；重复点击/网络重发关联同一幂等业务操作，不抹掉请求尝试记录 |
| trace_id / span_id / parent_span_id | 请求、队列、任务、工具、模型及导出链路贯通；跨进程显式传递，第三方响应 ID 另存 |
| actor_type / user_id / project_id | 用户/系统/运营及受信账号身份；系统任务可无 user_id，未登录请求使用匿名关联标识，不把手机号当标签 |
| conversation_id / message_id / input_revision | 对话轮次、prompt、结构化目标及不可变材料版本；同一对话可触发多个 job |
| job_id / run_id / parent_job_id | job 是逻辑工作单位，run 是执行实例；拒绝/免费预检/单轮 QA 也建立 job 记录，尚未有 run 时可空，不丢日志 |
| work_item_id / logical_call_id / call_id / attempt_no | 阶段、逻辑模型调用、每次实际发送及重试顺位；不同真实重试不是同一 call |
| occurred_at / ingested_at / seq | UTC 发生/接收时间及每 job 序号；服务端校正乱序，客户端时间不能替代权威时间 |
| environment / release / source | 生产/测试、应用/网关/解析器版本、浏览器/服务端/任务来源；明确模拟数据，不与生产指标混算 |

用户字段只从鉴权上下文取得；前端不能通过日志接口查询其他账号，不能写权威 token/成本或任务成功。业务事件与 UI 进度流共用关联 ID，但内部日志、堆栈、prompt 和后台候选不会全部下发用户界面。

#### 16.9.2 Prompt 保存方式

LOG-02：每条已提交用户 prompt 保存 prompt_id/version 与 message_id，记录提交时间、上下文来源、编辑前后版本及内容 hash。原始业务文字完整保存在加密内容区，不能仅保一个不可还原 hash、模型摘要或最后一轮消息。密钥、验证码、Cookie、访问令牌等认证凭证在保存前剔除并记录 redaction 标记；用户提示中包含这些凭证时也不例外。未提交输入不采集。

模型实际输入另存 model_request 快照或能在保留期内完整还原的内容清单：消息顺序/角色、用户 prompt 版本、系统/开发提示模板版本、历史对话版本、检索片段及材料锚点版本、工具定义/结果引用、模型与生成参数、截断/摘要策略及真实输入 hash。静态模板按版本去重，不反复复制整份审计报告；变化的片段不能只引用会被覆盖的“最新版本”。还原是诊断用途，不自动重放模型或收费。

记录 declared_intent 与 resolved_job_type，解释同一句话为何保存信息、回答问题或启动更新。仅点击按钮且无自由文本时，prompt_ref 可空，保存 action 和结构化输入快照，不伪造一句“用户 prompt”。输出引用最终回复 message/artifact 及质量结果；供应商隐藏推理正文不采集，推理 token 数在供应商提供时记录。

普通控制台、全文检索日志、指标标签、错误文本和默认客服页面不含 prompt/材料明文。工程运行人员默认只能看脱敏元数据；具有专门内容诊断权限的人员按原因/工单限时查看正文，每次查看、导出及权限变更记录审计事件。库运营、账务运营不因此获得用户正文权限。日志不自动进入募集书库、跨账号缓存或模型训练数据。

#### 16.9.3 Job 状态和错误记录

| 记录组 | 最低字段与判定 |
|---|---|
| 类型与上下文 | job_type=update/review/generation/qa/preflight/parse 等白名单；subtype 如 historical_revision/no_history_draft/source_identification、doc_type、目标市场/方式；系统维护任务单独标识 |
| 输入与配置 | input_revision、材料/目标/prompt 引用、规则/模板/模型/解析器版本、billing_mode、trigger_source、幂等键 |
| 执行过程 | 创建/入队/开始/结束时间、排队与阶段耗时、检查点、重试/取消/恢复、worker/lease；前端离线不改写服务端执行结果 |
| 业务结果 | outcome=succeeded/failed/cancelled/rejected，未终态为空；quality_status、delivery_status、artifact/message 引用；账务状态独立 |
| 错误 | error_id、category、code、发生阶段、safe_message、脱敏 stack、供应商 request_id/status、retryable、attempt_no、cause 指纹、恢复结果 |

job_type 由服务端路由确认，不只信任用户入口。一次执行拒绝也留下原因和输入引用；用户主动补料产生新输入版本时，新 job 通过 parent_job_id 关联。HTTP 200、模型 finish_reason=stop 不代表募集书成功：只有必要内容和质量检查通过、成果可获取才记录 delivery_status=delivered。M2 结算未完成时可保持运行账务状态 settlement_pending，业务交付结果与计费结果分别记录；终态只记一次。

错误分类至少覆盖 validation、auth、material_parse、ocr、model_provider、tool、queue、export、delivery、metering、internal。标准错误码与 16.7 一致；供应商原错误码另存，堆栈/请求地址/工具参数在写入前去除凭证和正文。用户取消单独归类，不记为系统故障；任务最终成功也保留中间错误和重试。结构化编码防止用户换行/控制字符伪造日志，日志中的文本不作为运维指令执行。

#### 16.9.4 Token、真实成本与计费口径

LOG-03：在实际发送模型请求前持久化 call_id 与 request_started；供应商响应、错误或取消发生后记录 call_finished/usage_observed。每次真实尝试均有记录，包括免费预检、解析、右侧问答、自检、失败和平台重试；不是只记录最终成功的一次请求。

| 字段 | 规则 |
|---|---|
| provider / model / provider_request_id | 实际供应商、API 模型 ID/版本及请求 ID；请求 ID 未返回时保留 null 与本地 call_id |
| input_tokens / output_tokens | 供应商实际输入/输出数；输入可含缓存、输出可含推理，按适配器明确包含关系 |
| cached_input_tokens / uncached_input_tokens | 只有已知缓存口径时归一；缓存是输入子集时 uncached=input-cached，不能再把 cached 加到 input |
| reasoning_tokens / total_tokens | 推理是输出子集时不重复加；total=input+output，仅在两项都可核实时给值 |
| usage_status / usage_evidence_ref | reported / pending / unavailable；保存允许字段的原始 usage 证据与映射版本，unknown 计数用 null，estimated_tokens 单列 |
| finish_reason / status / timing | 正常结束、长度限制、工具调用、取消等供应商结果；请求耗时、首响应时间和错误；不等于 job 成功 |
| cost / rate_version / billable / cost_payer | 定点费用及币种/费率版本；未确认费率成本为空，已知 token 仍保留；区分平台总消费、允许计费部分和最终用户扣分 |

网关记录是受信权威，执行框架转发的同一次 usage 是补充证据；按供应商账号作用域和请求 ID（无 ID 时用同一次 call_id）去重，不能按 prompt 内容去重，不同重试可能都真实消耗。供应商流式累计计数取最终/可验证累计值，不把每个分片累加成倍数。不同模型/计数器分别汇总，跨模型合计只作原始计数展示，不直接当可比费用。

断流、超时、取消未取得 usage 时记 pending 并按供应商可用接口/对账信息补齐；无法核实则 unavailable，保留部分已知计数与缺口。迟到 usage 追加修正事件后重算投影，不能篡改终态或重复收费。运维展示“已知消费＋未知调用数”，不能把未报告请求当零消耗，也不能用估算伪称实际。缓存复用且没有发模型时无新 call，记录 reused_from，新增 token 为已知 0。

示例口径：某次 input=1,200（其中 cached=200），output=300（其中 reasoning=100），真实 total=1,500，不是 1,800。若第一次失败调用消耗 400、第二次成功 1,500，运营记录总消费 1,900；按费用政策由平台承担的失败重试部分不会转为用户扣费。任务收费金额还受冻结上限、失败释放等规则约束，不能直接用原始总 token 推导。

M1 保存 billable=false、cost_payer=platform、billing_mode=platform_trial 或 source_preflight，reservation_id 为空；记录完整真实用量但不生成用户扣分。M2-03 复用这些调用和用量结构作计费归因，历史免费任务不能倒补收款。外购 OCR 页数/金额及数据查询次数另存计量单位，不能虚构为模型 token。

#### 16.9.5 持久化、故障恢复与查询

任务创建、状态/终态及交付凭证与 outbox 在同一数据库事务提交；模型网关使用持久化请求记录/缓冲再发请求。独立日志检索平台暂不可用时继续落可靠 outbox，异步重放，不能靠 stdout 或进程内队列作为唯一证据。外部模型响应与本地数据库无法形成同一事务：在途结果丢失明确记 unknown/pending 并先核对，不承诺不可能的端到端 exactly-once。

关键 prompt 引用、job 状态、模型尝试、usage、错误、权限及交付事件全量持久化，不采样；高频性能调试可采样且不影响计数。消费者以 event_id 去重，以 schema_version 校验，以 job seq 排序；异常进入可重放死信并报警。聚合是可重建投影，原始事件追加修正；不能因报告汇总而删除失败调用。

当平台既不能写事务记录也无可靠缓冲时，暂停接收新执行/新模型调用并提示服务异常，不能静默无日志运行；已在途调用的结果按检查点与可用存储保全，恢复后对账。日志管道故障本身通过独立健康检查告警。设计默认持久化后 60 秒内可检索；积压超过 5 分钟、死信新增、任务长期无终态或 usage 长期 pending 应告警，阈值按真实负载版本化调整。

后台至少支持按 user/project/job/trace、时间范围、业务类型/子类型、模型/应用版本、status/error_code 查询时间线，再关联受控 prompt、每次调用、用量和结果。索引至少包含 job_id+seq、user_id+时间、project_id+时间、job_type+状态+时间及 provider 请求唯一键；时间分区和分页避免全表扫及无限导出。

指标应明确分母：按选定创建时间窗口的已结束有效执行计算成功率 succeeded/(succeeded+failed)，cancelled、rejected、未结束任务数量及占比分别显示，不能从分母中隐去故障。按 logical job 去重，重试不是新成功任务；业务交付成功率与技术调用成功率分开，文件中有复核问题不等于技术失败。还须提供排队/执行 P50/P95、每类任务和模型的 token/真实成本、未知用量比例、错误分布与版本变化。普通用户只见本人任务结果/必要错误及费用，内部完整看板仅供授权人员。

#### 16.9.6 保存与清理

以下为 Web 阶段可调整的设计默认。M1 试用数据说明已发布诊断日志内容 180 天口径，API 与 Compose 默认也为 180 天；后续调整须同步配置和用户数据说明，不能使用无限期默认。M5 的诊断正文在本机按相同用途期限管理，平台临时模型请求副本仍遵守第 01 章清理要求，不以诊断名义暗中长期云存本地材料：

| 内容 | 初始保存策略 |
|---|---|
| 用户 prompt 和实际模型输入的诊断副本 | M1 默认 180 天，独立加密/权限；不改变产品对话/项目本身的保存策略，诊断副本到期后不得通过旧引用绕过读取限制 |
| 结构化任务/调用/错误与访问审计记录 | 180 天；移除正文/凭证，身份映射限权；依法或争议处理确需延长时单独记录理由和范围 |
| 无原始正文的统计汇总 | 365 天，按目的控制维度，不保留可恢复 prompt 的索引 |
| 备份与导出 | 有限生命周期，设计默认备份最长 30 天、导出链接 24 小时；恢复后应用删除清单，不让过期数据复活 |

项目删除/账号注销同时清理诊断正文、检索副本、导出和关联访问能力；依法需留存的必要计量/账务记录按规定隔离，不能连带长期保留 prompt。内容过期后 metadata 显示 content_expired/deleted，不伪装仍可完整还原。只读 append-only 指不能人工改写业务历史，不妨碍受控到期清理。M5 本机错误日志沿用无正文默认，平台模型网关继续权威记录调用用量；本地诊断正文上传范围需明确告知，不能绕过本机材料边界。

## 17 验收测试与实施路线

### 17.1 验收层次

验收分为交互、工程正确性、真实接入、专业成果四层。页面能点击和模拟模型通过，只覆盖前两层的部分内容。每个功能都要在实际部署的 Web 版本（M1–M4）或安装包（M5）、授权样本和真实服务上保留可复现结果。

### 17.5 专业质量门槛

关键事实、主体、金额、期间、单位、发行对象和条款在金标准验收集上不得出现未提示的确定性错误。任何跨用户数据泄漏、虚构引用、无依据签发、漏掉已知重大负面事实、错误现金扣款均为发布阻断问题。

可程序验证的数值用确定性复算，而不是另一个模型“觉得正确”。所有结果中的关键数据与规则结论应有可回查来源；无法验证时以待确认/未覆盖处理，不能靠高置信度文字通过验收。

建议对专家一致标注的问题统计精确率、召回率、严重问题漏报率、误报率和来源有效率；先定义分母和争议项排除规则。初始建议目标：明确问题精确率及召回率各 ≥95%，关键 P1 不漏报；这些是测试门槛建议，不能替代每个细分品种的验收。

OCR 统计字段级正确率与“错误但未提示”的数量，不能仅看平均字符准确率。表格中关键数值错误未被提示为 0，允许通过待确认机制安全失败；同时监测过量待确认以防产品不可用。

Word 检查包括实际打开、表格可编辑、章节完整、字体回退、页面布局、页眉、目录、批注锚点、修订关系、长表跨页、图片、特殊符号。存在更新版式变化应在交付说明中反映。
