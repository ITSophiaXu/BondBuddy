# 15 后台规则、模板及数据接入

## 15.1 运营后台与权限

OPS-01：普通用户没有募集书库入口。后台仅对授权运营、行业审核、数据接入及账务人员开放，职责分离：内容维护人员不能直接修改钱包，账务人员默认不能查看项目正文。

后台必须管理能力开关、规则版本、平台模板、内部参考稿、供应商配置、模型/价格版本、失败任务诊断、支付对账及活动参数。生产密钥不可在普通列表或日志中明文展示。发布、回滚、调账、授权变更记录操作者、理由与时间。

规则/模板发布建议双人复核；维护草稿与已发布版本分离，已启动任务锁定旧版本不随后台更新漂移。

## 15.2 内部相似募集书匹配

LIB-01：目的为无本企业历史稿时获取结构与写法参考。参考企业事实不能进入发行人事实库，不能向用户披露内部候选、评分、文件名或“蓝图匹配”步骤。

索引对象：文书 ID/哈希、来源与使用许可、发行人、市场/品种、资料时点、可读内容、前三大业务及原始收入证据、审核状态、替代关系和版本。

匹配流程：

1. 取得本发行人最近完整年度的合并口径分业务收入。明确主体、年度、币种单位、原表和每项收入来源。
2. 统一收入统计口径，去除重复合计行，核对板块划分；“其他”不能被未经核实地解释成某具体业务。
3. 按收入排序，识别前三项。业务名称仅使用人工审核的保守别名映射，不把宽泛行业标签当同一业务。
4. 匹配库内同样有来源证据的前三项业务集合全部一致的候选；顺序可不同，不能只命中一两项就通过。
5. 多个有效候选先按目标市场/品种适用性，再按审核有效性与资料新旧排序；不是数字相似度最高就直接选用。
6. 复制只读结构参考到任务隔离区，记录 reference_id、匹配证据、规则版本、最终选择原因，供内部复核。

来源冲突、只有部分业务附注、第三名并列不能唯一确定前三项时不猜。企业确实只有一两类业务的特例不能凭空补第三类；首版严格匹配无法处理时进入内部专家确认/能力补齐，不以无关企业替代。后续若支持少于三类的特例，须有单独版本化规则和样本验收。

用户已上传可用相似稿时，可作为用户指定结构参考，不要求后台偷偷另选一份；仍检查可读性、目标结构适用性并隔离事实。无匹配且没有指定可用参考时，按当前能力不可执行/失败处理，不靠收费公式中的 none 档绕过匹配要求。

前台的可操作反馈是“需补充最近年度业务收入附注”“现有资料暂无法完成编制”等，避免暴露实现细节，也不能把内部覆盖不足说成用户资料必然错误。

## 15.3 行业规则包

RULE-01：十个具体首发市场×品种组合，以及 DFI 储架安排，均需有效规则和样本覆盖。现有主要知识集中在交易所尤其上交所私募；大公募不能直接复用小公募包，银行间不能用八条通用方法冒充正式规则库。

每条规则应具备：

| 字段组 | 最少字段 |
|---|---|
| 身份/来源 | rule_id、版本、发布机构、文件名、官方 URL/文件哈希、条号、准确原文 |
| 效力 | 发布/生效/失效日期、过渡条款、后继版本、验证人/时间 |
| 适用性 | 市场、品种、投资者范围、申报阶段、行业、特殊事项 |
| 执行 | 必要输入、公式/判定逻辑、例外、检查器版本、证据定位 |
| 输出 | 通过/不适用/问题/待补证/待判断/未覆盖，严重级建议 |
| 验收 | 正例、反例、边界、来源冲突处理与专家确认 |

法规、自律规则、参考模板、机构内部准入、专家方法、窗口指导、示例必须标明不同效力。来源含疑问、批注、机器转录或未核实阈值时只作研究线索，不直接启用硬拦截。

规则更新流程：发现官方变更 → 获取原文及指纹 → 判断差异和过渡期 → 专家复核 → 回归样本 → 发布签名包 → 通知受影响未执行项目。历史成果保留当时依据，不能后台改掉后假装一直使用新规则。

### DFI 适用包

DFI 随首发验收，但按“统一注册/储架安排 + 文书阶段 + 实际工具”选择规则。分别维护注册适用条件与文件、有效期及变更、覆盖工具、分期发行披露、承销商团、具体一期工具条款的来源和效力。不将统一注册一律理解为必须有固定注册额度；有无额度及其限制以适用规则和实际文件为准。

当前内部知识摘录 S019:1505 涉及统一注册与实际发行工具分离、注册阶段额度及分期确定条款；S019:1493 涉及承销商团。两者仅作为待核查线索，不替代协会现行原文；境外发行人规则不能直接推广给境内企业。正式规则、发布/生效时间、适用主体和样本均经专业确认后发布规则包。

内部参考库可保留 DFI 注册与实际工具元数据；仍需满足同一发行人审计口径下前三大业务匹配。参考稿出现多个工具不等于实际发行多个工具，也不放开未验收的复杂产品。

## 15.4 平台与私有模板库

平台模板：为每个文种维护适用市场、章节/字段、表格/样式、规则依赖、样例与质量检查。平台必须持有相应授权，不能通过默认抽取用户模板建公共库。

私有模板：user_id + broker_id + document_type + version + hash，默认本机保存，处理所需暂存也执行账号隔离。用户可查看自己的版本、设默认、替换或删除；运行中快照保留。两个账号同券商不共享名称、结构和使用次数。

首发不提供“默认匿名共享”隐含勾选。未来共享需独立用户授权及新的脱敏审核产品流程，不影响本次默认私有要求。

## 15.5 启信宝、Wind、企业预警通

DATA-01：三家均为用户要求支持的接入目标，不将“开放网页搜索”当作这项需求已经完成。当前尚无正式接入与授权证据。

| 适配器 | 目标用途 | 上线前必须落实 |
|---|---|---|
| qixinbao | 企业主体、工商登记、控制关系及授权范围内风险信息 | 实际产品/API、企业唯一标识、授权字段、历史时点、费用和展示许可 |
| wind | 债券、发行/存续/兑付、评级及授权财务/市场数据 | 合同允许的接口或终端 SDK、席位/服务端调用模式、数据使用及留存权 |
| yujingtong | 企业信用风险、债券事件、公开重大事项及授权企业信息 | 对应产品/API、事件状态/时间、去重、覆盖、采购与再展示条款 |
| official_web | 官方公告、规则原文及必要公开检索 | 检索供应商/抓取许可、来源可靠性、失败及限流处理 |

以上为业务能力目标，不是未经核实的接口字段保证。Wind 可能涉及特定终端、SDK 或授权方式，不能假设存在任意平台可转售的通用 REST API；也不能复用个人席位给所有用户代查。

统一接口契约建议：

~~~text
query(provider, capability, entity_identifiers, query_scope,
      as_of, run_id, purpose, idempotency_key)
 -> status, records[], coverage, queried_at, source_refs[],
    usage_event_ref, rights_metadata, limitations[]
~~~

capability 可包含 entity_profile、ownership、bond_inventory、credit_events、litigation、penalties、announcements。每家发布 capability_map，标明支持、未购买、未验证和不可用；一个供应商并非必须支持全部枚举。

records 标准化结构必须保留供应商原字段映射和原记录 ID。空记录、主体未匹配、权限不足、限流、接口错误是不同状态，禁止都映射为空数组。

## 15.6 授权、费用与复核覆盖

每项调用检查平台合同、账号可用权、地域/席位、用途、缓存/展示和再分发限制。授权不足返回 DATA_NOT_ENTITLED，余额再多也不能越权查询。

若合同允许平台提供数据服务，采购费用并入同一任务，不另弹人民币付款或价格授权。用户已有授权账户的模式只有供应商合同允许时才设计专用连接；用户不必配置模型密钥。

允许的缓存键包含 provider、capability、entity_id、as_of、授权主体和有效期。历史财务、最新工商和最新事件适用不同刷新策略；任务结果展示事实时点和检索时间。缓存无效时不能假装刚查询。

替代源用于容错时必须覆盖同一业务要求并符合授权，保留实际来源。检索失败不等同不存在；整类必需核验不可用时按第 06 章判定未完成。数据源接入尚未完成应在研发状态中公开标记，不能在产品中显示虚假供应商成功标识。

## 15.7 接入验收

DATA-A01：每家供应商至少验证主体唯一识别、有效结果、真实空结果、历史/最新时点、授权失败、限流、超时、去重与费用事件。

DATA-A02：同名不同统一社会信用代码不得混合；商业登记字段与会计数据不能直接同名覆盖。

DATA-A03：供应商给出的诉讼/风险状态变化保留时间与证据，旧记录不无条件当当前有效。

DATA-A04：每次可计费用量能对应唯一采购事件；失败重试成本按计费规则由平台承担。

LIB-A01：严格三业务匹配、有并列/冲突/缺少业务项、全部无匹配和用户指定参考分别验收。

RULE-A01：每条生产硬规则都有正式依据或明确机构规则依据、适用性和通过/失败样例；未验证研究规则不能输出确定合规结论。
