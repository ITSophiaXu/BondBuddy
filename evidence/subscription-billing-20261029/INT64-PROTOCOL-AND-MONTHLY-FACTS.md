# Int64 协议迁移与月度经营事实

2026-10-29。实现与合成验证记录；没有真实扣款、客户材料或模型效果测试。

## 金额与积分协议

- 当前协议 `int64-decimal-v1` 为默认值。API 金额、积分、已声明累计计数使用非负 int64 十进制字符串；`"0"` 是零，`null` 是未知。禁止 JSON number、负数、小数、前导零、科学计数和越界。原始请求在 AJV 强制转换前验证。
- `number-v1` 仅提供能够精确表示的旧读取及服务端已经持久化的同一 owner／resource／request 重放。原处理器仍检查完整原请求哈希。旧数值不足以表示余额时明确拒绝，不舍入。
- 旧处理器的有界单任务价格和支付渠道适配器可以保留受检查的 number；原始业务请求、已锁定 manifest 和幂等哈希不被协议迁移重写。新 `check-batches` 原生字符串接口独立验证，不进入旧 number 解码器。
- 钱包累计、原 lot 分配、预留和授额使用 BigInt。订单/价格上限与表示上限分别处理；不存在累计充值的业务封顶。每次授额与任务质量返还都在账户锁内检查剩余总额，无法表示时整笔不入账，原申请及退款权利保留。
- 当前浏览器以精确字符串读取并以 BigInt 运算。旧 v1 恢复信封及退款申请保留原 body、原 headers 和原 digest，重放只增加传输协议标识。新记录采用 v2。
- 支付回调原始签名内容不进入该转换。支付实际收款／退款以已认证原渠道回执为准。
- `/admin/metrics`、任务时间线及 `/admin/trial/usage`、`/admin/trial/cost-ledger` 的累计 tokens 和相关计数使用精确整数；供应商十进制成本保留原 Decimal 文本，不把未知用量视作零。

## 月度事实 CLI

模块：`apps/api/src/subscription-facts-report.ts`。

```text
DATABASE_URL=<内部只读连接>
node apps/api/dist/subscription-facts-report.js 2026-01 2026-12
```

仅运行一个 PostgreSQL `REPEATABLE READ, READ ONLY` 事务。没有写账、补单、触发任务、退款或调用支付渠道。按北京时间自然月分组，跨度最多 36 个月，报告时点来自数据库当前时间。2026-11-04 起输出为 `subscription-facts-exact-v2` JSON；v1 曾使用退款事件的本地入库月份，迟到回执可能导致归月错误，历史 v1 不能代替修复后重新读取的月份事实。

| 字段 | 含义 |
|---|---|
| `accepted_order_amount_fen` | 已付款订单面额；属于预收，不等于任务收入 |
| `verified_payer_cash_fen` | 有认证实付证据的付款现金；任一相关订单缺证时为 null，同时保留 known 和缺证数 |
| `cash_refunded_fen` | 原渠道成功现金退款事件金额，按认证 `provider_succeeded_at` 的北京时间月份；存在缺成功日期的退款时，各月均为 null，与任务返积分分开 |
| `cash_refunded_fen_known` | 已有认证成功日期的当月退款金额；缺证时仍保留此已知部分，不能当作完整总额 |
| `unallocated_cash_refunds` | 报告时点已成功、但日期未知的退款笔数、精确金额和原退款 ID；尚无法分配到任何月份 |
| `net_payer_cash_flow_fen` | 当月实付流入减当月成功现金退款；付款缺证或存在日期未知退款时为 null，不用于重复冲减任务收入 |
| `redeemed_points` | on_delivery 原结算事件与原 lot 分配；分配不完整或重复时为 null |
| `quality_returned_points` | 原任务售后/更正事件的返还积分 |
| `net_earned_order_consideration_fen` | 各原 lot `A × 已兑付积分 / Q`，减原 lot `A × 质量返还积分 / Q`；保留精确分数 |
| `original_batches` | 上述兑付和返还按原资金批次追溯；不是按现行售价重估 |
| `expired_unfrozen_points_at_snapshot` | 报告时点已到期、未冻结余额，按该 lot 的到期月分组 |
| `excluded_legacy_progress_settlement_points` | 历史渐进扣费模式的结算数量；显式排除，不能假装已完成收入归属 |

到期字段是当前快照，不能称为历史当月到期流量。现有账本没有独立的到期事件，报告不会用今天的余额伪造历史失效数量；到期额度也不计收入。未来若要固定历史到期流量，应另增可核验的到期事件，而不是改写本报告。

现金退款不回填原支付月，也不用受理时间、通知外层时间或本地完成／入库时间。1 月付款、2 月认证退款成功分别记录两个月的流入与流出；1 月已成功、11 月才补入库的退款仍归 1 月。缺成功日期时不能借本地日期填补，也不能静默过滤为 0；同原退款号取得认证日期后，后续只读报告恢复归月，补证不能再次退款、增减积分或新增财务事件。此版本仅改变管理事实 CLI，无公开 HTTP DTO 变化；调用方须识别版本并接受退款和净现金流的 null。

`A/Q` 与既有 exact-v2 经营口径一致：沿用原批次已锁定对价，结果不是法定收入、实际供应商支出、税后净利润或利润率。实际税务、支付补贴和公司成本需另行会计核实。未知原现金基础不会退回使用积分面额估算。

## 新购、续期及 cohort

订单数记录真实已付款事件。已核实现金付费人数按用户去重，缺现金证据的订单另列，不当作零现金订单。

保留的订阅购买要求正现金实付且尚未全额现金退款。每位用户的第一笔保留周期归入新购；新周期只有在更早的保留周期已经结束后才算续期。周期序号 `cycle_index > 1` 不是续订证据，退款后重新开通不会因此被误判为续订。同一月或重叠周期的多张订单单列。

cohort 按第一笔保留订阅的实际服务开始月归组，观察其后第 1–12 个自然月的再次订阅购买。目标月完整结束后才计算 `跨月订阅复购人数 / cohort 人数`；未成熟的窗口返回 null。没有可观察 cohort 时返回空数组及明确状态，不填 0% 留存。后续全额退款会使历史 cohort 按报告时点重列。

这是购买复现事实，不是产品活跃留存率，也不是未来续费预测。90 天剩余额度、余额到期和同月加充值不构成一次新订阅复购。

## 验证范围

使用合成 PostgreSQL 克隆数据库和隔离 Azurite。覆盖大于 `Number.MAX_SAFE_INTEGER` 的钱包读写、并发预留、终态释放、旧键重放和改额拒绝、int64 余额上界、任务售后整笔回滚、原 A/Q 现金退款、逐月已付订单与不写账报告，以及成熟/未成熟 cohort、缺现金基础和分配不一致。

支付渠道使用已签名的合成回执；没有实际外部商户订单。模型未调用，因此这些证据只验证计费和账本行为，不能证明模型质量或实际公司盈利。
