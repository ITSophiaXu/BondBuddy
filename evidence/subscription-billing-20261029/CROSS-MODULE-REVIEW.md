# 账务模块交叉审查

2026-10-29。只读审查发现的两项接口联动问题均已交由原文件负责人修复；未改动正式资金或调用真实商户。

| 问题 | 原表现 | 修复与回归 |
|---|---|---|
| 日账单漏算质量返分来源 lot 的退款积分事件 | 一笔原来源 42,000 分 + 返分来源 10,500 分退款，现金 500 元正确，但对账仅看到 42,000 分，误报差 10,500 分；纯返分来源会误报零积分 | 按退款分配表、owner、lot 和精确事件键汇总各来源积分，同时单独核对现金。`payment-refunds.pg.test.ts` 的混合来源测试增加账单断言，定向运行 1 passed / 0 failed / 0 skipped，差异为零且钱包、积分流水计数不变。 |
| 旧 v1 已付检查复用与新付费检查不能组成一批 | 父批次强制所有子项 price_version 相同；旧 v1 复用为 0 分，新项使用自动计费版本，导致每次报价都返回 QUOTE_CHANGED | 父批次使用当前自动计费版本，子项保留各自合法历史版本。新增 `workpaper-legacy-checks.pg.test.ts`：v1 990 分范围/报价为明确合成历史凭据，原 lot 经过实际预留、Word 报告 promotion 和 finish 结算；再以真实 HTTP 受理混合批，仅新项冻结，原 v1 记录不变。最终 API/worker 统一构建后执行 `node --test apps/api/dist/workpaper-legacy-checks.pg.test.js`：1 passed / 0 failed / 0 skipped，约 15.5 秒。 |

其他审查范围：

- `payments.ts` 的已付订单现金补证只定位原充值 lot，不调用 grantCredits；缺失或归属/Q/source 不符时拒绝补证，不制造新余额。
- 关单先保存原意图，再由原渠道认证查单决定结果；晚到的认证 paid 可以覆盖本地 expired，已经 paid 不被失败回执降级。
- `payment-statements.ts` 只追加账单证据、比较记录、差异和告警，不调用支付、退款或余额变动函数。
- 批量逐份检查同事务内先核验总余额，再逐份保存 run 和预留；每一项仍通过自己的交付门槛结算，父批次完成不替代子项交付证据。

这些结果是代码和本地合成测试证据，不等于真实支付商户、模型质量或生产环境验收。
