# 付款意图恢复与冻结分项

2026-10-29。代码和合成验收记录；无真实商户支付、代扣或客户成交。

## 本轮实现

- `apps/web/src/checkout-intent.ts`：同一账号的付款意图在请求前持久保存，以浏览器 Web Locks 串行处理跨标签操作。保存首次订阅、手动续订的原订阅 ID、套餐、渠道，或原充值金额、项目，以及同一 `request_id`。读取或写入不可靠时不新建支付请求。
- 未知结果、一般接口错误和本机时间流逝均不删除意图。已知原订单查询同号；未知原订单重放原接口和正文。更换套餐、渠道、金额不能覆盖原未决意图。只有服务端核实终态、且当前页面观察过该原意图后，用户新购才能创建新请求键；过期旧标签不会把旧点击变成第二笔新购。
- 已绑定订阅订单继续核对原金额和原积分，当前套餐调价不改写它。本页必须认证读取并展示过该订单终态，跨标签 storage 通知本身不赋予新购资格。读取历史已付订单也不会据此自动消费另一笔新等待任务。
- 原付款对应的任务返回上下文保存在意图中，另一标签的等待任务不能替换它。取消等待任务仍由既有恢复记录校验，不删除支付订单。
- `subscriptions.ts` 从同一只读事务内的 lot 冻结总额和未决现金退款分配读取 `task_held_points`、`refund_held_points`，账户和每期额度分别显示“任务预留”及“原路退款冻结”。原 `held_points` 保留为兼容总额，未建立第二本余额账。
- 新分项使用现有 number 协议并做非负、安全整数检查。原附件要求的全量 int64 十进制字符串协议仍待统一迁移；本轮不把分项语义修正声称为该协议已完成。

## 其余只读审计发现

核对了原附件全部 300 行及最新版 Spec；以下未由本轮两项修复覆盖。

1. **记录刷新没有刷新消费/支付列表。** `subscription-billing-page.ts` 的账户刷新不调用 `history.refresh()`；`CreditHistory` 的“刷新记录与余额”只发 `bondbuddy:credits-changed`。订阅页面收到事件只刷新账户，已载入历史仍缓存。应追加消费/支付列表刷新，验证结算/返还/到账后的行与余额同步。
2. **取消自动续费结果未知后没有可用的查询入口。** `subscriptionSummary()` 仅在 `mandate_status==='pending'` 显示刷新；`cancel_pending` 时后端已将 `auto_renew=false`，界面会出现“授权自动续费”而服务端拒绝重新授权。应给取消待核对状态继续查询/解除入口。真实渠道代扣仍未具备；该用户状态机可用合成适配器先验收。
3. **价目中的范围展示不完整。** 账户价目只展示各项名称/单位/积分，只有全面复核输出 scope/included；其他 SKU 的后台 scope 多为“独立业务范围”，未完整展示最新版规定的年数、问题数量、诚信主体/官网、同轮维护及新范围边界。此项关乎无二次确认条件下的可理解收费规则，应从统一服务端范围元数据展示。
4. **月度经营验证闭环未完成。** 当前可检索实现中，订阅表消费者为账户/执行/退款/对账；`commerce-economics.ts` 是单 run 内部报告，没有订阅人数、成功续订 cohort、档位、90天兑换/结转、注册至首付费等月度聚合。最新版 Spec 第124行要求月度事实，财务文件里的 null 是诚实占位，并非经营报表已实现。可先做只读事实导出：明确同一人月去重、首付费/续订分母、零分母返回 null，费用证据不全保留 null，不能用累计注册用户填订阅人数。
5. **历史订阅订单详情依赖最近50期。** `subscriptionAccount()` 只返回50期；`paymentPeriod()` 找不到所查旧订单时会把订阅显示成“按需充值/永久有效”。应让单订单 DTO 明确业务类型及锁定周期，或另查所需期，不能仅从分页账户列表猜测订单性质。

已核实不存在的误报：手动续订入口已经调用 `/subscriptions/:id/renew`；当前月内不允许提前换档与 API/Spec 一致。订阅模式开启但无商户时仍显示积分、套餐和正确价表，购买关闭；已有浏览器用例使用真实 catalog 路由响应覆盖此行为。
