## Published identifiers, protocol and price

DeepSeek's [first-call guide](https://api-docs.deepseek.com/) names `deepseek-flash` for DeepSeek-V4.1-Flash and `deepseek-v4-pro` for DeepSeek-V4-Pro-0813 at `https://api.deepseek.com`; its OpenAI-format example calls `POST /chat/completions`. The older `deepseek-v4-flash` and `deepseek-v4-flash-vision-exp` names are accepted aliases for the current Flash model, not stable IDs to pin. The product phrase “DeepSeek Flash v4.1” is not an API ID. The legacy prototype's `deepseek-chat` default is not the current ID documented on that page. Account availability, negotiated prices and exact response behavior remain unverified.

## Documented behavior versus live evidence

- [Multi-round Chat](https://api-docs.deepseek.com/guides/multi_round_chat) says Chat Completions is stateless and the caller must resend prior messages. [Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode) says reasoning content must be preserved across turns that carry tools. The current text-only prototype bridge drops tool calls and some non-text content, so it cannot establish this behavior.
- [JSON Output](https://api-docs.deepseek.com/guides/json_mode) uses `response_format:{"type":"json_object"}` plus a JSON instruction, yet warns that output can occasionally be empty. Validate the returned JSON against the task schema and preserve a failure state. A claimed JSON mode is not proof of schema conformance.
- [Tool Calls](https://api-docs.deepseek.com/guides/tool_calls) documents function calls, while the client executes the tool. Strict JSON-schema tool mode is beta and uses `/beta`. The M1 probe exposes **no tools**. A future allowlist must resolve every material handle and `project_id` against the persisted owner before execution; uploaded content never supplies shell, arbitrary path, URL or tool authority.
- [Vision](https://api-docs.deepseek.com/guides/vision) documents JPEG/PNG/GIF/WebP and `input_image` in Responses for Flash. OCR and image-based use still need account tests and a material authorization path. No image is forwarded by this probe.
- The [first-call guide](https://api-docs.deepseek.com/) documents `stream: true`; the [rate-limit guide](https://api-docs.deepseek.com/quick_start/rate_limit) notes SSE keep-alive comments. End-of-stream usage availability, cancellation receipt, request-id headers, provider-side result lookup and retry idempotency were **not established** by the retrieved pages. The probe treats interruption or missing final usage as pending; it never silently retries. The current `/guides/responses_api` link returned the first-call page when retrieved, so detailed Responses field compatibility also requires a real probe.
- The [token usage guide](https://api-docs.deepseek.com/quick_start/token_usage) says actual usage is the API-returned usage, not offline token estimates. The probe normalizes `prompt_tokens`, `completion_tokens`, `total_tokens`, optional cached-input and reasoning-output subsets; it accepts totals only when `total = input + output`, `cached <= input`, `reasoning <= output`. Missing or inconsistent counts remain pending, never zero. A failed real attempt may still consume tokens; every actual attempt needs its own ledger row.

Official [Codex configuration reference](https://developers.openai.com/codex/config-reference) (OpenAI Docs, retrieved 2026-09-24) permits custom providers and says `model_providers.<id>.wire_api` supports only `responses`; it also documents provider base URL, environment key and retry settings. DeepSeek's pricing and vision pages advertise a Responses API, but there is **no live evidence** that this host's Codex CLI 0.156.1 can complete a DeepSeek multi-turn/tool/schema/stream/usage run. The prototype's loopback bridge translates Codex Responses to DeepSeek Chat Completions in a single buffered call and fabricates a Responses stream after completion. That can demonstrate neither genuine supplier streaming nor safe retry/reconciliation. The probe uses direct Chat Completions with no Codex process and cannot close the Codex compatibility criterion by itself.

## Bounded implementation and handoff

`apps/worker/src/deepseek-probe.ts` is an isolated testable Chat Completions probe. It sends no tools and cannot be reached from the API or production `runOnce`. Its caller must provide a durable owner-checked `ProbeJournal`; `recordIntent` must commit before the only outbound request. It records owner/project/job/run/trace, `logical_call_id`, `call_id`, attempt, prompt snapshot reference, model/config version, provider ID when available, finish reason, outcome and usage. A failed intent write prevents the call. A timeout, cancellation, malformed JSON, tool request or stream without `[DONE]` remains `pending_reconcile`, with no automatic retry. The synthetic tests exercise these cases and cumulative stream usage. The call ledger stores references and sanitized codes, never credentials or prompt text.

This is an interface handoff to #79: persist the intent and observation with the same owner, job/run/trace and outbox transaction; record each retry as a separate attempt; preserve raw permitted usage evidence and source/version; use a supplier-confirmed query or reusable result before clearing unknown outcomes. #17 currently offers only `confirmed_not_sent` reconciliation and intentionally lacks a durable completed-result path. #79 and #17 must agree on that path before this probe can be wired to runs. No migration or public contract was changed in this branch, avoiding a conflict with the parallel #79 Worker. A future live probe needs an approved account key available through the host's established secret mechanism, an authorized synthetic prompt and account access to the specified model; record only redacted request IDs, usage and behavior in #16.
