# BondBuddy 设计 v5 锁定后的开发计划

日期：2026-10-19。状态：**开发规划草案，等待设计锁定；没有创建 GitHub Issues，没有开始本计划的业务功能开发，没有部署。**

人力依据：用户确认 **1 名开发主导，配合 Codex**。以下估算已经考虑复用现有代码与 Codex 辅助，不按三人并行计算。

## 1. 排期建议

建议按 **约 20 周**安排完整业务版本，预算窗口为 **16–25 周（约 4–6 个月）**。分批提供本地真实功能验收，不必等全部完成才试用：

| 里程碑 | 从设计锁定日起的累计窗口 | 可实际验收的结果 |
|---|---|---|
| M0：范围与技术验证 | 第 1–2 周 | 固定版本、样本、接口；核实 Word 修改与重点网站接入难点，修正后续估算 |
| M1：项目与文件工作流 | 第 4–6 周 | 一个项目贯穿已有更新/复核/生成能力；项目文件真实归档；模板上传一次后复用；已有 6 类文件按新流程生成 |
| M2：文档复核与一致性闭环 | 第 8–12 周 | 四类复核、原文修订/清洁版；募集书与关联文件对比；逐项/批量接受；新旧版本与文件状态联动 |
| M3：12 类文件及项目问答 | 第 12–17 周 | 新增 6 类文件；Word 问题清单解析、回答、回填、补材料续答；第一批可检索的公募问答案例 |
| M4：诚信核查 | 第 16–22 周 | 名单、全国与属地来源执行、证据与底稿；各网站实际覆盖和待人工事项明确展示 |
| M5：本批统一验收 | 第 20–25 周 | 固定集成版本、旧项目兼容、真实样本与 Word/WPS 验收、缺陷修复、发布交接 |

这些窗口是单人顺序推进时的预计累计时间，不能相加。M0 的网站验证在前期完成，正式接入集中在 M4；如诚信核查业务优先级更高，可与 M3 对调，不能把同一个人的工期当成可并行压缩。

29 个 Issue 草案合计 **69–105 个开发人日**，包含各自实现、代码审阅与定向测试，以及单列的集成/质量验收工作。按每周 5 个工作日，另留约 15% 的跨模块返工和故障缓冲，约 **80–121 个工作日，即 16–25 周**。业务专家整理原始知识材料、等待授权/账号/网站恢复、用户迟延验收不计入开发人日。该范围是静态代码评估，M0 后应重新收敛。

估算前提：开发者基本全职投入、熟悉现有仓库；用户或业务同事每周能安排约两次短验收并及时提供模板和专业结论。Codex 用于实现、测试、代码检查和文档整理；不假设增加 Codex 会话就能同比缩短原件验收、网站接入或业务判断时间。

**诚信核查的工期前提待设计锁定时确认：**20 类网站都进入执行及覆盖清单；能自动查询的执行真实查询并保存证据，登录/验证码/无公开检索能力等未完成项明确转人工补证。若验收要求是“所有网站、所有地区始终无人值守完成”，目前不能给出可靠总工期；应先完成 INT-02，再单独估算接入、服务费用或无法实现的范围。列出官网链接不等于自动核查已完成。

## 4. 依赖与建议开工顺序

主依赖链：

1. BASE-01 → BASE-02 → FILES-01 → 各工作流归档/输入引用。
2. FILES-01 → GEN-01 → GEN-02 → GEN-03 / GEN-04。
3. REV-01 → REV-02 → REV-03；FILES-01 → CON-01 → CON-02 → CON-03 / CON-04，CON-04 复用 REV-03 的文档写入能力。
4. QA-01 → QA-02 → QA-03；KB-01 → KB-02 → 增强 QA-02。没有知识库时也应能依据项目已有材料回答，不能把通用资料库作为 Word 问答的硬前置。
5. INT-02 尽早验证；INT-01 → INT-03 → INT-04 → INT-05。
6. OPS-01 按模块接入，REL-01/02 按里程碑滚动验收。

单人开发建议每次只推进 **一个主要功能切片**。Codex 可以承担清楚界定的实现/测试，但公共契约、数据库和同一 Word 工具的修改应按依赖合入；避免同时开多个长期分支后集中解决版本冲突。

实际开工首批：BASE-01、INT-02、BASE-02、FILES-01、FILES-02、UX-01、GEN-01、GEN-02。第一轮用户验收选“旧项目继续使用 + 新项目更新 + 保存模板 + 两种文件生成 + 项目文件下载”这条真实链路。

若需要更早验证核心价值，优先保留 M1 + M2：**约 8–12 周交付项目文件、模板、已有生成、复核和一致性更新闭环**。此时 Word 批量问答、知识库、完整诚信核查和新增 6 类文件仍未全部完成，应明确列在后续里程碑，不称为全量设计交付。

## 5. Design lock 需要收口的产品决定

已确定：工作台无需先选项目；更新以新建项目为主；文件生成名称；模板上传后复用；项目文件直接展开；一致性以当前募集书为基准、用户接受后新建版本保留旧版。这些不再作为悬而未决的问题。

待在锁定时一次收口，当前估算采用以下假设：

| 决定 | 目前用于估算的假设 | 扩大范围的影响 |
|---|---|---|
| 12 文种的市场/品种覆盖 | 现有 6 类保留当前覆盖；新增 6 类按确认的目标市场和各一套主模板实现 | 每增加“文种×市场/品种”的实质新规则/模板族需追加开发与样本验证，不能只改下拉框 |
| 年度/半年度报告具体是什么 | 与设计的受托管理目录保持一致，锁定为一种业务报告定义 | 若同时要发行人定期报告和受托管理事务报告，应拆成额外文种与知识/模板任务 |
| 核查自动化边界及优先地区 | 全部来源列出并执行可行查询；受阻项明确待人工，允许补证 | 所有网站/地区全自动需 INT-02 后另估；相关账号/商业服务费另算 |
| 格式修改与手动编辑 | 网页逐处文字处理、原生 Word 修订/批注和清洁版；验证典型真实稿 | 完整在线 Office、复杂对象编辑/多人协作另立项目；不是当前 29 个 Issue 的隐含内容 |
| 一致性检查支持的文件 | DOCX 优先可修订；可读 PDF/图片/OCR 可查但标识限制；原始证据与签署文件只提示重核 | 自动修改扫描 PDF、签章文件或所有 Excel/图片不在本次 Word 更新估算中 |
| 公募问答知识资产 | 第一批 20–30 份确认来源，人工审核后检索；首版不训练模型 | 全网采集、海量清洗、持续增量采集或微调另估 |
| 新任务的费用 | 沿用账务基础；对新增检查/核查/Word 批量问题定义收费单位、取消/失败和重试规则 | 不能把设计里的演示价格或既有“单问题价格”默认为 Word 多题收费规则 |
| 缺资料、无人命中和已同步的口径 | 缺资料写入 UI 与文档；网站未查成不等于无异常；已同步只代表本轮已确认范围 | 需锁定样本文案及覆盖显示，避免同一状态在不同页面含义不一 |

这些是规划中的待决定事项，并非已替用户确认。锁定后新增范围写成变更单，注明影响的 Issue、验收样本和人日；小文案/间距调整不要求重新打开整份排期。

## 6. 验收与版本管理

### 每个 Issue 的工程交付

- PR/commit 指向冻结设计版本，列真实 API、worker、契约、迁移/配置和知识变更；数据库只加新迁移，不修改已部署迁移。
- 定向测试覆盖真实状态持久化、权限、输入/输出准确版本及该功能的关键失败路径。合成测试用于逻辑验证，必须标注；不冒充模型或网站实测。
- UI Issue 附同尺寸设计/实现对照；功能通过与专业结果通过分开记录。
- 每个开发 chat 用独立工作区/分支，面向 `develop` 交付；开工前与最新开发基线重新对齐，避免重复开发其他 chat 已交付的部分。当前设计分支继续用于设计迭代，不整体把其模拟实现并入生产入口。

### 统一验收样本建议

BASE-01 中由业务确认具体来源与预期，建议至少包含：

- 2 套具有不同表格/编号/修订历史的真实授权募集书，各自配套多个关联文件；另有金额/期间/单位不同但不应判冲突的对照。
- 12 类生成文种各至少一份可用模板及输出预期；一份模板包含旧主体事实，专门检查是否错误沿用。
- 3 份不同布局的问题清单（段落编号、表格、多级子问题），包含能回答、缺材料、事实冲突及补材料后续答的题目。
- 每条已开放的自动核查路径有真实查询证据；包含未发现、同名命中、接口失败/验证码/缺地区，并验证至少一个特殊属地。地区覆盖不能由少数样本外推。
- 政策样本包含准确命中条款、市场不适用和效力未确认；标点有应改和不应改对照。未触及内容不应被无关修改。

初版完成标准：用户能用真实授权文件贯通各已交付链路；下载 Word 与页面处理结果一致，旧版本仍可取；未能回答/核查/解析的内容明确保留待处理。性能与最大文件大小/题数/项目文件数在 BASE-01 固定，再按该边界测量耗时和成本；设计稿的定时进度不作为真实时延目标。

### 集成与发布分工

开发 chat 交付代码和测试，不部署。由用户指定的 **BondDraftAI 开发集成测试** chat 汇总固定版本，在独立本地环境提供验收，并维护 `work/local-integration-handoff.md`。用户验收并授权后，由 **BondDraftAI 统一发布** chat 排队发布和核验。本计划不修改共享交接文件、不向其他 chat 发消息，也不将“测试通过”写成“用户已验收”。

最终发布执行时间另由发布 chat 安排；上述开发工期截至本地业务版验收与交接，不含用户等待时间和生产发布窗口。

## 7. 维护方式

- 设计锁定时复制/更新本计划引用的 tag，并登记真正的锁定日期 T0；尚未锁定前不填假定上线日期。
- GitHub 建立一个设计落地 Epic，按本表建/关联子 Issue；将计划 ID、依赖、估算、验收样本和设计 tag 写入描述。
- 用待开发、开发中、工程验证完成、集成可验收、用户已验收五个状态管理；Issue 是否关闭按仓库当期规则，用户验收单独记录。
- 每完成一个里程碑，用实际人日、模型/站点结果和缺陷数量更新剩余估算；M0 后重点重估 Word 和网站部分。
- 业务部署与设计 tag 分别版本化，后续开发不移动 `design/project-consistency-v5-20261019`。
