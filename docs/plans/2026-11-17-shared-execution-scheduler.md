## 1. 设计结论与用户行为

取消“每个任务最多 4 路/8 路”的业务限制，统一从共享资源池调度**已经具备执行条件的独立工作**。实际并发由资源池的已验证容量和当前占用决定，可以随配置变化；任务不各自保存一套执行上限。

- 用户可提交 N 个符合认证、输入、幂等及原计费合同的独立任务。已接收任务持久排队；资源暂满只影响何时执行，不回到任务数额度拒绝。
- 调度顺序是账号 → 原始任务/批次 → 就绪工作。没有竞争者时，一个任务可借用全部适用空闲容量；有竞争时按共享资源实际占用公平分配。
- 分配发生在可安全切换的工作边界。已经发起的模型会话不因新任务加入而强行中断；公平分配作用于随后释放的资源。
- 同一来源材料可供多个独立目标读取。修改同一文档、存在先后依赖、更新同一成果指针的步骤仍受顺序和版本保护。
- 调度不会增加任务单价或重复报价/预留；排队与等待模型许可不计为模型执行。原计费模式、取消和退回规则保持。

例如，假设已验证共享容量为 8 个等价模型会话槽，且节点资源足够：

| 情况 | 预期行为 |
| --- | --- |
| 提交 12 个各有一个就绪会话的独立更新任务 | 12 个均受理；最多执行 8 个，其他等待 |
| 一个任务有 20 个独立题目或文件 | 可以同时执行 8 个，结束一个再补一个 |
| 同一账号两个任务，各有足够独立工作 | 竞争时逐步趋向 4 + 4；一个任务结束后另一个可用到 8 |
| 一个账号提交 100 个任务，另一个提交 1 个任务且有足够独立工作 | 先按账号分配，不能因 100 个任务获得 100 倍份额 |
| 第二个账号只有一个就绪会话 | 它可占一个槽，其余可由第一个账号使用，不空留其公平份额 |
| 某份整篇募集书当前只有一个不可拆分的模型会话 | 执行一个会话；不能靠调度器把它复制为 8 份或承诺加速 8 倍 |

表内数字只是容量为 8 时的示例，不进入业务判断。已有不可拆分的整篇编制链路可以作为一个工作单元接入；将其拆成章节并行属于另外的算法变更，必须证明跨章事实、结构、合并及质量门禁等价。

| `packages/contracts/src/execution-capacity.ts`、迁移 0181/0188 | 全局/节点容量只接受 4/8；`max_nodes` 等也属于有限运营策略 | 公共 V2 schema 和数据库都读取同一版本的资源策略；校验真实资源与预算，不把 4/8 当业务枚举 |
| `apps/worker/src/runtime.ts`、`apps/api/src/queue.ts` | 长任务租约、运行循环、模型许可分层等待；任务租约数不等于模型实际占用 | 协调工作和昂贵执行分开；以实际许可计份额，等待者不占执行槽 |

[#1348](https://github.com/ITSophiaXu/BondBuddy/issues/1348) 的“四并发”是历史扩容目标，要求同时保护 CPU、内存和暂存空间，并非永久产品规则。原有进程隔离和资源预算仍有必要，问题在于同一容量被多层不同常量重复表达，且单位不同。

当前 `ModelCallPermit` 保护的是一次 contained Codex 调用/会话及其进程树，并不保证等于一个供应商 HTTP 请求。会话数、HTTP 并发、RPM/TPM、任务数量和文件分组大小必须分开计量。上传分块、Blob 下载、ZIP 和解析的 I/O 限制也不随本设计机械删除。

## 3. 执行模型：业务任务与可调度工作分离

沿用唯一 PostgreSQL、`bb_runs` / `bb_jobs`、outbox、模型调用 journal、私有 Blob 和收费账本。新增的是同一队列内部的工作单元记录，不增加用户任务系统、报价系统或消息中间件。

一个工作单元可代表一题回答、一个独立文件、一次整篇模型调用，或一个必须独占写入的合并/交付步骤。前置步骤产生已验证的不可变输出后，后继单元才可变成 ready。

拟新增 `bb_execution_units`，字段至少包括：

- `owner_user_id`、受信 `root_task_key`、`unit_key`、输入与依赖结果 hash、`scheduler_version`、资源类别及资源画像版本。来源绑定为互斥联合：业务任务绑定现有 `job_id/run_id`，复核助手绑定现有 `message_id`；助手不为调度另造收费 run。
- 内部状态、控制版本、attempt 引用、grant token、node/epoch/session、检查点与输出引用、就绪时间及下一次可重试时间。公共 run 枚举不复制到这里。
- 业务任务唯一键 `(job_id, unit_key)`，助手唯一键 `(message_id, unit_key)`，数据库约束两类来源必须且只能选一类，并分别验证归属；重试增加 attempt，不新建工作身份。已有逻辑模型调用 ID 和完成结果继续复用；无法证明与旧调用同一输入时不自动重发。
- 输入 manifest 与可变调度记录分开。新增策略版本、节点或并发数不改旧输入 hash、报价、执行请求键和材料版本。

`root_task_key` 由服务端从已核验的原始 run 或冻结批次成员关系推导；批次全部子 run 归同一根任务。不能采用客户端提供的 scope，也不能用共享来源项目把彼此独立的新任务合为一项。助手仍归其真实账号和已持久化请求，参与同一适用资源池的公平分配。

协调器只短时读取检查点、持久化就绪单元和推进状态；等待依赖/资源时退出，由 outbox/轮询再次唤醒。就绪单元先保存小型引用，取得许可后才加载大材料、创建工作目录和启动子进程。不能先对 N 项 `Promise.all` 再让 N 个进程、连接或完整 prompt 在内存等待。

当前 `StageContext.lease`、检查点、journal 和 evidence 写入依赖父 job 的长租约，不能直接清空父租约实现“让出名额”。V2 必须一起引入单元执行 fencing：写入时核对 owner/run/input、单元 token、node/epoch/session、父任务控制版本和相应权限；父协调器短租约不能成为子单元写入的唯一依据。首次接入保留旧链路，待这些写入路径全部覆盖后启用 V2。

## 4. 唯一容量策略

在现有 `bb_execution_capacity_policy` 基础上增加版本化策略及历史记录，初始导入已经核验的有效运营值。本文不提高生产容量、供应商预算或节点上限。容量参数改变不要求改业务函数。

| 资源 | 分配与保护方式 |
| --- | --- |
| contained 模型会话 | 全局、供应商路由和节点可用会话许可取共同可满足的额度；计入所有服务组、旧 holder 和状态不明但尚未证明退出的进程 |
| 节点 CPU / 内存 / 暂存磁盘 | 工作类型有测量形成的画像和保留量；启动前分配，进程树由容器/cgroup 等实际限制约束；单纯查询“剩余内存”不作为可超卖证据 |
| 供应商请求 / RPM / TPM | 能在直接适配器请求边界观测和控制时分别限流；Codex 内部请求不可见时明确缺少这种精确控制，保留会话限制及供应商限流反馈，不用会话数假称 TPM 已受控 |
| 解析 / 渲染 / I/O | 使用各自资源类别和节点能力，按实际依赖调度；不得占用模型槽等待纯解析，也不得因模型繁忙完全堵住上传确认 |
| 本地执行器 / 数据库连接 | 限制实际执行和短事务并发；分页预取。启动时核对节点声明容量与消费者可承接容量，发现只能执行 4 却宣称 8 时明确不就绪或降低对外可用量 |
| 节点数量 / 费用预算 | 继续遵守已授权的云资源和费用策略；队列积压提供扩容需求，不直接授权购机或增费 |

策略采用经过验证的非负安全整数、资源画像和跨字段校验；暂停授予用明确开关表达。不得将 `0` 在不同层同时解释为“不限”和“禁止”。数据库保留唯一槽位、所有权、预算以及 node/epoch 约束，删除的只是散落的 4/8 枚举式容量限制。

有效容量取配置上限、节点能力与健康限制中共同可满足的部分。遥测可以因压力减少新授予；自动恢复最多回到已经验证的配置上限。首版不实现未经测量的自动加倍或以瞬时空闲率无限提升并发。遥测失效时停止依赖该遥测的新授予，保留既有 holder 直到取得退出证明。

策略调低时，若当前占用高于新值，等待自然排空后再授予，不杀任务也不伪造空闲；调高后按新版本利用真实新增容量。活跃 holder 记录原 grant 的策略版本，统计时始终计入全部实际占用。

## 5. 公平性、资源领取和防止等待层相互阻塞

首版权重全部为 1，调度针对同类资源池，不引入付费插队政策：

1. 从依赖已满足、未暂停/取消、账务允许、没有待核模型调用的单元中，选出至少存在一个可适配健康节点的候选集合。资格判定使用数据库事实。
2. 对等价模型会话，优先实际已占许可较少的账号，再比较该账号上次授予次序；账号内对原始任务用相同规则，最后按单元就绪时间和稳定 ID 排序。占用包括已授予未启动、正在运行和退出尚未证实的 holder，不使用“任务租约数量”代替。
3. 新加入的账号/根任务从当前公平队列位置开始，不把服务计数重置到历史最优位置。批次新子项和失败重试复用原根任务公平记录，不能通过拆单或反复重试插队。
4. 在短事务中重新验证候选及资源，将单元 grant、资源 holder、调度次序和 outbox 原子写入。事务提交后才准备大材料/启动执行；各 worker 不能各自读取同一个“剩余 1 槽”后都启动。
5. 完成并持久化结果、确认进程树退出后释放相应资源。唤醒调度器，分配下一项。无竞争时可反复从同一个任务取得工作，直至资源用满。

若后续同池工作出现显著不同的资源画像，使用预留资源的主导份额进行选择：`max(该账号各资源占用 / 该池各资源可用总量) / 权重`，账号内再按根任务计算；资源为零时该类单元不具备候选资格。此升级须有异构负载回归，不将文件数或历史总提交数作为权重。

选不进某节点的大单元不能阻塞其他节点；同时设置可观测的老化等待和未来空闲资源保留，防止小任务持续填缝让大单元永久等待。达到可配置老化阈值后，只对确实可容纳该单元的节点逐步保留所需空闲资源，其余资源仍可分配；已运行任务不被抢占。大于所有已批准节点能力的单元必须显式记录资源无法满足，不能无限显示普通排队。

并发领取使用现有短事务调度锁扩展；领取/控制操作统一锁序：调度锁 → 策略 → run → job → unit → node（多个按 ID）→ holder。模型结果写入保持 run → job → unit/attempt 顺序，不反向申请调度锁；完成后另发调度唤醒。节点 drain/控制路径同样审计锁序，禁止持有行锁再申请前序锁。网络请求、模型运行和等待不持有事务。

不得让一个单元拿着某类资源无限等待另一类资源：同一步需要的资源一并授予，不能满足就不取得昂贵执行许可。父步骤规划完成、退出其模型会话后才启动子步骤；不让父会话一边占住所有槽一边等待子会话。已启动会话中临时发生供应商退避仍真实占资源，不能仅因没有输出就释放其 holder。

## 6. 数据安全、暂停恢复和计费

- **并行读、独立写**：来源材料按不可变 pin 读取。每单元独立 scratch/output/Codex home；不得共享可变文件或一个编辑器状态。
- **顺序合并**：题目/文件结果按冻结序号汇总。前置校验、合并、实际渲染、可信质量门禁和双 Word 发布仍按依赖执行；调度优化不能跳过它们。
- **同目标保护**：现有同目标运行保护继续有效。将来缩短到“结果提交时版本比较并交换”的前提，是解决 [#1441](https://github.com/ITSophiaXu/BondBuddy/issues/1441) 等共享输入指针问题并通过并发写回验收；本设计不先行取消现有互斥。禁止最后完成的任务无条件覆盖较新成果。
- **控制作用域**：暂停/取消先更新父控制版本，阻止新的 grant，再按原语义停止所属单元、保存已完成检查点和排空进程。另一独立任务不受影响。迟到结果必须核对原输入和控制版本，不能发布成当前成果。
- **未知调用**：保留调用 intent、attempt、逻辑 ID、结果和 usage 待核状态。取消或连接断开不能推定供应商未执行；进程退出证明与供应商结果核对分别完成。未知结果不盲目重发。
- **退出证明**：holder 不按 TTL 删除。只有原 token/node/epoch/session 对应的实际进程树退出证明才释放执行占用。启动确认丢失也须核对，不能凭 grant 超时回收。
- **失败边界**：保留当前同一 run 出错/不确定时停止新工作并等待已接受同伴排空的语义，已完成结果可恢复。批次其他独立目标按其现有依赖和控制关系处理；不扩大为全站阻塞。
- **重试屏障**：[#1543](https://github.com/ITSophiaXu/BondBuddy/issues/1543) 的 worker 级恢复屏障只能在单元级正向退出证明覆盖之后收窄，不能为提高并发直接删掉。
- **费用投影**：从单元活动聚合到原 job/run，纯 waiting 不计活动；并行活动按原合同的有效时间并集计算，不把 8 个子单元变成 8 倍运行时长。固定价沿用原交付结算。模型真实用量逐 attempt 留存，unknown 保持 unknown；不存在子单元各自重新报价/预留。

## 7. 公共契约、迁移与启用顺序

新增公共内容只在 `packages/contracts` 定义：版本化容量策略、必要的单元/许可边界和有限等待原因；API/worker 导入同一定义。旧 `execution-capacity-v1` 只接受 4/8，不能向旧消费者直接返回 12，也不能将 12 截成 8 隐藏真实状态。新增 V2 DTO 与明确的消费者版本能力，相关消费者升级后才启用 V2。

迁移全部追加，编号在实施时按最新 develop 分配，不修改 0179、0181、0186、0188 或 0191：

1. 增加单元、受信根任务映射、公平调度记录、策略历史、控制版本、必要索引及 owner 复合外键。
2. 为 holder/journal/activity 增加兼容的单元绑定，严格区分 V1 job token 和 V2 unit token；全部模型/evidence/检查点/交付写入函数同步校验。按运行身份提供最小权限并用实际受限角色测试，不能只在数据库 owner 下通过。
3. 保留批次成员唯一性、已有输入和计划 hash。旧 `max_parallel` 及分组值仍可解析/重放，运行时不再把它作为容量来源；子 run 按分页需求物化，有限物化窗口不能决定整个批次的执行上限或隐藏扩容需求。
4. 先发布可同时识别 V1/V2 的组件，V2 领取开关保持关闭；核对主站、每个现存执行节点和未来启动模板的能力/源码版本。
5. 启用时停止新的 V1 领取并让已有会话自然排空，任务提交继续排队；确认活跃租约及 holder 已安全交接、未知结果已有隔离记录后，在一个事务中提升 scheduler epoch、启用 V2。数据库拒绝旧消费者重新领单；不得仅靠环境变量让新旧调度器各自分配一遍资源。
6. 已完成旧阶段继续复用；待核调用维持隔离。暂停的旧任务只有在输入、调用及检查点映射可证且无活跃旧执行时迁入 V2；否则保留显式兼容路径，不盲目整任务重跑。

回退使用可读 V2 记录的上一兼容版本：关闭新 grant，保留队列、结果和账务，等待/核对现存进程后恢复领取。不删除单元表或强清 holder 来“回滚”。若旧 binary 无法读 V2，不能在仍有 V2 活跃工作时直接回退到它。生产切换仍由用户指定的发布 chat 在集成验收后执行。
