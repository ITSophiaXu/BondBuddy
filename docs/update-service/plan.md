# BondBuddy 募集书更新（新版）实现方案

> 本文档直接交给 Codex 执行。请先通读全文，再按「第 12 节 里程碑与 PR 拆分」逐个 PR 实现。每个 PR 都要能独立编译、测试通过。

---

## 0. 背景与目标

### 0.1 现状问题

现有「募集书更新」任务把整份募集书交给 Codex CLI 智能体，在一次逻辑调用里自由完成。智能体会自己读文件、自己读扫描页图片、自己决定下一步。由此带来三个问题：

- 扫描版审计报告的图片很快占满单个上下文的图片额度（512 KB），触发上下文切换。每次切换都要保存和恢复全部工作文件，新上下文还要重新熟悉进度，反复空转，最后耗尽固定时间窗口、交付失败。
- DeepSeek 的 Responses 接口不保存会话状态，每一轮请求都要重发全部历史。token 总量约等于请求次数乘以平均上下文长度。日志分析显示，88–93% 的累计上下文来自「读任务说明和知识库」和「智能体临时写脚本提取材料、自己跑 OCR」这两类动作。
- 进度不落盘，失败只能整体重来。

### 0.2 目标

- 新建一套独立服务，只实现「募集书更新」，不依赖「项目」概念。用户从主站点击「募集书更新」后跳转到新站，免登录直接使用。
- 用**固定流水线**代替自由智能体。模型只在少数明确的判断点上做小调用，输入输出都是结构化 JSON。
- 与现有版本相比，在质量不下降的前提下：
  - 单任务 token 消耗不超过现有版本的 20%；
  - 单任务端到端耗时 P90 不超过 30 分钟（不含用户核对的等待时间）；
  - 任何一步失败，只重做该步，不从头再来。

### 0.3 第一份真实样本（任丘建投，2025 年 9 月末一期更新）的发现

样本：历史募集书（2025 年第二期，报告期截至 2025 年 6 月末）、2025 年三季度财务报表（XLSX）、附注（由 PDF 转成的 DOCX）、人工最终稿（2026 年第一期，报告期截至 2025 年 9 月末）。对比历史稿和最终稿的结果：

- 改动规模：2,313 段中有 752 段有变化，134 张表中有 98 张有变化，最终稿表格里共有 808 个新数值。
- **最终稿表格里的新数值，只有 62% 能在输入的报表和附注中直接找到。** 其余主要是两类：一类是由报表数计算出的比率、占比、毛利率，程序可以算出；另一类来自输入里没有的材料，例如前五名客户和供应商、工程项目明细、担保人财务数据、银行授信、融资租赁明细。
- **改动并不都来自财务数据。** 这次同时换了期次（2025 年第二期改为 2026 年第一期）、发行规模（10 亿元改为 7 亿元）、品种（两个品种改为单一 5 年期）、受托管理人和中介机构信息，第十三节「债券受托管理人」有 182 段改动，第十四、十五节也有较多改动。这部分必须由用户提供「本期发行要素」，模型无法推断。
- 第四节有大量结构性改写：删除了失信核查等段落，新增了控股股东介绍，重写了化工业务模式。这类改动依赖尽调材料，不在财务报表里。
- 输入工作簿里有过期和无关的工作表（2022 年口径的附注底稿，以及另一家公司的债券明细），真正有用的是 01–04 号报表工作表。程序必须识别并忽略这些噪声。
- 一期更新时，表格的列结构不变（仍是「最近两年及一期」），只替换最近一期这一列，并把标题和正文里的「2025 年 6 月末」或「2025 年 1–6 月」改为「2025 年 9 月末」或「2025 年 1–9 月」。
- 目录页码和表格编号也会随增删变化，需要在生成 Word 后统一重新编号、更新目录。

据此对范围做如下调整：

1. 改动分为三类，分别处理并分别验收：
   - **A 类，财务数据驱动：** 报表、结构分析表、指标表、明细表，以及引用这些数字的正文。由程序和模型自动完成，按第 13 节的标准验收。
   - **B 类，发行要素驱动：** 期次、规模、期限、品种、中介机构、受托管理人。由新增的「本期发行要素」表单提供数据，程序和模型据此改写，按表单逐项核对验收。
   - **C 类，需要额外材料：** 客户和供应商、项目明细、担保人数据、业务模式变化、合规核查。第一期不自动改写，在「更新说明」中逐项列为待办，标明需要什么材料、在哪一节。用户上传了对应材料的，第二期再支持。
2. 财务输入同时支持三种形式，优先级依次为：报表 XLSX、附注 DOCX（包括由 PDF 转换来的）、PDF（文字版或扫描件）。
3. 离线评测与人工最终稿比对时，按 A、B、C 三类分别统计，C 类只检查有没有列进待办。

### 0.3b 第二份真实样本（沧州交通，定向债务融资工具，跨三年补更）的发现

样本：历史募集书为 2021 年度第一期（报告期为 2019–2020 年）；人工最终稿为 2024 年度第一期（报告期为 2021 年、2022 年及 2023 年 1–6 月）。财务材料为 4 份 PDF，共 205 页，**全部是扫描件，没有文字层**。

- 属于不同的募集书类型：银行间定向债务融资工具。章节体系（第一章至第十六章）和公司债不同，并且 2021 年版与 2024 年版的披露格式本身也有变化。**程序不能假设固定的章节编号或标题。**
- 改动规模接近重写：最终稿 1,849 段中，只有 554 段未变，841 段是新写或大幅改写；表格从 102 张增加到 145 张。大幅改写集中在「公司基本情况」（383 段）和「发行人主要财务状况」（317 段）两章。
- 表格的列结构发生变化：从两期（2020 年、2019 年）变为三期（2023 年 1–6 月、2022 年、2021 年），没有任何一期保留下来。因此：
  - 「旧数复核」不能用旧募集书里的数（没有重叠期间），改为用审计报告里的「上年数」交叉核对：2022 年报告中的 2021 年数，应与 2021 年报告中的年末数一致。映射的正确性则通过「科目名称与数据集科目对应」加上表内勾稽来验证。
  - 表格不再逐格替换，而是**按新报告期重建**：保留原表的行结构和样式，重新生成列，程序填数。报表中新出现的重要科目要增行，所有期间都为 0 或空的行按原稿惯例删除或保留。
- 用户上传的材料多于本次需要：2024 年半年报在最终稿里没有使用。**任务必须先确定目标报告期**（从文件中识别候选项，由用户确认），再选择对应的材料；未使用的文件在「更新说明」里列出。
- 2023 年半年报只有 4 页报表，没有附注。最新一期的明细表（如应收前五名、借款明细）无法从输入中得到，归入 C 类待办。
- 205 页扫描件全部需要 OCR。这是验证 S3 识别和 S4 人工核对的关键样本：在 4 核机器上，OCR 耗时必须纳入第 13 节的耗时指标；只对定位到的报表页和附注页做表格级 OCR，审计报告正文和声明页只做快速识别用于分类。

据此补充：

1. S5 报告期规划支持三种情形：只替换最近一期（一期更新）、滚动一年（年度更新）、全部期间替换且列数可变（跨多年补更）。
2. S6 表格更新分两种模式：有重叠期间时用「旧数复核」；没有重叠期间时用「报告间上年数交叉核对 + 表内勾稽 + 科目对应」。
3. 任务类型先支持一期更新（样本一），再支持跨多年补更（样本二）。后者的叙述章节改写量远大于前者，按章节单元处理，token 预算单独设定。

### 0.3c 第三份真实样本（中捷农场，跨品种迁移）的发现

样本：历史募集书为 2024 年度第一期定向债务融资工具（银行间，报告期 2022–2023 年）；人工最终稿为 2026 年面向专业投资者非公开发行公司债券（交易所，报告期 2024 年、2025 年及 2026 年 1–3 月）。财务材料为 2025 年审计报告 PDF（83 页，没有文字层），以及 2026 年一季度报表 XLSX 和附注 DOCX。

- **这是跨品种迁移，不是更新。** 最终稿 1,458 段中，只有 83 段是沿用原文、仅数字变化，136 段小改，307 段中改，779 段是新写。
- 新写部分主要是公司债的标准条款：债券持有人会议规则、受托管理协议、投资者保护机制、信息披露安排、税项。这些内容不来自历史募集书，而来自目标品种的标准模板（样本一就是同品种的公司债）。
- 发行人特有的内容，如「发行人基本情况」的业务和治理部分，大多从历史募集书搬过来并改写；财务章节按新报告期重写。

据此定位：

1. **第一期只做同品种更新**（样本一、样本二）。跨品种迁移（样本三）对应价格表里单独的「迁移」任务，放在第二期。
2. 第二期迁移的做法：以目标品种的标准模板为骨架，标准条款直接由模板加发行要素生成；发行人特有的章节从历史募集书按章节对应搬迁并改写；财务章节沿用更新任务的 S3–S8。需要维护一个「品种模板库」（公司债、企业债、定向工具、中期票据等）以及章节对应表。
3. 样本三的财务材料仍可用于第一期验证 S3：一份无文字层的审计报告，加一份 XLSX 报表和 DOCX 附注。

### 0.4 非目标（第一期不做）

- 新项目编制、底稿、诚信核查、问答等其他任务类型。
- 跨品种迁移（如定向工具改为公司债），放在第二期，见 0.3c。
- 项目管理、协作、版本历史。
- 正式收费（第一期免费内测，见第 9 节）。

## 1. 设计原则（Codex 必须遵守）

1. **智能体运行时用 DeepSeek Harness，不自己写，也不用 Codex CLI。** 智能体循环、会话持久化、上下文压缩、重试和会话日志全部交给 DeepSeek Harness（下称 DSH）的 Python SDK，不要手写多轮对话循环。
   - **模型不挂通用 shell、文件编辑器和读图工具**，只挂本方案定义的业务工具（见第 7 节）。所有文件解析、OCR、取数、写 Word 都由程序完成，模型拿不到原始文件。
   - 只需单次结构化回答的判断（分类、映射、批量确认），也通过 DSH 以单轮会话执行，保证日志和用量统计口径统一。
2. **模型只做判断，不搬数字。** 模型输出「映射」「是否需要修改」「改写后的段落」这类结构化结果。财务数字一律由程序从财务数据集写入。
3. **每次模型调用都小而有界。** 单次输入不超过 40K token，最多 3 轮修正。超限即为设计错误，应继续拆分，不允许加大上限。
4. **每一步幂等、可续跑。** 每个阶段的产物以内容哈希为键落库或落盘。重跑时已完成的阶段直接复用。
5. **校验不通过不交付。** 每个阶段都有机器校验，不通过时退回到更小的范围重试，或标记给人工核对。不允许静默跳过。
6. **复用现有确定性模块，只重写编排层。** 现有仓库里生成修订版 Word、清洁版 Word 和质量检查的代码已经踩过很多坑，优先抽成共享包直接复用，不要重写（见第 8 节）。

## 2. 总体架构

```
主站 (现有 BondBuddy)                 新站 bb-update (新服务器 / 独立容器)
┌───────────────────┐  短期登录凭证   ┌──────────────────────────────────┐
│ 「募集书更新」入口 │ ─────────────▶ │ web   上传 / 进度 / 核对 / 下载    │
│ 灰度开关(按用户)   │                │ api   任务、文件、登录、状态       │
└───────────────────┘                │ worker 流水线各阶段（队列驱动）    │
                                      │ agent-runner  DSH Python SDK + 业务工具 │
                                      │ postgres  任务与中间产物元数据     │
                                      │ 对象存储  原文件与中间产物         │
                                      └──────────────────────────────────┘
                                                   │
                                                   ▼
                                       DeepSeek 接口（只由 agent-runner 经 DSH 调用）
```

### 2.1 技术栈

与现有仓库保持一致，方便复用代码：

- TypeScript / Node.js，monorepo 结构：`apps/update-web`、`apps/update-api`、`apps/update-worker`、`packages/update-core`。
- PostgreSQL；队列用 PG 表加 `SELECT … FOR UPDATE SKIP LOCKED` 实现，不引入新中间件。
- 对象存储抽象成接口：本地磁盘和腾讯云 COS 两种实现，用环境变量切换。
- **agent-runner**：Python 容器，内置 `deepseek-harness-sdk`（锁定版本），通过内部 HTTP 接收 worker 下发的「智能体单元」（一个表格兜底、一个章节改写、一次批量确认），返回结构化结果和用量。worker 不直接调用 DeepSeek 接口。
- OCR 用 Python sidecar 容器，通过 HTTP 调用。引擎可插拔：先接 tesseract chi_sim（现有日志显示环境里已有），预留 PaddleOCR 接口。
- PDF 处理（同样放在 Python sidecar）：pdfplumber 提取文字层和表格，pypdfium2 渲染页面。
- DOCX 处理：复用现有仓库中的 DOCX 读写和修订痕迹模块。

### 2.2 部署

- 用 docker compose 部署 6 个服务：web、api、worker、agent-runner、ocr、postgres。
- 第一阶段可以先部署在现有的腾讯云 4 核 16G 机器上，用独立的 compose 项目名、端口和数据卷；验证通过后再迁到独立服务器。
- 这台机器同时运行旧版的执行节点，因此新服务必须设置资源上限，避免影响旧任务：

| 服务 | CPU 上限 | 内存上限 | 说明 |
|---|---|---|---|
| postgres | 0.5 | 1G | `shared_buffers=256MB` |
| api + web | 0.5 | 1G | 两个服务合计 |
| worker | 0.5 | 1G | 并发 1 个任务（`UPDATE_WORKER_CONCURRENCY=1`） |
| agent-runner | 0.5 | 1G | 同时最多 2 个 DSH 会话（`AGENT_CONCURRENCY=2`）；每个会话独立工作目录，结束即删除 |
| ocr | 1.5 | 3G | 并发 2 页（`OCR_CONCURRENCY=2`），300 DPI 页面渲染完立即释放 |
| 合计 | 3.5 | 7G | 至少给旧执行节点和系统留约 8G 内存 |

- 在 compose 中用 `deploy.resources.limits` 设置上述上限。OCR 采用逐页流式处理，不把整份 PDF 一次性渲染进内存。
- 磁盘：新服务的数据卷单独挂载目录，并在管理页显示占用。
- 上线前在这台机器上跑一次压测：新服务处理一个 70 页扫描报告的同时，旧执行节点跑一个任务，观察两边的内存峰值和耗时，确认没有互相挤占后再开放灰度。
- 通过子域名访问，例如 `update.<主域名>`，由 Nginx 反向代理并配置 HTTPS。

## 3. 用户流程

1. 用户在主站点击「募集书更新」。如果该用户在灰度名单内，主站签发短期登录凭证并跳转到新站；否则走旧流程。
2. 新站「新建任务」页：
   - 选择更新类型：年度更新、一期更新（第一期只做这两种，其余灰显）；
   - 上传历史募集书（**必须是 DOCX**，沿用现有规则）；
   - 上传最新一期财务报表和附注：XLSX、DOCX 或 PDF 均可，PDF 可以是扫描件；以及需要的往期报告；
   - 填写「本期发行要素」表单：债券全称和期次、发行规模、期限和品种、增信方式、主承销商、受托管理人、律师事务所、会计师事务所、评级机构（如有）、募集资金用途。已有字段从历史募集书中预填，用户只改变化的部分；
   - 可选：填写或确认发行人名称、目标报告期截止日。
3. 系统识别材料，生成财务数据集，并做勾稽核对。
4. 如果存在勾稽不通过或低置信度的格子，进入「核对」页：左边显示原 PDF 页面截图，右边显示识别值，用户只需处理被标记的格子。没有被标记的格子时，自动跳过这一步。
5. 系统完成更新，进度页按阶段显示进度。
6. 用户下载修订版 Word、清洁版 Word，以及一份「更新说明」：列出改了哪里、数字的来源页码，以及需要人工关注的位置。
7. 「我的任务」页列出历史任务，可以下载结果或重新运行。

## 4. 数据模型（PostgreSQL）

表名统一使用前缀 `bu_`。

```sql
bu_users(id uuid pk, main_user_id text unique, email text, display_name text, created_at)
bu_sessions(id uuid pk, user_id uuid, expires_at, created_at)

bu_tasks(
  id uuid pk, user_id uuid, kind text check (kind in ('annual','quarter')),
  state text check (state in ('draft','queued','running','awaiting_review','succeeded','failed','cancelled')),
  current_stage text, target_period_end date, issuer_name text,
  error_code text, error_detail jsonb,
  token_in bigint default 0, token_out bigint default 0, token_cached bigint default 0,
  created_at, started_at, finished_at
)

bu_files(id uuid pk, task_id uuid, role text, -- 'prospectus' | 'audit_report' | 'output_tracked' | 'output_clean' | 'output_notes'
         filename text, sha256 text, size bigint, storage_key text, created_at)

bu_stage_runs(id uuid pk, task_id uuid, stage text, input_hash text, state text,
              attempt int, started_at, finished_at, error_code text, metrics jsonb,
              unique(task_id, stage, input_hash))

bu_artifacts(id uuid pk, task_id uuid, stage text, kind text, content_hash text,
             storage_key text, json jsonb, created_at)   -- 小产物直接存 json，大产物存对象存储

bu_model_calls(id uuid pk, task_id uuid, stage text, unit_key text, -- 例如表格 id、章节 id
               attempt int, model text, prompt_hash text,
               input_tokens int, output_tokens int, cached_tokens int,
               latency_ms int, status text, error_code text, created_at)

bu_jobs(id uuid pk, task_id uuid, stage text, run_after timestamptz,
        locked_by text, locked_until timestamptz, attempts int, state text)

bu_review_items(id uuid pk, task_id uuid, kind text, ref jsonb, source_page int,
                original_value text, proposed_value text, resolved_value text,
                state text, resolved_by uuid, resolved_at)
```

OCR 结果另建全局缓存表 `bu_ocr_cache`，以「文件 sha256 + 页码 + 引擎版本」为键。同一份 PDF 在不同任务里不重复识别。

## 5. 流水线阶段

每个阶段需要明确五项内容：输入、处理、模型使用、产物、校验。worker 按顺序领取阶段任务。每个阶段在 `bu_stage_runs` 里记录结果，用 `input_hash` 判断能否复用。

### S1 文件接收

- 计算 sha256，检查格式：募集书必须是 DOCX；财务材料可以是 XLSX、DOCX 或 PDF；检查大小和页数上限。
- 产物：`bu_files` 记录。
- 校验：文件能打开；DOCX 不加密，PDF 不加密。

### S2 募集书解析

- 把 DOCX 解析成**带稳定 ID 的结构树**：章、节、段落、表格、单元格。每个节点记录在原文档中的路径（XML 定位）和纯文本。
- 识别所有表格，产出表格清单：表格 ID、所在章节标题、表头行、首列行名、单元格数值、合并单元格信息。
- 从全文抽取报告期表述的候选位置：用正则匹配年份、「近三年」「最近一期」「报告期」「X 年 1-X 月」「截至 X 年 X 月 X 日」等。
- **不使用模型。**
- 产物：`prospectus_tree.json`、`tables.json`、`period_mentions.json`。
- 校验：结构树能无损还原出原文纯文本（逐段比对）。

### S3 财务报告识别

0. **XLSX 和 DOCX 输入优先。** XLSX：逐个工作表识别类型（合并或母公司的资产负债表、利润表、现金流量表、所有者权益变动表，或附注明细），读取编制单位、报表日期和金额单位；编制单位或日期与本次任务不符的工作表直接忽略，并写入「更新说明」。DOCX 附注：按「（一）货币资金」这类标题切分科目，读取附注表格。只有 XLSX 和 DOCX 都缺失的部分，才走下面的 PDF 流程。
1. 逐页判断有没有可用的文字层：有就用 pdfplumber 提取文字和表格；没有或文字层是乱码，就渲染成 300 DPI 图片做 OCR（走缓存）。
2. 定位三大报表页和主要附注页：先按关键词规则匹配，规则无法判断时，把各页文字摘要交给模型做一次分类调用（只给文字，不给图片）。
3. 把报表行解析成标准化记录：

```json
{ "statement": "balance_sheet|income|cash_flow|indicator",
  "scope": "consolidated|parent",
  "item_key": "accounts_receivable",
  "label_raw": "应收账款",
  "period_end": "2025-12-31",
  "period_type": "point|ytd|fy",
  "value": 123456789.12, "unit": "yuan",
  "source": { "file_id": "...", "page": 37, "bbox": [x0, y0, x1, y1] },
  "confidence": 0.97 }
```

4. 科目标准化：维护一张 `item_key` 科目字典，覆盖企业会计准则的报表科目和常见别名。字典匹配不上的行名，批量交给模型归类，一次调用处理全部未匹配项。模型只能从字典里选，或者返回「无法归类」。

- 产物：`financial_dataset.json`，包含所有报表的全部期间，并带来源页码。
- 校验（勾稽规则，见附录 A）：资产合计 = 负债合计 + 所有者权益合计；各小计等于明细之和；期末现金与资产负债表货币资金核对；本期报表的「上年数」与上期报告的「本年数」一致（如果两份报告都上传了）。不通过的格子写入 `bu_review_items`。

### S4 人工核对（有标记项时才进入）

- 任务状态变为 `awaiting_review`，前端展示被标记的格子和原页截图（截图由程序裁切 bbox 区域）。
- 用户修正后重新跑勾稽检查，全部通过（或用户确认「已核实，按此值使用」）后继续。
- 这段等待时间不计入任务执行时间。

### S5 报告期规划

- 根据更新类型、旧募集书现有报告期和新报告截止日，**由程序**计算新旧报告期对应关系，例如旧报告期 2022–2024 年，新报告期 2023–2025 年；一期更新则加上「2026 年 1–6 月」。
- 产出 `period_plan.json`：保留哪些期、删掉哪些期、新增哪些期，以及每一期在报表里的列标题写法。
- **不使用模型**，规则写在代码里，并配单元测试。

### S6 表格更新：模型出映射，程序填数

对 `tables.json` 中的每张表：

1. **相关性筛选（程序）：** 表格包含年份或财务科目关键词才进入后续步骤，其余表格保持原样。
2. **映射调用（模型，每张表一次）。** 输入只包含：表格所在章节标题、表头行、首列行名、合并单元格结构、`period_plan`、科目字典里的候选科目。**不给数值。** 输出：

```json
{ "table_id": "t_042",
  "action": "update|keep|manual",
  "unit": "wan_yuan",
  "columns": [ { "col": 2, "period_end": "2024-12-31", "period_type": "fy" }, ... ],
  "rows": [ { "row": 5, "item_key": "accounts_receivable", "kind": "value" },
            { "row": 6, "item_key": null, "kind": "ratio", "formula": "row5/row20" },
            { "row": 12, "kind": "subtotal_of", "rows": [5, 6, 7] },
            { "row": 13, "kind": "keep_text" } ],
  "notes": "..." }
```

3. **旧数复核（程序，关键校验）。** 对映射中仍然保留的旧期间，用映射去数据集取数，按 `unit` 换算后与旧募集书里的原值逐格比对，容差 ±1 个最小显示单位。不一致比例超过 5%，或者合计行不一致，就判定映射有误：带着不一致的格子重试映射一次，仍不通过就把整张表标为 `manual`。
4. **填数（程序）。** 按 `period_plan` 做列滚动（删列、加列、改列标题）；新期间的值从数据集取出，按表格原有格式写入（单位、小数位、千分位、负数写法）；比率类按公式计算。
5. **兜底：** 对 `manual` 表做一次小上下文调用，只给这张表加上对应的数据切片，由模型输出逐格编辑操作，再经程序做勾稽和与数据集的比对。仍不通过的，原样保留并写进「更新说明」，提示人工处理。

- 产物：每张表一组编辑操作（格式见第 6 节）。
- 指标：记录映射一次通过率、兜底比例、人工比例，写入 `bu_stage_runs.metrics`。

### S7 报告期文字替换

1. 程序根据 `period_mentions.json` 和 `period_plan` 生成替换建议，例如「2022 年度、2023 年度和 2024 年度」改为「2023 年度、2024 年度和 2025 年度」。
2. **一次批量调用**（太多时按 50 条一批）：每条给出前后各 100 字和建议替换值，模型只回答「采纳 / 不改 / 改为其他写法（给出文本）」。用于识别「2022 年发行的债券」这类描述历史事实、不应修改的年份。
- 产物：编辑操作。
- 校验：模型给出的「其他写法」必须只包含 `period_plan` 里的期间；替换后不能残留应被删除的期间（专门做一次全文扫描）。

### S8 叙述章节更新

1. **找出需要更新的章节（程序 + 模型）。** 程序先找出包含报告期数字或财务科目的段落，按小节分组。模型对每个小节判断类型：财务分析、经营情况、债务情况、无需更新等。这一步只给小节标题和首句，一次调用处理全部小节。
2. **逐节改写（模型，每节一个 DSH 会话，最多 3 轮修正）。** 会话 id 为 `{task_id}:S8:{section_id}`，失败时用同一 id 续跑。模型通过业务工具按需取数据，提交前必须调用 `validate_edits`。初始输入：
   - 本节原文；
   - 本节相关科目在新旧各期的数据切片（由程序计算好增减额和增减比例）；
   - 全局事实表：发行人名称、报告期、单位、已完成章节的关键结论摘要，不超过 2K token；
   - 写作规则：只附与本节类型相关的几条，不附整本知识库。
3. 输出采用「段落级替换」格式：每条包含原段落 ID 和新文本。新文本里的数字一律写成占位符，例如 `{{accounts_receivable@2025-12-31|wan_yuan|2}}`、`{{yoy:revenue@2025}}`，由程序渲染成数字。只有程序无法计算的数字才允许直接写，并且必须附上来源说明。
4. 校验：
   - 占位符都能解析；
   - 直接写的数字必须能在数据集或原文中找到；
   - 不允许删除原文中未涉及报告期的段落；
   - 新文本中不能出现旧报告期；
   - 「增加 / 减少」这类方向词必须与数据的正负一致（程序检查）。
   - 不通过时带着错误清单重试，最多 3 轮；仍不通过就保留原文，并在「更新说明」里标出。
- 每一节完成就落库。失败只重做这一节。

### S9 生成 Word

- 把 S6–S8 的全部编辑操作按文档位置排序，检查有没有冲突（同一节点被多处修改）。
- 复用现有模块生成：
  - 修订版 DOCX：所有修改以修订痕迹呈现，作者显示为「BondBuddy」；
  - 清洁版 DOCX：接受全部修订后的版本。
- 生成「更新说明」（DOCX 或 Markdown 均可）：逐条列出修改位置、修改前后的内容、数字来源页码、兜底和人工待办项。

### S10 质量检查

- 复用现有质量检查模块。另外增加以下检查：
  - 全文没有残留应被删除的旧期间；
  - 所有表格在更新后勾稽成立；
  - 清洁版与「原文 + 编辑操作」一致；
  - 文档能被 Word / LibreOffice 正常打开（用 `soffice --headless` 转换一次 PDF 来验证）。
- 不通过时任务失败，失败原因写清楚；不交付半成品。

## 6. 编辑操作格式（统一中间表示）

```ts
type EditOp =
  | { op: 'replace_paragraph'; node_id: string; new_text: string; reason: string; sources: Source[] }
  | { op: 'replace_text'; node_id: string; start: number; end: number; new_text: string; reason: string }
  | { op: 'set_cell'; table_id: string; row: number; col: number; new_text: string; sources: Source[] }
  | { op: 'insert_column'; table_id: string; after_col: number; header: string[] }
  | { op: 'delete_column'; table_id: string; col: number }
  | { op: 'keep'; node_id: string; reason: string };

type Source = { file_id: string; page: number; item_key?: string; period_end?: string };
```

所有阶段只产出 `EditOp[]`，只有 S9 会修改 DOCX。如果现有仓库已经有「操作日志」格式，就写一个适配层转换过去，不要另造一套写入逻辑。

## 7. 模型调用：基于 DeepSeek Harness

### 7.1 总体约定

- 用 DeepSeek Harness 的 Python SDK（`pip install deepseek-harness-sdk`），以 `sdk-minimal` 配置为基础，通过补丁文件定制。**DSH 已经提供的能力不得重写**：智能体循环、会话持久化与续跑、自动上下文压缩、图片移出、会话 JSONL 日志、流式调用与重试。
- worker 把每个「智能体单元」发给 agent-runner。一个单元对应一个 DSH 会话：

| 单元 | 会话 id | 轮次上限 | 输出 |
|---|---|---|---|
| 页面分类（S3） | `{task}:S3:classify` | 1 | JSON |
| 科目归类（S3） | `{task}:S3:items` | 1 | JSON |
| 表格映射（S6） | `{task}:S6:map:{table_id}` | 2 | JSON |
| 表格兜底（S6） | `{task}:S6:fix:{table_id}` | 3 | 经工具提交的 EditOp |
| 报告期确认（S7） | `{task}:S7:{batch}` | 1 | JSON |
| 章节类型判断（S8） | `{task}:S8:classify` | 1 | JSON |
| 章节改写（S8） | `{task}:S8:{section_id}` | 3 | 经工具提交的 EditOp |

- 单轮 JSON 单元：在提示词中给出 JSON Schema，agent-runner 用 pydantic 校验结果。校验失败时在同一会话里追加一条错误说明让模型重答，计入轮数。
- 每个单元的初始输入不超过 40K token。超过时 agent-runner 直接返回 `UNIT_TOO_LARGE`，由 worker 拆小后重发，**不允许截断内容了事**。

### 7.2 业务工具（以 DSH 工具或插件形式注册）

模型只能使用下面这些工具。工具全部只读，或只写入 agent-runner 的暂存区，不接触原始文件和数据库：

| 工具 | 作用 |
|---|---|
| `get_section(node_id)` | 返回某节原文（段落 ID + 文本） |
| `get_table(table_id)` | 返回表格结构和当前值 |
| `get_financials(item_keys, periods)` | 从财务数据集取数，含增减额、增减率和来源页码 |
| `get_facts()` | 返回全局事实表（发行人、报告期、单位、已完成章节摘要） |
| `get_rules(section_type)` | 返回该类章节的写作规则（只返回相关条目） |
| `validate_edits(edits)` | 按第 5 节的校验规则检查，返回错误清单 |
| `submit_edits(edits)` | 提交 EditOp；必须在 `validate_edits` 通过后调用，否则拒绝 |

### 7.3 硬性要求（Codex 必须遵守，PR 审查逐条核对）

1. **锁定 DSH 版本。** 在依赖文件中写死精确版本号。DSH 目前处于开发者预览阶段，会有不兼容改动，升级必须单独开 PR，并附评测报告前后对比。
2. **关闭会话日志上传。** DSH 默认会把会话日志随请求上传给 DeepSeek，必须在配置补丁里设置 `session-log-deepseek: enabled: false`，并在启动自检中确认已关闭；自检不通过，agent-runner 拒绝启动。
3. **不挂通用工具。** 配置中移除 `sdk-minimal` 默认带的持久 bash、`read_image` 和 `working_directory`，也不挂 `str_replace_editor`，只挂 7.2 节的业务工具。启动自检要列出模型可见的工具清单，出现清单以外的工具就拒绝启动。
4. **隔离运行。** `sdk-minimal` 默认是完全访问权限。agent-runner 容器以非 root 用户运行，只读根文件系统；每个会话使用独立的临时工作目录和 `dsh_home`，会话结束后删除工作目录，会话日志转存到对象存储后再删除。
5. **不读 `~/.dsh`。** 所有配置都通过显式传入的 `dsh_home` 和补丁文件提供，便于复现。
6. **用量入库。** 从 DSH 会话日志中提取每次模型请求的输入、输出和缓存 token，包括压缩摘要请求，写入 `bu_model_calls`（`stage` 和 `unit_key` 取自会话 id），并累加到 `bu_tasks.token_*`。
7. **压缩是兜底，不是常态。** 记录每个会话的压缩次数。评测中压缩次数大于 0 的单元要在报告中列出，并通过拆小单元来消除。
8. **前缀缓存。** 系统提示词和工具定义保持固定、放在最前面，以利用 DeepSeek 的前缀缓存。

### 7.4 预算与配置

- 单任务 token 预算可配置，默认取旧版同类任务中位数的 25%。超出预算后任务暂停并告警，**不静默继续**。
- 提示词模板放在 `packages/update-core/prompts/`，带版本号，`prompt_hash` 入库。
- 配置项：`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DSH_MODEL`、`DSH_VERSION`、`AGENT_CONCURRENCY`，以及按单元类型覆盖模型的配置。密钥只放在 agent-runner 的环境变量里，不进代码仓库，也不传给 worker。

## 9. 登录与积分

### 9.1 登录（共享账户）

- 主站新增接口 `POST /api/sso/update-ticket`：要求已登录，签发 5 分钟有效、只能使用一次的 JWT。签名用 RS256，主站持有私钥，新站持有公钥。凭证内容：`sub`（主站用户 id）、`email`、`name`、`jti`、`exp`。
- 主站入口按钮跳转到 `https://update.<域名>/sso?ticket=…`。
- 新站校验签名、有效期以及 `jti` 是否已使用，然后创建或更新 `bu_users`，签发自己的会话 Cookie（HttpOnly、Secure、SameSite=Lax）。
- 两边**不共享数据库**。
- 灰度：在主站加用户级开关 `update_service_enabled`，未开启的用户仍走旧流程。

### 9.2 积分

- **第一期免费内测**，新站不扣费，但完整记录 token 和耗时，供后续定价参考。
- 第二期（另开 PR，本期不做）由新站调用主站接口完成计费，账只记在主站一处，新站不保存余额：
  - 任务开始时预扣：`POST /api/billing/reserve`，参数 `external_task_id`、`kind`；
  - 成功交付时结算：`POST /api/billing/settle`；
  - 任务失败时释放：`POST /api/billing/release`。

## 11. 离线评测工具（M0 先做）

在 `apps/update-worker` 中提供命令行入口：

```
pnpm update:eval --samples ./samples --out ./eval-out [--stages S2,S3,S5,S6]
```

- `samples/` 下每个子目录是一个真实任务：历史募集书、审计报告，以及可选的人工最终稿 `expected.docx`。
- 输出 `eval-out/report.md`，内容包括：
  - S3：识别出的科目数，勾稽通过率，标记格子数；
  - S6：表格数，映射一次通过率，兜底比例，人工比例，旧数复核不一致的明细；
  - S7 和 S8：修改条数，校验失败数；
  - token 合计和分阶段 token，耗时；
  - 如果有 `expected.docx`：逐表、逐段与人工稿比对，统计数字差异。
- **M1 的验收门槛**：在 10 个以上真实样本中，三大报表和主要指标表的映射一次通过率 ≥ 90%，旧数复核不一致率 ≤ 1%。达不到门槛时先调整科目字典和提示词，不进入 M2。

## 13. 最终验收标准

在不少于 20 个真实任务上，与旧版本对比：

1. **token：** 新版中位数不超过旧版中位数的 20%。
2. **耗时：** P90 ≤ 30 分钟，不含人工核对等待时间。
3. **成功率：** ≥ 95%，失败原因可读且可重试。
4. **数字准确：** 与人工最终稿相比，表格数字的差异数不多于旧版；所有修改过的数字都能追溯到报告页码。
5. **完整性：** 应更新的章节和表格没有遗漏，旧报告期没有残留。
6. **质量检查：** 全部通过。
7. **盲审：** 内部审阅人不知道哪份是新版，对新版的评价不低于旧版。

## 附录 A：勾稽规则（第一版，后续可扩充）

- 资产总计 = 负债合计 + 所有者权益合计（合并报表和母公司报表分别核对）。
- 流动资产合计 = 各流动资产项目之和；非流动资产、流动负债、非流动负债同理。
- 归属于母公司所有者权益 + 少数股东权益 = 所有者权益合计。
- 营业总收入、营业总成本、营业利润、利润总额、净利润之间的加减关系成立。
- 现金流量表期末现金及现金等价物余额 = 期初余额 + 现金净增加额。
- 同一科目在本期报告中的「上期数」与上期报告中的「本期数」一致（两份报告都上传时检查；不一致可能是追溯调整，只标记，不阻断）。
- 容差：合计类为 ±1 个最小显示单位。

## 附录 B：Codex 工作约定

- 每个 PR 只做一个里程碑项，改动超过约 1,500 行时继续拆分。
- 不提交任何密钥、客户文件或真实样本；样本只放在本地 `samples/`，并加入 `.gitignore`。
- 每个阶段都要有单元测试；S3、S6、S8 的提示词改动要附带评测报告前后的对比。
- 遇到设计里没写清楚的地方，在 PR 描述里列出假设，不自行扩大范围。
- 不得在新服务中调用 Codex CLI，也不得手写多轮对话循环来替代 DSH。发现 DSH 缺少某项能力时，先在 PR 描述里说明，再决定是写 DSH 插件还是另行处理。
