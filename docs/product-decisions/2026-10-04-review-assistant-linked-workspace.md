# M3 修订：复核结果与项目助手组成同一个工作区

> 2026-10-04 后续决定：[当前动作与助手执行摘要](2026-10-04-review-agent-progress.md)，实施 #547。左侧使用紧凑当前动作，右侧助手回复区域更新同一任务的当前执行摘要及折叠已完成动作；不展示心跳、耗时、预计时间、任务/动作时间戳及百分比。下文要求可见开始/结束时间的条款仅保留审计语义，界面以此后续决定为准。

日期：2026-10-04。依据：产品负责人确认“澄川科技 · 募集书复核”这版设计，并要求项目助手在桌面右侧常驻；按钮是人与助手执行任务的快捷入口，募集书复核过程必须在助手中展示；对话提出的新要求经明确执行后，左侧复核结果必须同步反映。本决定修订 M3 产品需求和验收，不声明业务运行时已经完成。

## 决策与旧规则的覆盖

左侧是当前报告、材料和问题的操作区，右侧是同一项目的助手、执行过程和任务结果入口。两侧消费同一个持久化任务及成果关系，不能分别维护一套“按钮复核”和“聊天复核”流程。用户可以只点击按钮完成常规操作；这些真实执行仍在助手时间线形成任务卡，不要求先手写聊天指令。

本决定覆盖以下旧交互要求，旧版本仅作历史记录：

| 旧依据 | 被覆盖的规则 | 本次生效规则 |
|---|---|---|
| [2026-10-02 M3 范围](2026-10-02-m3-review-scope.md)第“页面与常规操作”“助手的五类场景”“联合验收”节 | 助手默认收起；任务启动、执行过程和结果仅在页面反馈，标准操作不进入助手 | 桌面助手常驻；真实执行投影到助手任务卡，和左侧结果关联；不伪造用户自然语言消息 |
| `product-prototype/docs/m3-review-workspace-design.md`旧版及 `delivery-plan/issues/M3-01.md` | 任务完成以 toast 和页面状态为主，助手只用于额外说明 | 助手承担任务发起后的持续反馈；左侧保留任务状态、结果及直接操作 |
| [2026-10-03 CLI 统一执行](2026-10-03-m3-cli-runtime.md)的交互不变及“无需助手的按钮闭环”表述 | 被解释为按钮流程与助手相互独立 | 无需输入聊天文本仍可完成按钮闭环，但任务必须进入同一助手时间线并关联成果 |

继续有效：明确执行、材料和输入快照、问题/报告来源、幂等、项目互斥、资源归属、真实证据、工作台版本记录、无收费，以及 Codex CLI 统一业务执行。自然语言发送、保存说明、上传文件或接受业务观点本身都不创建复核/修订任务。用户异议、补证、已修改不等于复核通过。

## 页面与原型基准

复核页仍只有“材料与要求”和“复核结果”两个标签。足以容纳两列的桌面尺寸，助手在右侧持续可见，不提供重复的顶部“项目助手”打开按钮，也不要求任务开始后另行打开助手。窄屏用一个可展开抽屉入口，任务发生后有可见的状态提示；助手是否展开不改变任务语义、上下文或消息。

当前设计基准为 `product-prototype/public/review-v2.html`、`review-v2.css`、`review-v2.js`，配套工作台为 `dashboard-v2.html/css/js`。2026-10-04 修订前原型 checkout 为 `19918c66500d5078781b553613d237da6b3e708c`；本轮修订源文件及快照须另行登记，不能将该旧 commit 冒充新交互基准。实现 PR 必须登记最终原型 commit/源文件 hash、实现 commit，并附同尺寸逐屏对照。

复核页不增加版本历史列表。工作台继续展示完整复核、差异复核、修订、停止及失败记录并进入准确成果。复核页和助手可以显示任务所需的源报告、输入或成果编号及“查看本轮结果”链接；这是当前任务的来源/去向，不是一套重复的版本管理。

标题使用实际项目名称。“澄川科技”及原型内文件、问题和回复属于 synthetic 示例，不成为真实项目默认数据。

## 同一任务的两种入口

### 快捷点击

用户在材料区点击“开始复核”，或在结果区确认具体范围后点击“重新核验”“执行修订”，就是明确执行。页面在点击前可查看任务类型、材料/要求、源稿/来源报告、输入版本和范围。既有配置已明确时，开始按钮本身可完成提交，不为形成聊天记录额外增加一次确认。

提交调用现有平台执行入口，锁定输入并返回真实 run。助手时间线创建/恢复对应任务卡，注明“从材料区开始复核”或“从问题 F-002 重新核验”等入口及关联对象。来源说明是系统任务记录，不写成用户曾发送“帮我复核这份募集书”。只有实际提交成功才显示“已提交”；提交失败或返回结果尚未确认时，显示真实状态并先核对任务，不凭客户端计时认定成功。

筛选、打开依据、打开说明、勾选候选项、预览范围和下载等浏览操作继续直接完成，不逐次制造消息或任务卡。任务卡记录有执行意义的持久化任务，实际用户消息保留为用户消息，真实 CLI 回复保留为助手回复，三种内容在显示和数据语义上区分。

### 对话要求

从问题进入讨论时，助手显示本次引用的 project、report、finding 和材料版本。用户可解释口径、提供异议或补充证据，也可要求重新复核。助手根据真实上下文给出可核对的提议，不凭“重核”“修改”等关键词直接执行。

复核提议至少展示：

- 任务类型：完整复核或差异复核；修订是另一个明确任务类型。
- 来源报告及引用问题，问题对应的原句/位置和关联检查对象。
- 将使用的源稿、固定材料版本、已保存要求，以及新增证据。
- 本轮拟重核的对象和关联影响范围、明确排除/保留的对象。
- 未覆盖部分将沿用哪个报告，材料不足或映射不清的限制。

“关注 F-002”不默认把完整复核缩为差异复核。“重新复核这份募集书”的范围不明确时，先展示完整/差异选择及各自影响。助手不能把差异结果描述成全稿重新通过。

用户可调整范围、补材料、暂存或取消提议。采纳使该提议成为确定的执行依据，但不自动启动任务；明确的“确认并开始重新核验”可以在一次操作中完成采纳和提交，文案必须表达这两件事。修订计划继续要求可核对的修改目标/排除项，空修改计划不能创建任务。

执行入口与快捷点击复用相同校验、项目锁、幂等、队列、受控 Codex CLI 和成果登记。助手不新建执行器，不通过普通聊天回复静默修改报告或 Word。任务卡保存提议/要求的来源绑定，成功提交后跳转或定位左侧相关问题，并展示“正在重新核验”的真实关联。

## 助手任务卡与真实状态

每个 run 在同一项目时间线有一张稳定任务卡。卡片随事件更新，不为每次轮询重复追加“开始”“进行中”消息。任务卡至少能回查任务类型、发起入口、确认的范围、输入/源报告、当前状态、真实开始/完成时间、失败/停止原因、成果或待处理原因。

| 阶段/状态 | 助手呈现 | 左侧呈现 |
|---|---|---|
| 正在提交，返回结果未确认 | 明确提交中/正在核对提交结果；不能承诺已经创建 run | 保留原材料或报告，阻止重复执行，允许核对恢复 |
| 已提交/排队 | 真实 run 的任务卡、任务类型、输入及范围 | 项目活动任务提示；相关旧结果仍可查看 |
| 执行中 | 宿主持久化的实际阶段/工具事件摘要，如读取材料、执行检查、汇总报告、登记成果 | 明确当前展示的来源报告；差异范围内对象标“正在重新核验” |
| 请求停止 | “正在停止”，直到服务端确认终态；停止请求可追溯 | 保留旧有效报告，不提前标为已停止或已完成 |
| 已停止 | 确认停止时间/原因和实际保留内容 | 恢复旧有效结果；被中断范围标本轮未完成，不写重核通过 |
| 失败/待处理 | 真实错误/待处理原因和可用的恢复操作，注明缺少的成果 | 保留旧有效报告，相关范围标未完成/待处理 |
| 完成且成果已登记 | 完成摘要、实际覆盖和未覆盖、报告/成果链接 | 当前跟随本轮的视图展示新报告及本轮结果；沿用项保留出处 |

阶段名和状态枚举以 `packages/contracts/` 的唯一公共定义为准。表中的中文是产品展示语义，不授权页面另造一套状态机。宿主没有产生某个细分阶段事件时，使用已有真实阶段/任务状态，不模拟精确进度、百分比、剩余时间或“检查全部条款”。

展示用户可理解的工作进度和工具结果摘要，不显示模型隐藏思考、原始 prompt、凭证或跨项目材料。CLI 实际回复或已核验工具事件可支持摘要；模型自述不能替代实际工具事件或任务终态。无需为显示“任务已完成”另调用模型。

任务时间线只消费服务端白名单的用户摘要和安全字段。原始工具输出、CLI 日志、prompt/推理及内部路径不能直接渲染；现有事件 DTO 仅移除 `channel` 不构成足够的输出过滤。事件生产/序列化须明确哪些字段可对归属用户展示，并验证未知字段不会透传。

复核助手流中断和业务任务中断分别呈现。刷新、关闭页面、网络短断或助手回复失败不会自行取消已提交的 run；重新连接先补读持久化任务/事件和成果关系，不靠重复执行恢复。

## 左右关联和新结果

右侧任务卡“查看本轮结果”进入准确 report，问题引用定位该报告的 finding，并使左侧能看见相应卡片/详情。左侧“讨论此项”带入准确报告、问题和材料引用，在助手中显示当前上下文。关联导航不能只高亮一个同名问题或静默使用最新报告。

同一项目的当前结果视图跟随刚明确启动的任务：开始时保留旧报告并标运行范围，完成时读取已登记的新报告，明确本轮类型和来源。用户正在回看历史报告时不强制替换；显示“本轮有新结果”及准确入口。加载新报告失败时保留旧报告及可重试提示，不能把旧结果的版本号改为新版本假装更新完成。

差异复核新报告须逐对象区分：

- **本轮已重新核验**：有真实本轮检查及结论；可进一步区分新增问题、结论更新、仍需处理、已核验解决或仍待证据。
- **沿用原报告**：不在本轮范围，保留来源 report、原时点和原结论，不计入本轮已检查覆盖。
- **本轮未完成/未覆盖**：在请求范围内但实际未执行、材料不足、映射歧义或中断，显示原因；不得归为已解决。

运行中标记是任务进度，不改写原报告。新报告形成后保存 lineage/来源关系及实际覆盖；不能由“新报告未返回旧 finding”推断旧问题已解决。只有本轮结论及有效证据明确支持，才能显示“已核验解决”。同一业务问题的稳定关系与报告内 finding 身份须可追溯，新增、移动或无法可靠映射的问题如实说明。

完整复核须声明完整请求范围和实际三维覆盖；沿用、未执行的维度不能算作本轮完整三维通过。结果数量变化、技术任务成功、Word 交付成功与专业结论分别呈现。

修订任务同样进入助手任务卡；确认的计划、实际处理清单和修订/清洁 Word 从同一卡片和左侧成果区可访问。修订后左侧显示“已修改，待复核”及实际处理记录，保留源报告；修订完成不自动启动差异/完整复核，也不把原问题标为已核验解决。

## 上下文、输入与并发

执行依据固定 owner/project、源稿、来源 report/finding、材料及解析/规则/技能版本、已保存要求/已采纳提议、任务类型与范围，并形成不可变输入版本/hash。助手会话上下文是讨论依据，不覆盖任务快照。执行中新增说明/材料进入下一版，明确生效轮次；不能改变正在运行的输入或偷偷追加检查范围。

未发送草稿与其 project/report/finding/material 引用一起保存。切换问题、标签或报告时保留原草稿及上下文，可明确选择继续原讨论或开始新引用，不把 F-001 草稿换绑 F-004。报告更新后旧草稿仍引用旧报告，需要新的提议时显式选择来源。助手抽屉收起、桌面/窄屏切换和刷新不能丢草稿或改变其绑定。

同项目复核、差异复核和修订共用一个活动任务互斥边界。左右入口、双标签页、连点和断线重试不能绕过服务端锁。相同执行意图复用 `execution_request_id` 返回同一 run；任务卡以持久 run 身份去重。不同输入或不同任务意图不能错误地合并成同一 run。

从两个入口并发发起冲突任务时，服务端返回现有活动任务，两个区域展示可核对的同一状态，不制造第二张“已提交”任务卡。新的提议可保存待执行，活动任务结束后仍须核对输入/来源是否过期；旧提议不能自动在新材料上执行。

停止/失败占用的任务和输入版本不复用。恢复先核对已持久化事件、CLI 调用尝试和成果，复用已完成调用；状态未知的供应商调用不能自动重发。事件流须有稳定身份/顺序和恢复游标或等价机制；乱序、重播和重复事件不能将终态退回“执行中”，也不能重复生成任务卡。

归属校验在所有读、保存、采纳、执行、恢复和下载路径继续生效。公共字段/状态/事件在 `packages/contracts/` 唯一定义；本文规定语义，具体契约新增与迁移由实施 Issue 精确定义并测试，不复制到页面和 worker。

## 架构和本轮范围

Codex CLI 继续是 M3 的业务理解、检查选择、解释、提议与修订决策执行入口。沿用受控 worker、固定 Skills 和有界工具。平台保留权限、队列、任务事件、输入/提示/成果版本、幂等、恢复、真实 usage 和私有存储；时间线是既有真实任务的展示/恢复契约，不是另一套 AI 或业务执行后端。

本轮代码审计得到以下实施落点，必须在后续实现任务中补齐，而非由页面模拟：

- 现有 `run_events` 的持久化 SSE 序号和 `executions.snapshot` 可作为任务卡及 `message | task` 时间线投影来源，复用既有事件恢复机制。不为任务卡新增模型调用，不把任务事件写成伪造用户消息。
- 当前 `ReviewProposal` 主要表达修订提议；新版本需明确 `full / differential / revision` operation 语义，固定 source report/hash、材料与输入 pin、范围及排除项。具体字段由公共契约唯一声明，旧修订提议以版本兼容处理，不能靠解释文本猜任务类型。
- 讨论引用报告与任务的执行来源报告分字段保存：完整复核沿用现有契约 `source_report_id = null`、`finding_ids = []`，可以另存 `context_report_ref` 说明需求来自哪个问题；差异复核/修订才使用其明确来源报告与允许目标。不能把“正在讨论 F-002”的上下文直接塞入完整执行源字段，更不能因此静默改为差异复核。
- 已采纳的复核要求须持久化进入下一执行输入；execute 快照锁定 accepted proposal/origin 与其 hash。当前 worker 不会仅因历史 `context_messages` 存在就使用其中要求，不能把“聊过”显示成“本轮已采纳并执行”。提议采纳但未执行、提交中、真实执行中须能区分。
- 模型输出已有 `cited_finding_ids` 但当前消息持久化未保留其完整语义；须定义并保存 `reply_metadata` 或等价的版本化公共引用契约。前端用经过服务端校验的实际引用定位，不用正则从回复正文猜 finding/report。若新增持久字段，采用加法迁移并保留旧消息。
- 提议/回复 schema 与逻辑调用、reply/resultVersion 一同版本化，并固定在 prompt/context 快照。旧 queued/running/completed 消息及旧提议保留 legacy validator 和原版恢复路径；不能仅更换常量将旧调用当作缺失或重新发送，不能以新 schema 强行解释已经持久化的旧结果。
- 差异报告须保存类型明确的 follow-up lineage：来源报告/旧 finding 到本轮 finding/coverage 的映射和未映射原因。仅有“请求过哪些 finding”或稳定数字 ID 不足以证明解决；本轮证据、实际结论和覆盖才是展示依据。

仍不包含收费：无价格/报价确认、余额准入、充值、冻结、扣费、结算、退款或用户消费事件。内部真实用量和成本审计继续保留，缺失 usage 为 unknown。M2 既有规则不受影响。#77/#78 参考库、可选商业接口和另建搜索平台继续排除，公开核验按现有真实 web search 边界执行。

材料与要求快捷开始完整复核 → 助手显示真实执行卡 → 左侧出现带来源及覆盖的报告 → 从 F-002 进入助手说明并补证 → 确认本轮差异范围 → 同一任务流程执行 → 左侧区分新结论/沿用/未完成 → 按已采纳计划修订并获得真实双 Word → 明确另行重核 → 工作台回查全部快照。
