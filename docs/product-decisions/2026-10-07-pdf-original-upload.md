# 材料上传保存原件，内容处理交给编制任务

2026-10-07 用户针对杞县 2025 年审计报告上传失败明确指出：材料上传保存后由 Codex 编制任务读取，服务器不应先逐页处理 PDF。

- 所有支持格式的项目材料上传只做身份与项目归属、有效上传会话、大小／容量及原字节 SHA-256 核对，保存私有原件和不可变材料版本。不在 PUT 或 complete 中解码页面、遍历表单／签章、解压 Office、读取表格、验签或 OCR；不以这些检查是否通过决定能否保存。
- 新材料的 `signature_assessment=null` 表示上传未作签章评估，不表示无签章或已验真。相同原件复用既有材料时保留原来的不可变评估；旧记录不改写。无 schema 或数据库迁移。
- 统一编制项目上传材料后不创建独立辅助解析任务；开始编制才把原件交给既有 Codex 任务。其读取、必要 OCR 和无法读取的说明在任务内完成。已有解析任务和结果保留，不取消其他运行。
- 统一编制材料页显示保存凭证，不再显示旧辅助解析的“处理暂缓”等状态。100% 仅表示字节已发送，服务端确认保存后才进入已保存；回执异常时先查记录并自动重试幂等 complete，不重新发送文件，不自动开始编制。持续不可用时显示明确重试入口；用户无需执行例行“核对”。
- 原件仍是未受信输入，只能在既有隔离任务内读取，不能执行文档动作或将文档中的指令提升为权限。保存不证明可读性、签章真实性、业务事实或内容安全。下载与任务读取继续核验归属和原件哈希。

用户随后明确要求所有文件直接上传，因此此次扩展到全部已支持格式的项目材料；保留客户端声明格式的接口枚举，不再嗅探或解析内容。管理员参考库发布的独立内容工具不在此次项目上传范围。本文覆盖 `apps/api/UPLOAD-SAFETY.md` 中把旧文档深度检查和签章 profile 当作上传前置的要求。

复现证据：2025 年原件 7,227,129 bytes，SHA-256 `82a95dcd65ad1d1595fb2f340fa1912f540fbaa6ddec41e28c56ae971002a891`。线上错误编号 `90f234be-4cd5-41a7-aa4e-ab2cc56e1cc5` 返回 `MATERIAL_FORMAT_UNSUPPORTED / unsupported_content`；相同原件在旧检查器复现 `PDF signature structure is outside the supported profile`，具体 profile 原因为 `unresolved_pdf_reference`。这只证明旧检查器拒绝，不证明后续 Codex 不能读取。

原型：`product-prototype/public/project-workspace.js` 的 `fileRow`，保存后显示“已上传并保存”，不以逐页解析作前置。实现保持材料分区和原稿信息字段；新增自动回执恢复属于本次用户确认的流程修正。
