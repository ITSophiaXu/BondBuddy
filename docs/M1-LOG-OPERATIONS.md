# M1 log operations (#79)

Scope: durable forwarding, the operator query API, restricted prompt view, retention and deletion. All code-level evidence is **synthetic** (PostgreSQL 16/Azurite, no real provider calls). Alert delivery to external channels is #35, and real anonymised provider evidence is #16.

## Event catalog (`OBSERVABILITY_EVENT_KINDS`)

`operation.submitted`, `operation.rejected`, `job.state_changed` (run and parse jobs, including terminal states), `prompt.snapshot_saved`, `model.call_started` (durable intent), `model.call_finished`, `model.usage_observed`, `model.usage_corrected` (actor `operator`), `error.recorded`, `artifact.delivered`, `log.content_purged` (stage = purge reason, including browser diagnostic text). Payloads are the `InternalObservabilityEvent` schema: ids, codes and counts only.

Committed user operations now include `auth_register`, `auth_login`, `auth_logout`, `project_create`, `project_edit`, `project_archive`, `project_restore`, `project_delete`, `material_upload_start`, `material_upload_bytes`, `material_complete`, `material_delete`, `material_download`, `execute`, `run_cancel`, `run_resume`, `artifact_download_grant`, `artifact_download`, and `browser_error_report`. The operation and corresponding `operation.submitted` event commit with the business change where a database transaction exists. Download records mean an authorized download request reached delivery; they do not prove the client saved every byte. No unsubmitted form content is collected.

### Browser exception intake and browser integration seam (#18)

`POST /api/v1/browser-errors` uses the current cookie session plus normal Origin/CSRF protection. Request fields are `error_type` (bounded identifier), `fingerprint` (64 lowercase hex chars), optional `message` (at most 1536 characters), `route_id` (route template/identifier, no query string), `frontend_version` (bounded build identifier), optional `project_id`/`job_id`, and UTC `client_time`. The body is capped at 2 KiB; undeclared fields fail validation. The browser should remove credentials, email addresses, phone numbers, personal text, URL queries and stack frames before sending. The API runs the existing secret scrubber again, masks email addresses and phone numbers, and stores at most 1 KiB of the resulting message, truncated only at a UTF-8 character boundary. It validates every project/job reference against the logged-in owner. It never trusts a browser-supplied user or session ID.

The response is `201 {report_id,deduplicated,received_at}`. Identical fingerprint/session submissions in a rolling five-minute window return the first report; each user may create at most 20 distinct reports per five minutes. `UNAUTHENTICATED` is 401, foreign references are 404, `VALIDATION_FAILED` is 422, and `RATE_LIMITED` is 429. The API records `browser_error_report` plus `error.recorded` (`BROWSER_ERROR_REPORTED`, stage `browser`) in the same transaction. `GET /api/v1/browser-errors/{report_id}` is owner scoped; the audited `GET /api/v1/admin/browser-errors/{report_id}` requires `log_reader`. `GET /api/v1/admin/logs/events` supports user/project/job filtering and exposes `error_id` for that detail lookup. The regular log retention pass erases message text in bounded batches after `BB_LOG_CONTENT_RETENTION_DAYS`, or when the account/project is deleted; each purge emits an outbox-backed event. Fingerprints and limited metadata remain.

## Operator API (`/api/v1/admin/...`, contracts in `packages/contracts/src/admin-logs.ts`)

Without an active grant for the exact role, every route returns the same 404 as an unknown resource. Filters are allow-listed (`ADMIN_LOG_FILTERS`), and any other key or malformed value returns 422. This is also the log-injection boundary.

- `GET logs/events` (log_reader): filters are user_id, project_id, job_id, trace_id, from, to, model_id, status, error_code and limit (≤500). `model_id` matches the event's attempt, or the job for job-level events.
- `GET jobs/{job_id}/timeline` (log_reader): returns prompt refs with `content_state`, stages, attempts with token breakdown and duration, errors, artifact, outcome and consumption.
- `GET metrics` (log_reader): see metric definitions below.
- `GET prompts/{snapshot_id}?reason_code=` (prompt_viewer only): the audit row commits before the body is read, and the response is `no-store`. A purged, missing or hash-mismatched body returns 404. There is no separate export route; this audited view is the only plaintext exit.
- `GET jobs/{job_id}/timeline` includes `user_submissions` in project version order, with each message's edit version, previous ID, hash, input and material version references, and purge state. It contains no plaintext. Each listed `snapshot_id` can be opened through the audited prompt view above. `user_submission_id` on an attempt refers to the run submission locked before that call.
- `GET jobs/{job_id}/user-submissions?reason_code=` lets `prompt_viewer` discover the same version references by job ID without needing `log_reader`. This metadata lookup is audited; plaintext still requires a separate audited `GET prompts/{snapshot_id}` request.
- `POST runs/execute` accepts optional `user_prompt` from an actual submit action. The server saves its scrubbed body before queueing the run and binds the immutable input revision and material versions. Repeating the same `execution_request_id` returns the same run without a new version. The controlled `POST internal/projects/{project_id}/submissions` seam is disabled by default and accepts committed message text, a stable `message_id`, a unique `submission_request_id` for replay, an optional run, input revision/hash, and verified material versions. Editing a message reuses `message_id` with a new request ID and increments `message_version`. The existing public conversation route remains unavailable until its project conversation ownership and UI integration are completed.
- `GET alerts`, `GET evidence-gate` (log_reader).
- `POST evidence-gate/resume`, `POST attempts/{attempt_id}/usage-corrections` (**log_operator** only: a write role separate from the read-only `log_reader`; grant both when an operator must also read).

## Metric definitions (`AdminMetricsResponse`)

- **Scope:** jobs created in `[from,to]` that match the filters. `status` means job state. `error_code` means the job error code or any of its error records.
- **Job rates:** `success_rate` = succeeded / (succeeded+failed+cancelled), and `failure_rate` = failed / the same denominator. Both are null when no job is finished. Durations are `updated_at − created_at` of finished jobs (avg, p95).
- **Attempts:** counts by status. `conflict` counts attempts whose effective usage is unresolved.
- **Consumption:** `all_attempts` includes failed retries. `completed_attempts` covers final successful calls only. `retry_attempts` covers attempt_no > 1. Only `measured` attempts add tokens. unknown, pending and conflict attempts go into `unresolved_attempts` and are never counted as 0. Totals are null when nothing is measured. Cached input and reasoning output are subsets of input and output, not additions.
- **operations:** submitted/rejected, including rejections before any run was created.

## Forwarding

Run `node apps/api/dist/log-ops.js forward` with `BB_LOG_SINK_FILE` set to an NDJSON file (mode 0600). Each invocation handles one bounded batch. It leases observability outbox rows, delivers them, then records `bb_log_deliveries` and `delivered_at` in one transaction. The Linux `flock` file writer serializes all cooperating processes on a 0600 `.lock` file, scans the NDJSON file itself for `delivery_key`, appends only missing records, and fsyncs the file (even on a replay that appends nothing) and new directory entry before PostgreSQL acknowledgement. There is no sidecar receipt index. A replay after file fsync but before PG acknowledgement finds the existing key; a crash before a complete append leaves a detectable incomplete tail and blocks acknowledgement. Existing malformed, duplicate or conflicting keys and unsafe permissions also block delivery. JSON encoding prevents CR/LF line forging. `health` raises `log_backlog_stale` when the oldest undelivered event is older than `BB_LOG_BACKLOG_ALERT_SECONDS` (default 300), and `usage_conflict` for unresolved conflicts.

Before calling the sink, the forwarder verifies that **every** claimed outbox row resolves to an observability event with matching owner, kind and event ID. A missing or inconsistent source blocks the whole batch: no sink call, receipt or outbox acknowledgement occurs; the evidence gate pauses and raises `evidence_persist_failed`. After sink acceptance, an existing `bb_log_deliveries` row is checked against the exact outbox ID, sink, key and immutable source event before acknowledgement; `ON CONFLICT DO NOTHING` alone is not treated as proof of successful delivery.

The writer checks both the active file and any `.1` segment left by the earlier scheduler under the same lock. With `BB_LOG_ARCHIVE_ENABLED=0` (the deployment default), automatic rotation remains disabled and a batch exceeding `BB_LOG_SINK_MAX_BYTES` fails closed. Do not manually rotate to clear the cap.

### Private Blob segment archive (migration 0041)

Enable only after PR #226 and migration 0040 from #207 have been integrated, this migration has applied, and the **old scheduler has stopped**. Set `BB_LOG_ARCHIVE_ENABLED=1`, `BB_LOG_ARCHIVE_LOCAL_MAX_BYTES` (default 256 MiB, at least twice the segment cap), and `BB_LOG_ARCHIVE_CONTAINER` (default `bondbuddy-private`). Missing DB or Blob configuration, a missing/public container, failed receipt lookup, bad bytes or full local budget stops forwarding; the outbox remains pending and the sink alert/evidence gate path applies. The ops container limit is 384 MiB with `NODE_OPTIONS=--max-old-space-size=256`, leaving native memory room during bounded segment scans; validate load against the target VM before enabling. Do not enable the archive in production until the fault matrix and independent integration are accepted.

One stable `.lock` flock covers PG permanent `delivery_key` receipt checks, local scans and appends, sealing, Blob readback, archive receipt persistence and unlink. The active segment has a fsynced `.active-id`; sealed files have unique `.seg.<UUID>` names, never reused. PostgreSQL `bb_log_segments` stores ID, state, byte length, SHA-256 and record count. The writer recomputes those facts from complete, private 0600 files at restart and reconciles a rename that committed before its PG update. It imports a legacy `.1` by a unique rename, so the previous scheduler's bytes cannot be overwritten. A delayed process checks the permanent PG receipt while holding the lock even after many sealed files were retired; a failed PG query rejects the append.

Sealed files with missing key receipts remain local for replay. For a fully receipted segment, the writer uploads a stream to `log-archive/<sink>/<UUID>.ndjson` using create-only conditions, then streams it back and checks length and SHA-256. A lost upload response triggers a readback of that same unique name; different bytes fail. Only after an immutable `bb_log_archive_receipts` row matches the sealed metadata does the writer recheck every key receipt and local hash, unlink the file and fsync its directory. A crash before or after unlink is reconciled on the next pass. The Blob archive is the selected independent durable destination for these NDJSON bytes; it is **not** an external collector consumption ACK. A future collector needs its own receipt and retirement policy.

### Archive lifecycle decision (migration 0069)

Private archive segments retain their own 180-day default (`BB_LOG_ARCHIVE_RETENTION_DAYS`, integer 30–3650), measured from sealing. This window is independent of prompt/provider-result content retention. Once `BB_LOG_ARCHIVE_ENABLED=1`, the scheduled `archive_retention` task runs every 15 minutes by default (`BB_OPS_ARCHIVE_RETENTION_SECONDS`) in bounded batches. The deployment still defaults to archive disabled; no archive cleanup runs in that mode. The segment cap must be at most 64 MiB while the mixed-user verifier is memory bounded; higher cap settings fail startup instead of creating segments that cannot be cleaned. Do not apply a container-wide Blob lifecycle rule, because it cannot check database receipts or legal holds.

Before deleting an expired segment, the task checks the current lifecycle row against private Blob length, SHA-256, NDJSON record count and owner fields. It writes a durable delete intent, then deletes the object and writes the final audit row. A lost acknowledgement retries safely. The immutable original upload receipt remains historical evidence; `bb_log_archive_lifecycle` tracks the current object after a rewrite and its final deletion. Local segment retirement must be confirmed before the lifecycle row exists. A writer restart reconciles older receipts only when the corresponding sealed local file is absent.

An active legal hold may target a segment UUID, a `user_id`, or a sealed-time range. It overrides expiry and user deletion until released. Both setting and release require an active `log_operator` grant and are recorded in `bb_log_archive_legal_holds` with actor, reason and timestamps; segment-specific changes also append `bb_log_archive_audit`. Each skipped cleanup pass appends `skipped_hold` with segment ID, reason and before hash/count. Use the restricted maintenance commands in the runbook, not direct SQL mutation.

After an account closes, the next cleanup pass removes that user's lines from each mixed-user segment, regardless of segment age. It writes a new unique Blob object, reads it back to check length/hash/count, then atomically switches the current lifecycle row and appends the before/after audit. The old object stays available until that commit; a later pass deletes it using `pending_old_key`. Failed switches retain the old row/object and retry the same deterministic new key. A segment containing only that user is deleted directly. The task records a failed pass and raises the scheduler failure alert; operators must resolve repeated failures before the 30-day deletion deadline. Holds leave the affected segment unchanged and record why. The original immutable receipt and action audit retain only metadata after bytes are deleted.

`bondbuddy-private` is also exported by `deploy/m1/scripts/blob-snapshot.mjs` and may be included in off-host backup copies. Capacity planning and deletion response must count live archive, local pending segments and backup copies separately. This task changes live archive objects only; existing backup retention remains a separate policy. Keep the container private and monitor growth.

The writer requires stable local file and lock paths shared by its processes. Do not externally rename, unlink, replace or append to the active file, `.1` or `.lock`; do not use an NFS mount without verified lock and fsync semantics. High-volume scan cost needs capacity testing; archive mode currently rejects a segment cap above 64 MiB because the lifecycle verifier must read the complete segment. Stop the old scheduler before deploying this change so an old process cannot continue its unsafe rotation.

## Model attempt cost attribution (migration 0061)

`bb_platform_cost_ledger` is one row per supplier attempt, including failed retries. `billable=false` only for `confirmed_not_sent`; other attempts are potentially platform paid even if usage is unresolved. `cost_bearer=platform` in M1 and never deducts user credits. The management cost-ledger API adds per-item `model_provider`, `billable`, `cost_bearer`, `rate_ref`, `pricing_status`, decimal `cost_amount` and `currency`. Its existing top-level `pricing_status=unknown` remains for compatibility; use the per-item status for attribution. Daily trial token quotas remain a separate conservative admission measure, not a monetary charge.

Migration 0061 creates immutable `bb_model_cost_rates` rows with a version reference, exact provider/model pair, effective start and optional expiry, currency, four token-category rates per million tokens, source reference, recorder and reason. For a given attempt time, the latest effective start wins; duplicate starts for one provider/model are rejected. This lets a new version supersede an open-ended prior version without editing its audit record. No rate or amount is seeded. For M1, enter a rate **only through a reviewed additive database migration** after #16 verifies the supplier's model ID, token categories, currency and published/contracted price. Record the source reference and human review reason in that migration. This controlled migration path avoids a runtime price-write permission in the shared API database role; it is not an operator HTTP endpoint. Historical ledger rows recalculate from the matching immutable rate version, so a newly verified backdated version may turn earlier `rate_missing` rows into `priced`; retain the review and deployment record for audit. Never edit an existing rate row.

`unknown` means usage is pending/unknown/conflicted, the call was confirmed not sent, or the exact provider/model identity is absent. Measured usage with an identity but no effective rate is `rate_missing`. `priced` requires measured effective usage and an exact effective rate. `cost_amount` is a decimal string and `currency` is present only for `priced`; otherwise both are null. The calculation is `((input−cached_input)×input_rate + cached_input×cached_rate + (output−reasoning_output)×output_rate + reasoning_output×reasoning_rate) / 1,000,000`, rounded to ten decimal places. Null subset counters mean zero subset, while missing input/output totals never become zero. `bb_call_usage_effective` selects one measurement per attempt, excludes conflicts and applies audited corrections, so duplicate provider/gateway/framework reports do not multiply charges. Failed attempts with measured usage still contribute their own amount. This is operational cost attribution, not an invoice or a substitute for supplier billing reconciliation.

## Evidence gate

`recordPotentialCall` (the only call-intent seam, used by the durable probe journal and the adapters) checks the gate before and inside its transaction. `observeUsage` is guarded too. Connection, resource or crash-class failures (SQLSTATE 08/53/54/57/58/XX, or non-SQL errors) append a `paused` gate row and a critical `evidence_persist_failed` alert. Constraint and validation errors do not trip the gate. If even the pause cannot be written, the process holds it in memory and persists it on the next attempt. Only an operator `resume` reopens the gate.

## Retention configuration

Before a diagnostic snapshot is written to private Blob, `scrubSecrets` replaces known sensitive fields in JSON objects (including nested arrays and `session_cookie`, `x_api_key`, `one_time_password`), and handles embedded or quote-escaped JSON objects in surrounding text. It also applies the existing prose patterns for cookies, authorization headers, tokens, passwords and short verification codes. Ordinary text outside those objects, CR/LF boundaries and business placeholders such as `{债券名称: 本期公司债}` remain available for audit; quoted prose and backslashes inside escaped JSON strings are preserved. A forward scan inspects complete braced fragments and decoded quoted keys, including fields after ordinary first fields. Input and scrubbed output each have a 10 MiB UTF-8 limit. The JSON parser uses an explicit stack capped at 1024 levels and source-interval replacements rather than an object tree. At most four embedded JSON string layers are accepted. Complete quoted subtokens at that boundary are decoded once more only to classify their fields; a further quoted or structured token that needs another decode is rejected. The same normalized key and literal/encoded separator classifier handles quoted, bare and decoded fields, including spaced key spellings in surrounding prose and after a closed root. Once a known loose field is recognized, its complete quoted value is replaced as one source interval. Following punctuation and ordinary prose remain outside that value when whitespace separates the punctuation from the next token; punctuation glued to a bare suffix (including comma, semicolon and Chinese comma/semicolon, literal or Unicode escaped) is ambiguous and raises the fixed error before storage. Ordinary prose after a closing quote and whitespace remains available. A single unquoted scalar ending at CR/LF or EOF can be replaced, but whitespace or punctuation in an unquoted value makes the boundary ambiguous and raises the fixed error before storage. Callers that need mixed content should use JSON or quote the sensitive value. Unterminated quoted values also reject. All nested scanners share a budget of `64 × input UTF-16 code units + 65,536` charged scan units, including quoted and bare key tokens, separator lookahead and each of the eight bounded prose-rule passes. Prose rules use nonoverlapping horizontal-space branches, so long ordinary whitespace does not trigger regex backtracking growth. A further structured layer, exceeded depth/body/work budget, or a malformed fragment with sensitive-field evidence raises the fixed `Diagnostic body rejected` error before any Blob write or reference. There is no per-fragment size, fragment-count or structural-token cap; valid bodies up to the whole-body limit are retained without splitting. This is bounded recognition, not a guarantee that arbitrary free text or unknown secret names cannot contain a secret; callers must avoid putting unrestricted credentials into diagnostic bodies. Existing `scrub_v1` references remain readable under the same storage contract.

| Variable | Default | Meaning |
|---|---|---|
| `BB_LOG_CONTENT_RETENTION_DAYS` | 180 (1–3650) | Age after which prompt snapshot and provider-result bytes are purged, for terminal or run-less content |
| `BB_LOG_RETENTION_POLICY_VERSION` | `log_retention_v1` | Stored on each tombstone |
| `BB_LOG_ARCHIVE_RETENTION_DAYS` | 180 (30–3650) | Sealed archive segment lifetime when archiving is enabled |

`node apps/api/dist/log-ops.js retention` (needs `AZURE_STORAGE_CONNECTION_STRING`) purges a batch. Content of closed accounts is reclaimed regardless of age (`user_deleted`). Content bound to a non-terminal run is never purged. The following are kept: operation, attempt, usage, correction, error, event and audit rows, and snapshot metadata with hashes (see `CLOSURE_RETAINED_RECORDS`). The 180-day M1 default matches the published trial data notice and current API/Compose configuration (see #6 acceptance comment 5831276003). A change requires an updated configuration and user notice. Remote archives containing mixed users' NDJSON records have no automatic deletion policy yet; do not apply this prompt-body window to them. Prompts are never used for public libraries or training.

Prompt Blob creation now commits a `bb_prompt_blob_intents` row before writing bytes. Both user/run prompt snapshots and the fixed synthetic platform probe use this writer; the probe retains its template version, synthetic redaction marker, and run/input hash binding. The writer holds its row lock through Blob upload and reference commit. If reference registration and compensating Blob deletion both fail, the committed intent remains due for the next retention invocation. The sweeper locks each due intent, rechecks `bb_snapshot_refs.object_key`, and deletes only an unreferenced object; a failed Blob delete or database commit leaves the intent replayable. An intent with a registered reference is marked registered and never swept as an orphan. The one-hour grace applies to a crashed writer with no immediate failure signal; it does not override a live writer's row lock. There is no automatic scan for orphan objects created before migration 0042 or by code that bypasses this writer; those require a separately reviewed inventory. A process crash after Blob deletion but before PostgreSQL commit is safe to retry because Blob deletion is idempotent. A prolonged Blob operation can hold a PostgreSQL row lock and delay a retention batch; alert on repeated `retention_purge_failed` and retry after storage recovers.

Migration 0069 adds the archive lifecycle, legal holds, user-purge receipts and action audit. Migrations 0064–0068 are reserved by parallel changes; apply them in numeric order before 0069 when available. Rollback may stop the archive lifecycle task, but preserve its state and audit tables while archive objects remain. Dropping them would lose rewrite recovery addresses and legal holds.
