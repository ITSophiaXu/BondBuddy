# M1 log operations (#79)

Scope: durable forwarding, the operator query API, restricted prompt view, retention and deletion. All code-level evidence is **synthetic** (PostgreSQL 16/Azurite, no real provider calls). Alert delivery to external channels is #35, and real anonymised provider evidence is #16.

## Event catalog (`OBSERVABILITY_EVENT_KINDS`)

`operation.submitted`, `operation.rejected`, `job.state_changed` (run and parse jobs, including terminal states), `prompt.snapshot_saved`, `model.call_started` (durable intent), `model.call_finished`, `model.usage_observed`, `model.usage_corrected` (actor `operator`), `error.recorded`, `artifact.delivered`, `log.content_purged` (stage = purge reason). Payloads are the `InternalObservabilityEvent` schema: ids, codes and counts only.

## Operator API (`/api/v1/admin/...`, contracts in `packages/contracts/src/admin-logs.ts`)

Without an active grant for the exact role, every route returns the same 404 as an unknown resource. Filters are allow-listed (`ADMIN_LOG_FILTERS`), and any other key or malformed value returns 422. This is also the log-injection boundary.

- `GET logs/events` (log_reader): filters are user_id, project_id, job_id, trace_id, from, to, model_id, status, error_code and limit (≤500). `model_id` matches the event's attempt, or the job for job-level events.
- `GET jobs/{job_id}/timeline` (log_reader): returns prompt refs with `content_state`, stages, attempts with token breakdown and duration, errors, artifact, outcome and consumption.
- `GET metrics` (log_reader): see metric definitions below.
- `GET prompts/{snapshot_id}?reason_code=` (prompt_viewer only): the audit row commits before the body is read, and the response is `no-store`. A purged, missing or hash-mismatched body returns 404. There is no separate export route; this audited view is the only plaintext exit.
- `GET alerts`, `GET evidence-gate` (log_reader).
- `POST evidence-gate/resume`, `POST attempts/{attempt_id}/usage-corrections` (**log_operator** only: a write role separate from the read-only `log_reader`; grant both when an operator must also read).

## Metric definitions (`AdminMetricsResponse`)

- **Scope:** jobs created in `[from,to]` that match the filters. `status` means job state. `error_code` means the job error code or any of its error records.
- **Job rates:** `success_rate` = succeeded / (succeeded+failed+cancelled), and `failure_rate` = failed / the same denominator. Both are null when no job is finished. Durations are `updated_at − created_at` of finished jobs (avg, p95).
- **Attempts:** counts by status. `conflict` counts attempts whose effective usage is unresolved.
- **Consumption:** `all_attempts` includes failed retries. `completed_attempts` covers final successful calls only. `retry_attempts` covers attempt_no > 1. Only `measured` attempts add tokens. unknown, pending and conflict attempts go into `unresolved_attempts` and are never counted as 0. Totals are null when nothing is measured. Cached input and reasoning output are subsets of input and output, not additions.
- **operations:** submitted/rejected, including rejections before any run was created.

## Forwarding

Run `node apps/api/dist/log-ops.js forward` with `BB_LOG_SINK_FILE` set to an NDJSON file (mode 0600). Each invocation handles one bounded batch. It leases observability outbox rows, delivers them, then records `bb_log_deliveries` and `delivered_at` in one transaction. The Linux `flock` file writer serializes all cooperating processes on a 0600 `.lock` file, scans the NDJSON file itself for `delivery_key`, appends only missing records, and fsyncs the file (even on a replay that appends nothing) and new directory entry before PostgreSQL acknowledgement. There is no sidecar receipt index. A replay after file fsync but before PG acknowledgement finds the existing key; a crash before a complete append leaves a detectable incomplete tail and blocks acknowledgement. Existing malformed, duplicate or conflicting keys and unsafe permissions also block delivery. JSON encoding prevents CR/LF line forging. `health` raises `log_backlog_stale` when the oldest undelivered event is older than `BB_LOG_BACKLOG_ALERT_SECONDS` (default 300), and `usage_conflict` for unresolved conflicts.

Before calling the sink, the forwarder verifies that **every** claimed outbox row resolves to an observability event with matching owner, kind and event ID. A missing or inconsistent source blocks the whole batch: no sink call, receipt or outbox acknowledgement occurs; the evidence gate pauses and raises `evidence_persist_failed`. After sink acceptance, an existing `bb_log_deliveries` row is checked against the exact outbox ID, sink, key and immutable source event before acknowledgement; `ON CONFLICT DO NOTHING` alone is not treated as proof of successful delivery.

The writer checks both the active file and any `.1` segment left by the earlier scheduler under the same lock. Automatic rotation is disabled. A batch needing new bytes is rejected in full if it would exceed `BB_LOG_SINK_MAX_BYTES`; its outbox rows remain pending. A replay of keys already in either segment may still be acknowledged after fsync, including a legacy file that already exceeds the cap. A PG delivery receipt proves local sink acceptance and fsync before database acknowledgement; it does **not** prove that an independent collector consumed or archived the NDJSON bytes. These files are currently the only durable consumer copy. Retiring a segment therefore requires both a complete durable key history for delayed forwarders and a separate, verifiable archival or collector acknowledgement tied to that segment's bytes and retention policy. Neither retirement boundary exists today. Do not delete or overwrite a segment merely because all its keys have PG receipts, and do not manually rotate to clear the cap.

The writer requires stable local file and lock paths shared by its processes. Do not externally rename, unlink, replace or append to the active file, `.1` or `.lock`; do not use an NFS mount without verified lock and fsync semantics. High-volume scan cost and configurations above the default 64 MiB cap need capacity testing. Stop the old scheduler before deploying this change so an old process cannot continue its unsafe rotation.

## Evidence gate

`recordPotentialCall` (the only call-intent seam, used by the durable probe journal and the adapters) checks the gate before and inside its transaction. `observeUsage` is guarded too. Connection, resource or crash-class failures (SQLSTATE 08/53/54/57/58/XX, or non-SQL errors) append a `paused` gate row and a critical `evidence_persist_failed` alert. Constraint and validation errors do not trip the gate. If even the pause cannot be written, the process holds it in memory and persists it on the next attempt. Only an operator `resume` reopens the gate.

## Retention configuration

Before a diagnostic snapshot is written to private Blob, `scrubSecrets` replaces known sensitive fields in JSON objects (including nested arrays and `session_cookie`, `x_api_key`, `one_time_password`), and handles embedded or quote-escaped JSON objects in surrounding text. It also applies the existing prose patterns for cookies, authorization headers, tokens, passwords and short verification codes. Ordinary text outside those objects, CR/LF boundaries and business placeholders such as `{债券名称: 本期公司债}` remain available for audit; quoted prose and backslashes inside escaped JSON strings are preserved. A forward scan inspects complete braced fragments and decoded quoted keys, including fields after ordinary first fields. Input and scrubbed output each have a 10 MiB UTF-8 limit. The JSON parser uses an explicit stack capped at 1024 levels and source-interval replacements rather than an object tree. At most four embedded JSON string layers are accepted. Complete quoted subtokens at that boundary are decoded once more only to classify their fields; a further quoted or structured token that needs another decode is rejected. The same normalized key and literal/encoded separator classifier handles quoted, bare and decoded fields, including spaced key spellings in surrounding prose and after a closed root. Once a known loose field is recognized, its complete quoted value is replaced as one source interval. Following punctuation and ordinary prose remain outside that value when whitespace separates the punctuation from the next token; punctuation glued to a bare suffix (including comma, semicolon and Chinese comma/semicolon, literal or Unicode escaped) is ambiguous and raises the fixed error before storage. Ordinary prose after a closing quote and whitespace remains available. A single unquoted scalar ending at CR/LF or EOF can be replaced, but whitespace or punctuation in an unquoted value makes the boundary ambiguous and raises the fixed error before storage. Callers that need mixed content should use JSON or quote the sensitive value. Unterminated quoted values also reject. All nested scanners share a budget of `64 × input UTF-16 code units + 65,536` charged scan units, including quoted and bare key tokens, separator lookahead and each of the eight bounded prose-rule passes. Prose rules use nonoverlapping horizontal-space branches, so long ordinary whitespace does not trigger regex backtracking growth. A further structured layer, exceeded depth/body/work budget, or a malformed fragment with sensitive-field evidence raises the fixed `Diagnostic body rejected` error before any Blob write or reference. There is no per-fragment size, fragment-count or structural-token cap; valid bodies up to the whole-body limit are retained without splitting. This is bounded recognition, not a guarantee that arbitrary free text or unknown secret names cannot contain a secret; callers must avoid putting unrestricted credentials into diagnostic bodies. Existing `scrub_v1` references remain readable under the same storage contract.

| Variable | Default | Meaning |
|---|---|---|
| `BB_LOG_CONTENT_RETENTION_DAYS` | 180 (1–3650) | Age after which prompt snapshot and provider-result bytes are purged, for terminal or run-less content |
| `BB_LOG_RETENTION_POLICY_VERSION` | `log_retention_v1` | Stored on each tombstone |

`node apps/api/dist/log-ops.js retention` (needs `AZURE_STORAGE_CONNECTION_STRING`) purges a batch. Content of closed accounts is reclaimed regardless of age (`user_deleted`). Content bound to a non-terminal run is never purged. The following are kept: operation, attempt, usage, correction, error, event and audit rows, and snapshot metadata with hashes (see `CLOSURE_RETAINED_RECORDS`). The 180-day M1 default matches the published trial data notice and current API/Compose configuration (see #6 acceptance comment 5831276003). A change requires an updated configuration and user notice. Remote archives containing mixed users' NDJSON records have no automatic deletion policy yet; do not apply this prompt-body window to them. Prompts are never used for public libraries or training.

Prompt Blob creation now commits a `bb_prompt_blob_intents` row before writing bytes. Both user/run prompt snapshots and the fixed synthetic platform probe use this writer; the probe retains its template version, synthetic redaction marker, and run/input hash binding. The writer holds its row lock through Blob upload and reference commit. If reference registration and compensating Blob deletion both fail, the committed intent remains due for the next retention invocation. The sweeper locks each due intent, rechecks `bb_snapshot_refs.object_key`, and deletes only an unreferenced object; a failed Blob delete or database commit leaves the intent replayable. An intent with a registered reference is marked registered and never swept as an orphan. The one-hour grace applies to a crashed writer with no immediate failure signal; it does not override a live writer's row lock. There is no automatic scan for orphan objects created before migration 0042 or by code that bypasses this writer; those require a separately reviewed inventory. A process crash after Blob deletion but before PostgreSQL commit is safe to retry because Blob deletion is idempotent. A prolonged Blob operation can hold a PostgreSQL row lock and delay a retention batch; alert on repeated `retention_purge_failed` and retry after storage recovers.
