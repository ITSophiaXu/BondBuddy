## 新增容量测试

`apps/api/src/upload-capacity.test.ts` 使用真实 HTTP socket、PostgreSQL 16.14 和 Azurite。文件为合成 TXT，登录身份使用测试注入；这项测试证明传输/存储/配额路径，真实登录另由 HTTPS 浏览器用例覆盖。

- 五份内容不同的 **100 MiB（104,857,600 字节）** 文件逐份上传并完成持久化，每份从 Blob 重读并核对 SHA-256。
- 数据库总量 **524,288,000 字节**，确为实际传输和保存，不是修改材料元数据模拟。
- 满 500 MiB 后，再传最后一份的改名副本仍复用原版本；额外新内容保存被 422 拒绝；声明 100 MiB + 1 的单份文件在启动时被拒绝。
- 五次新增、一次复用后仍只有五个材料版本、五个 parse job，零个全文 run。临时冗余对象继续遵循既有生命周期，配额测试不代表暂存空间预留。
- 前五份 PUT 各 1.47–1.99 秒，complete 各 0.82–1.10 秒；测试本体约 20.49 秒，测试进程约 27.35 秒。仅为本机单次观测，不是 Azure 网络吞吐、并发服务 SLA 或 1,500 页混合扫描性能。

显式 opt-in，必须指向可销毁的专用本机数据库与 Blob：

```sh
npm run build
# 配置 BB_TEST_DATABASE_URL、BB_TEST_AZURITE_CONNECTION_STRING
# 并设置 BB_RUN_UPLOAD_CAPACITY_TESTS=1
node --test apps/api/dist/upload-capacity.test.js
```

测试删除自己创建的 Blob 容器；数据库中的不可变隔离记录保留在专用测试库，不尝试破坏审计记录。不要对生产存储运行容量测试。
