## 真实网页操作与判定

所有创建、上传、填写、报价接受、提交和下载均通过真实网页控件完成。保留截图、trace、浏览器收到的真实响应和本地持久证据；只读 API/本地测试库可以补充核对输入门禁、报价和账务，不能代替坏掉的页面或用直接 API 创建任务绕过网页。现有自动报价若没有独立金额确认弹窗，读取正常页面展示的价格/范围后按产品现有“开始”操作提交，不新增产品确认步骤。

### 诚信核查

1. 登录隔离账号，新建东营测试项目，上传原件并等待服务器确认；在诚信核查页面填写上表主体、站点和备注。
2. 保存，刷新后再次核对一个主体、五个指定站点及备注；读取当前价格版本、可执行范围和页面预留说明。保存报价响应和提交前余额。
3. 在页面确认本轮范围/报价并开始，仅接受一次。保存新项目 ID、run ID、锁定输入 hash/revision 和接受时价格，观察输入门禁及冻结。
4. 等原任务进入终态。若 `input_lock` 拒绝，尤其 `INPUT_REVISION_CONFLICT`，本条失败；记录错误和模型调用次数，不重新提交来隐藏失败。
5. 在结果页逐一核对所选主体与五个站点，记录有结果、无结果、受阻或失败的明确状态、实际查询标记、查询时间、证据/原因。`public_matches`、`no_public_results`、`needs_manual` 等内部状态需结合浏览器 outcome/诊断解释，不能把所有“待人工”都当作受阻。
6. 从结果页下载企业核查报告，验证非空、文件格式及 hash；刷新并重新读取同一任务的状态、五项结果、可下载成果及结算信息。

通过须同时满足：已通过输入门禁；成功完成并可下载报告；所选站点没有缺项或无解释的 pending；存在实际查询及其持久证据；账务符合接受时规则。某站 `blocked` 或 `failed` 可以作为明确的部分受限结果，不单凭该站受限判整条失败，也不强制所有网站都返回“无结果”。

未实际查询任何站点却显示成功，必须失败。仅有 `search_performed: true`、已打开官网或模型文字声称查询，不足以证明成功查询；核对当前服务端保存的查询/截图证据。全站受阻且没有可交付报告时，记录真实外部阻碍及零扣费，本条未通过，不能因为“受阻允许”签发五条通过报告。不得添加虚假查询、改站点选择或绕过验证码来凑成功。

### 底稿

1. 登录隔离账号，新建东营项目，上传募集书和目录，等真实上传确认与目录解析完成。
2. 在页面选择“1 尽职调查文件”、实际条目和募集书版本，填写样本要求。保存目录 hash、选择条目及源版本；刷新确认选择和要求仍可读取。
3. 读取页面单价、数量、总价、价格版本和扣费规则；保存报价及余额。通过正常页面操作接受并提交一次批次，记录 batch ID 及后续每个 item/run 的对应关系。
4. 等整个所选批次完成；逐份核对成功或已交付说明，不能把 partial/paused/failed 批次的部分 ZIP 当完整通过。不要为了数量一致删掉失败条目。
5. 从页面“下载已完成文件（ZIP）”下载；验证可解析归档，按非目录文件统计，数目必须大于 0，并等于页面该批次显示的已完成成果数。记录每个文件的相对路径、字节数和 hash；目录占位不计文件，说明文件计入实际成果。
6. 刷新后再读同一批次的完整状态、显示数量、逐份清单和扣费；再次核对下载入口。成果路径只应落在样本约定的两类目录。内容或分类不符另报生成结果 Bug，不放宽计数检查。

当前页面的“X / N 份完成”来自 succeeded 条目数，ZIP 则由已交付 document/explanation 组装；因此用页面 X 与归档普通文件数比较，并核对编号对应关系，不只检查 ZIP 字节数或把目录文件也算进去。若一项产生多份文件造成现有页面计数与 ZIP 语义不一致，作为产品问题登记；本测试 PR 不改产品展示、压缩包或公共契约来掩盖差异。

## 五条流程的账务与耗时报告

扩展的是测试报告内部结构，不修改公开 API/DTO。各条都保留独立账务核对结果，不能只在总报告上写“余额正确”。

| 记录 | 要求 |
| --- | --- |
| 输入与价格 | 接受时 quote/scope quote ID、新任务 ID、价格版本、报价积分、价格规则/行项目、页面展示原文及证据路径 |
| 钱包快照 | 提交前、接受后、终态后、刷新后 available/frozen，连同取样时间；JSON 中写十进制字符串 |
| 冻结和结算 | 该任务的 reservation、held/settled/released 状态、reserved/charged/released points、相应流水及页面实扣；底稿逐项记录并汇总 |
| 成果 | 页面显示成果数量、下载文件/ZIP 条目数、下载 hash、刷新后 readback 是否一致 |
| 耗时 | startedAt、submittedAt、terminalAt、checkedAt、durationMs；保存每次 resume 的起止时间，不覆盖首次提交时间和原失败记录 |
| 模型用量 | 该任务真实调用的逻辑调用数、尝试数、已知 token/usage；探针与业务调用分开，未知用量明确写 unknown，不写成 0 |

金额使用现有 Int64/string 语义：归一化为十进制字符串，运算使用 BigInt；不得用 Number、浮点或格式化展示文本进行精确账务计算。若响应确为 number，只接受安全整数，再无损转为字符串；不能对不安全整数猜测原值。

为明确归属，新增五条的最终验收建议串行执行每条业务全链路，使用同一隔离测试账号且不混入其他任务、充值、退款或过期批次变动；现有三条首次基线仍原样运行。串行窗口内，任务前可用余额减终态可用余额应等于该任务实际结算积分；接受时预留、结算与释放应逐笔守恒，终态后不残留本任务冻结，刷新/下载不能再次扣款。若保留 worker 并发以节约时长，则必须按 run/reservation 归集同窗口全部事件后核对总钱包，不能将共享余额差全算给一个用例。

**诚信核查 v4 的合法部分结算需要单独处理。** 当前版本 `bb-task-price-scope-20261111-v4` 的规则是基础 2,000 积分加每个有证据的成功“主体×官网栏目”85 积分，封顶 22,738；零成功查询不扣费。预留按可执行范围计算，交付按经过证据验证的成功范围结算，官网明确零结果计成功查询，受阻/失败项不计成功。因此有合法的 `实际结算 < 初始报价/预留`：必须与页面披露的范围规则、最终显示实扣、持久成功对数及冻结释放相符，不能简单断言实扣总等于预留。

该解释依据 [automatic-pricing.ts](../../packages/contracts/src/automatic-pricing.ts)、[integrity-billing.ts](../../packages/contracts/src/integrity-billing.ts)、[integrity-billing-evidence.ts](../../apps/api/src/integrity-billing-evidence.ts) 及 [integrity-workspace.ts](../../apps/web/src/integrity-workspace.ts) 的当前定义。测试读取接受时实际版本，不能把 v4 结算公式套到旧固定价、v2/v3 或管理价。其他流程同样按接受时规则及页面披露结算；金额、价格版本、冻结或页面 readback 不一致，均失败。

若页面没有展示足以解释的报价规则/最终实扣，或刷新后丢失这些信息，作为独立页面或计费 Bug 登记；不能只用数据库自洽就写成页面报价已验证，也不能在本 PR 改收费政策或放松断言。

## 预定实现边界与验证

前置基线完成后，预定只修改 `scripts/release-smoke/` 的 runner、flows、support、support tests 和 README：扩展两份样本映射与 hash、五条必需用例、专用浏览器流程、准确的账务/数量/时间判定、原任务 resume 和报告。必需清单为上述原三条加 `integrity-dongying`、`workpaper-dongying`；每项恰好一条，全部 passed 才形成通过报告。任务 1 的 verify 必须读取同一用例清单，避免仍认可只有三条的报告。

计划中的 support 单元测试包含缺项/重复/未通过用例、输入门禁拒绝、无实际查询的伪成功、站点受阻但有合法交付、ZIP 为空/数量不符、账务不符、大额 Int64、v4 合法少扣与旧版保价、刷新后信息不一致、resume 保留任务与时间。它们是测试工具的判断规则验证，不能代替真实网页或模型结果。

两条新流程各在调通后完整运行一次并留证据；调试优先 `--resume` 读取同一任务，保留原失败、任务 ID 和调用量，不反复新建付费任务。若故障必须重提，新任务与原失败分开记录，不能把增加消耗或失败记录抹去。未完成/超时/暂停保持未通过，不签发通过报告。

发现产品问题按 [Bug 提报规范](../BUG-REPORTING.md) 检查重复并独立登记，附候选 SHA、真实复现步骤、脱敏证据、实际/预期、账务结果及影响范围。测试 PR 用 `Refs` 关联，继续保留失败；不改运行代码、公共契约、迁移或收费政策，不以修正测试名义降低要求。
