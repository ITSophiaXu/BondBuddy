# #978 上传重试后的成功／失败行收敛

日期：2026-11-11（北京时间）。开发基线：`cc7c0b58`，分支 `fix/978-upload-retry-state`。

## 问题与证据边界

原 Issue 的用户截图显示同名文件的成功行与失败行并存；未取得当时浏览器日志、上传 ID 或运行版本，不能据此认定后台确实保存了两份材料，也不能把本次故障注入当作客户当时发生了本机存储异常的证明。

本次使用合成文件和可控回执在真实 Edge 中重现同类症状。旧代码的首轮 11 项新增测试为 **6 pass / 5 fail / 0 skip**；失败项分别覆盖失败行对账、刷新后恢复、服务器内容复用、迟到错误和成功后的本机恢复记录写失败。

## 可复现根因

1. `refreshProjectMaterials` 仅对 `uncertain` 且非 `restored` 的行匹配已保存材料。已经标为 `failed` 的行以及刷新后从本机恢复的行不会收敛；列表渲染另行显示服务端成功材料，于是两行同时保留。
2. `UploadRecovery` 收到有效完成回执后仍须写本机 journal；写入异常会变成上传失败。页面的成功处理还先读取 journal，再更新成功状态，读取异常同样会丢掉已经收到的成功回执。
3. 已保存材料被列表确认后，旧上传的状态回调与错误处理仍可将其改回失败／待确认；迟到的“字节尚未到达”还可能触发多余重传。
4. 刷新失败会删除本页已有可信回执的成功行；旧快照清理等待期间完成的另一上传也可能被误删。

后端已有同上传 ID 的事务锁与回执重放，并按同项目、材料分类、SHA-256、大小和媒体类型复用材料。本次真实 PostgreSQL／Azurite 回归验证了这些行为；未修改后端去重或计费逻辑。

扩大恢复回归还发现一个独立的既有缺陷，另记 #991：PUT 回执丢失使记录停在 `bytes_unknown`，之后 complete 返回临时检查失败的 422 被写入 `lastError`，下一次显式确认却把该错误当作原 PUT 的永久拒绝，直接返回旧错误而不查服务端。原版产品的浏览器用例已复现失败；新增单元在修复前 3 fail / 9 pass。修复只允许 **422 + MATERIAL_UNREADABLE + inspection_timeout／inspection_queue_timeout／inspection_worker_failed** 再次确认原上传，其他确定拒绝仍保持，不创建上传或传字节。

## 修复

- 统一将准确匹配的失败、取消、待确认及刷新恢复行收敛为已保存。账号、项目、材料分类、SHA-256、大小和媒体类型均须一致；仅文件名或上传 ID 相同不够。结果有歧义时保留恢复状态。
- 活动上传只接受本上传身份或已核验材料版本的成功信息；非活动状态兼容服务端返回的旧上传 ID／旧文件名内容复用。格式、结构等明确拒绝不因另一个旧上传的同名材料而被清掉，恢复后同样保留该限制。
- 有效服务端回执先决定成功，本机 journal 异常单独提示。`confirmedMaterial` 只从本次新校验成功的 API 回执产生；旧 `saved` 记录重新查询 404／503 后的记账失败不能冒充新成功。
- 列表确认成功后结束原请求，成功状态不被迟到回调、错误或字节待到达响应回退。原 journal 锁释放后清理恢复记录，刷新／离页重进不会重新显示旧失败行。
- 列表读取失败保留本页已核实成功的材料，当前列表未恢复前仍阻止开始任务。只有明确 404 才清理对应失效回执，旧快照缺项不会删掉并发完成的材料。
