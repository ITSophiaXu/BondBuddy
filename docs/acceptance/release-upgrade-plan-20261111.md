## 造数清单与真实性边界

使用一个新建测试账号和分开的业务项目。初始积分为带明确 synthetic 原因的隔离测试授予，建议 100,000 积分，不发起真实付款，不赋予任何生产权益。实际冻结、结算和余额仍走产品账务逻辑。

| 标识 | 升级前准备的数据 | 路径和边界 |
| --- | --- | --- |
| account/materials | 账号、项目、授权东营募集书及选定问题原件 | 通过真实旧网页注册、登录、新建和上传；记录新 ID、原字节 SHA-256、名称、大小及归属。 |
| completed-qa | 一个已完成、已结算、页面可下载 Word 的旧问答任务 | 使用旧版本的正常输入、成果发布、持久化和结算函数，仅把内容生成阶段替换为明确 synthetic 的文档；成果写入真实 Azurite。用于验证旧成果引用、下载与账务历史，不代表旧版真实模型质量。 |
| accepted-fixed-qa | 一个旧固定价、已接受但未执行的单题问答任务 | 旧网页/API 报价并提交，业务 worker 关闭，保持 queued。旧契约为 `project-qa-question-60-v1`；金额以旧 API 实际报价和接受回执为准，并与持久记录核对，不能直接改金额。拟作为升级后唯一完整真实模型任务。 |
| accepted-v2-integrity | 一个已接受的 `bb-task-price-170-20261029-v2` 诚信核查任务 | 复用东营诚信案例的主体/站点范围。指定 v2 报价的建立是 test-only 夹具，随后由真实旧 API 接受、冻结并创建 queued 任务；金额以旧 API 实际报价和接受回执为准，不把源码价格表数值当作本次已取得的报价。 |
| accepted-v3-qa | 一个按旧应用正常默认自动价接受的单题问答任务 | 恢复旧版正常自动报价配置后，经真实旧 API 取得 v3 报价并创建 queued 任务，积分以该 API 实际回执为准；同时覆盖“上一版本正常产生的数据”，避免只测试特殊历史价格。 |

问答题目从已授权原问题文件选择一项，登记准确题块和原文 hash，不为省费改写原题或伪称完整七题验收。问题整理/题块准备采用旧版本确定性提取和明示 synthetic 的 preparation 夹具，不额外调用模型分题。`completed-qa` 的正文应显著标注 synthetic 测试成果，不复用旧项目签字、履职记录或未获授权的模型生成稿。

旧版本的 `server.ts` 仍允许 `BB_SUBSCRIPTION_BILLING_ENABLED` / `BB_OUTCOME_PRICING_ENABLED` 控制报价模式。因此可在本隔离环境临时使用旧版已有配置，通过真实旧 API 创建固定价任务，然后恢复正常自动报价配置。这是测试配置，不代表当时生产配置相同；新候选不为测试重新开放退役的旧报价入口。

旧版本默认自动价已经是 v3，浏览器不能合法指定新建 v2 报价。`automatic-billing-context.ts` 明确禁止从浏览器接受历史价格 pin。建议参照现有 `integrity-pricing.pg.test.ts`，在旧 API 容器内由 test-only helper 调用旧版本导出的 `withAutomaticBilling(..., v2)` 与 `requestScope` 创建指定历史 scope，再通过真实旧 API 完成接受。此步骤需要在报告中标为 synthetic 历史合同夹具；不得改写已发布价表、已接受报价、冻结金额或输入 manifest，也不得声称它是旧网页自然创建的 v2 订单。

## 执行阶段

### A. 创建旧环境并保存升级前快照

1. 为本次运行生成唯一 Compose 项目和私有运行目录，检查 Docker endpoint 是本机。数据库只使用该项目内的 PostgreSQL，不继承宿主生产 `DATABASE_URL`、Blob、支付或模型连接变量。
2. 从固定旧 SHA 构建并记录正式 Web/API/worker 镜像，迁移到该旧提交的 schema；启动 PG、Azurite、Web/API，业务 worker 保持关闭。注册测试账号并授予 synthetic 积分。
3. 经真实旧网页完成账号、项目和上传。异步上传确认只调用旧版既有 `claimUploadConfirmation` / `processUploadConfirmation` 消费器；不为了上传启动会抢业务任务的整个 worker。不需要的解析作业可留在队列，不能把它们的存在记作业务任务已执行。
4. 按造数清单准备完成成果、固定价 queued 任务、v2 queued 任务和旧默认价 queued 任务；模型调用计数必须为零。真实 API 返回的接受结果与数据库 owner/project/run/input/quote/reservation 绑定必须一致。
5. 保存 `before-upgrade` 快照及必要的本地测试库/对象备份。该备份只包含本次新建测试环境。至少记录：用户/项目/材料 ID、原材料及成果字节 hash、任务状态和 input hash、报价 ID/版本/积分、冻结状态、credit lots、allocations、append-only events、已存在模型调用记录数量。

### B. 在相同数据卷上升级

1. 停旧 Web/API，确认所有业务 worker 已停且没有在途供应商调用；保留相同测试 PG、Azurite、测试账号认证配置和数据卷。没有关闭生产入口、生产迁移或生产服务操作。
2. 用候选镜像运行正常迁移程序，记录每份迁移及耗时；再切换候选 Web/API，先保持业务 worker 关闭。不能重置数据库、改写已部署迁移或通过重建数据掩盖升级失败。
3. 立即保存 `after-migration` 快照。原数据中的余额、冻结、流水、已接受报价、输入、任务状态与成果字节必须保持；新增表/列按迁移清单单列，不要求包含迁移元数据的数据库文件逐字节相同。所有金额使用十进制整数/BigInt，不能经浮点数比较。
4. 从候选网页验证原会话（仍在有效期内时）、重新登录、旧项目打开、原材料下载、旧成果下载及 hash；刷新后再读取一次。自然过期的会话可以要求重新登录，不能据此判定账号升级失败。

### C. 核对已接受任务并只完成一个真实任务

1. 读取旧任务及其已接受报价、输入快照、预留和关联 scope，调用候选已有 worker 输入校验函数，核对无 `INPUT_REVISION_CONFLICT`、无新 scope quote、无重新定价。其他历史任务的这一检查证明输入门禁和账务绑定兼容，不能代替完整模型执行或交付验证。
2. 同一 request ID 的原接受请求重放必须返回原 run。旧 `number-v1` 协议仅能重放已经受理的请求；新请求使用 `x-bb-billing-format: int64-decimal-v1`。不要要求已退役的旧协议继续接受新付费任务。
3. 保存升级后、不改变任务控制状态的账务快照。随后通过正常任务控制 API 暂停除 `accepted-fixed-qa` 外的待执行任务，记录这是测试控制动作而非迁移结果。
4. 检查只有选定任务可被业务 worker 领取，再启动候选 worker。**仅把 concurrency 设为 1 不足以控制成本**：当前 `claim()` 支持 task kind/interactive 过滤，没有单个 run ID allowlist；第一项完成后可能立即领取下一项。暂停其他任务是启动前必需检查，不能依赖看到完成后及时停止。
5. 选定的单题旧固定价问答真实完成后立即停 worker，核对原输入和原报价、一次结算、终态、页面成果、实际 Word 下载及刷新读取；所有真实模型调用必须归属于该选定任务。真实调用/工具/修复可能不止一次，分别记录 completed/failed/unknown 和用量，不把“一项任务”记作“一次模型调用”。
6. worker 保持关闭，通过候选网页新建一项新任务，真实取得当前价并接受为 queued，核对当前价格版本、输入锁定和新冻结；不再执行第二项真实模型任务。
7. 验证结束后通过正常取消流程释放未执行测试任务的冻结，记录清理前后差异。清理释放不能混入“升级前后账务不变”的断言。失败时保留同一环境和原 run ID，不自动清库或重新提交。

## 钱包与账务断言

- 迁移本身不能改变原 lots 的 `remaining/frozen`、已有 reservation、allocation 和流水；原价格版本、接受积分与 input hash 保持不变。
- 接受任务时：可用额减少报价积分，冻结额增加同额；没有真实付款或供应商费用记入测试钱包。
- 已冻结任务正常交付时：冻结减少实际结算积分；不能错误要求“可用额再次减少报价积分”。如果合同存在释放部分，分别比较结算和释放。这里选定的旧固定价单题应按旧 API 原接受回执记载的金额结算一次，不预填尚未执行取得的账务结果。
- 同 request ID 重放、刷新、旧成果再次下载不能重复冻结或结算；其他 queued/paused 任务不能因该任务完成而被重新报价或扣费。
- 清理取消产生的 release 事件在单独阶段比较，允许并要求正常释放；不能删除 append-only 事件使钱包看起来恢复原样。

## 拟保存的证据和恢复规则

私有报告记录旧/新 SHA/tree、镜像 ID/架构、授权样本 hash、schema 变化、业务步骤、每阶段起止时间、真实/夹具边界、before/after 快照摘要、每项断言结果、模型调用计数/用量与最终下载 hash。账号密码、令牌、Cookie、原件、生成稿和原始数据库内容不提交 PR。

拟按 `old_environment_ready → seeded → snapshot_before → migrated → compatibility_checked → one_live_run_finished → new_request_checked → cleanup` 记录阶段。恢复只读已提交 run 和现有阶段，不重做注册、授予、提交、旧成果 fixture 或模型调用。失败留下原证据；属于产品问题按 `docs/BUG-REPORTING.md` 单独提报，不在本 PR 修改产品或降低检查标准。

## 时间、调用和费用估算

| 项目 | 计划估算或上限 |
| --- | --- |
| 热缓存准备、造数、迁移、非模型检查 | 预计 30–60 分钟，实际分阶段计时。 |
| 首次构建旧/新镜像 | 可能另需 45–120 分钟，取决于缓存、网络和本机资源；不是承诺完成时间。 |
| 选定单题真实任务 | 预计 5–30 分钟；使用实际超时/暂停状态留证，不能根据此前七题耗时保证单题时长。 |
| 真实业务完整运行数 | 最多 1 个：旧固定价单题问答；其余任务验证历史数据、输入门禁及账务绑定，不额外完成真实模型生成。 |
| 应用测试积分 | 在旧 API 实际报价、接受后登记选定任务金额；新任务也按候选 API 实际报价登记。源码中的历史单价只能用于交叉核对，不能代替本次报价与结算回执。这些是隔离应用账价，不是供应商账单。 |
| 供应商调用/费用 | 一项任务可含多次模型、工具和修复调用，实际记录；不能预先写成只有一次调用或虚构人民币费用。Copilot 额度或供应商硬限额是否可执行，需要在授权配置就绪后另行核对。 |

不为本方案增加旧版真实分题、旧版真实成果生成或重复模型探针；前置三流程测试负责确认基本环境，选定升级后任务本身验证其真实生成链路。调试复用现有 run；无法确认调用是否完成时保留为 unknown，不重复提交碰运气。

## 不能据此宣称的结果

- 不证明旧版真实模型曾生成过 `completed-qa` 的正文，也不证明其专业内容质量；它是显著标记的 synthetic 历史成果夹具。
- 不证明 v2 价格由当前旧网页自由选择产生；它是可信旧函数建立、真实旧 API 接受的历史合同夹具。
- 不证明所有历史任务类型和价格版本均完整跑过真实模型。其他类型的等价覆盖缺口见价格矩阵，另开模拟测试 PR。
- 不证明生产数据迁移成功、线上 DeepSeek 输出质量通过、全部旧版本兼容或回滚兼容；本次只验证指定旧 SHA 到指定候选 SHA、指定隔离数据。
- 不承诺供应商人民币硬预算或单次 API 调用上限。如果用户要求可强制执行的费用上限，必须先确认本机模型供应方确有相应能力，再实现并验证限制。

## 待用户确认

1. **建议方案**：接受旧成果和 preparation 为明确 synthetic 夹具、v2 由可信旧函数构造；仅升级后旧固定价单题真实完成。如此可把旧环境模型调用控制为零，同时验证真正的数据库/存储升级和原报价续跑。
2. 若要求“旧成果必须由旧版真实模型生成”，需批准额外旧版运行及调用消耗；不能同时宣称旧环境零模型调用。旧成果专业质量还需单独验收。
3. 确认旧 SHA、最终候选固定方式，以及只完成一项真实任务、其他任务只到真实输入门禁的覆盖边界。批准方案后才另行实现和执行；当前不合并、不部署。
