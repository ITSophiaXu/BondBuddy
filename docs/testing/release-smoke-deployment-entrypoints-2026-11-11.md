## 镜像一致性（2026-11-12补充实现）

建议正式候选在目标Linux架构上测试并复用同一镜像ID或不可变digest；测试后直接导出/加载，避免相同源码重新构建得到不同依赖或基础镜像。Windows宿主本身不是障碍：Docker Desktop的Linux amd64镜像可与amd64服务器一致。

如果测试机只能跑arm64而部署为amd64，不能要求二者image ID相等，也不能据相同SHA声称运行等价。建议用目标架构重新构建并跑真实样本（仿真或独立受控runner），然后部署该镜像；若需接受跨架构源码等价，应另定义并确认目标平台验证证据，不能仅新增跳过参数。

本次按继续完善发布门禁的授权实施相同 ID 和目标平台的强制核验。`verify-images.mjs` 只复用本地仍保留的被测镜像，缺失时要求加载相同归档，不用重建结果冒充已测试镜像；release tag 漂移、源码 revision 或架构不一致均拒绝。导出前及部署实际容器启动后再次核对。没有跨架构豁免。原有真实模型/人工质量凭据仍不可被 smoke 或结构检查替代。

报告要求 `release-five-flow-v1`，五条实际流程各有接受报价、冻结/结算、完整成果结构、至少两次独立网页下载与刷新不改账证据；检查器绑定候选 Git 源码和 API 镜像。`completedAt` 首次写定，24小时期限仍按原始用例完成时间计算，resume 不能延长。

## 启用与回滚衔接

当前历史版本没有两份原始通过证据。`rollback-readiness.mjs` 在正常版本切换前检查旧版原始凭据、准确角色的成功日志以及保留镜像，因此会在任何 pending、迁移和服务切换前拒绝无可验证回滚路径的升级，而不是等回滚时才失败。单机部署/回滚和每个角色的部署/回滚共用各自 state 下的部署锁。此检查不替代备份或迁移兼容性检查。
