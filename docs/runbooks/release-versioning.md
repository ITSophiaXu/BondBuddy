# BondBuddy 生产版本号管理

自 2026-11-22 起，正式生产版本使用 `vMAJOR.MINOR.PATCH`。首个已登记的生产基线为 `v1.0.0`。版本号表示**实际部署并核验的整套生产状态**，不表示 `develop`、`master` 或某个 PR 的最新提交。

## 编号规则

- `MAJOR`：需要作为新兼容基线管理的重大或不兼容变更。
- `MINOR`：一次包含新功能或多个功能的正式发布。用户所说的“大发布”必须有新版本号。
- `PATCH`：生产修复或配置兼容性修复。建议每次生产变更都递增版本号，避免多套实际状态共用同一号码。
- 本地集成测试候选可以用 `vX.Y.Z-rc.N`，不得把候选版标为已上线。未部署的 PR 不创建正式版本号。

版本号单调递增，不重用、不移动、不删除已发布标签。回滚到旧代码也是一次新的生产状态变更：保留原标签和历史记录，给此次回滚后的实际状态分配新版本号，注明所引用的旧版代码与数据恢复点。

## 每次正式发布

1. 发布负责人从最新 GitHub Release 选择下一个版本号，核对远端标签未占用。固定本批候选源码和各组件镜像，完成项目既有的本地集成验证、用户验收、迁移与回滚检查。
2. 在统一部署锁下发布；核验公网入口、API、实际运行的各 worker、数据库版本和本批关键业务链路。失败或尚未上线的候选不创建正式标签。
3. 在受限的私有运维位置保存完整发布清单：版本号、北京时间、负责人、PR/提交、各组件实际源码提交和不可变镜像 ID、数据库迁移号及备份摘要、配置变更摘要、验证结果、回滚目标、已知问题。即使仓库为私有，也不得提交密钥、服务器路径、客户数据或完整私有环境；仓库可见性变化前应重新审查发布记录。
4. 在仓库创建不可移动的注释标签 `vX.Y.Z`，指向这次部署的固定主源码提交；在 GitHub Release 记录面向协作者的变更摘要与验证状态。若组件使用不同提交，标签说明应明确它只锚定主源码，完整组件矩阵以私有清单为准，不能声称所有容器同版。
5. 在交接记录中分别标注“开发完成”“本地集成版可验收”“用户已验收”“已部署并核验”；仅最后一种状态对应正式生产版本。

## 查阅与核对

- GitHub 的 `vX.Y.Z` 标签和 Release 是版本索引；私有发布清单是准确复现生产多组件状态的依据。
- 发布前核对实际容器镜像 ID、源码标签及数据库迁移号，不能仅凭 Git 标签、环境变量或网页显示的版本号判断当前生产状态。
- `v1.0.0` 是首次补建的生产基线标签，锚定当时主站 Web/API 源码；其余组件和数据库的准确版本记录在私有清单中。此后按上述流程在每次发布后登记。
