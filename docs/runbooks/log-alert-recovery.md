# Runbook: #79 log alerts and recovery

For the isolated pre-release fault drill and phase-by-phase reconciliation, see [log recovery drill](log-recovery-drill.md).

All alerts are rows in `bb_ops_alerts`, visible through `GET /api/v1/admin/alerts`. External paging is wired by #35.

| Alert | Meaning | Action |
|---|---|---|
| `log_sink_unavailable` (critical) | The sink rejected a batch. Nothing was marked delivered | Check the sink (file path, disk, permissions). Once it is fixed, keep running `log-ops forward`, and the backlog replays. Consumers dedupe on `delivery_key` |
| `log_backlog_stale` (critical) | The oldest undelivered observability event is older than the threshold | Check that the forwarder timer runs and that the sink is healthy. Replay is safe to repeat |
| `evidence_persist_failed` (critical) + gate `paused` | An execution-evidence write failed at the infrastructure level. New external model calls are refused with 503 | 1. Restore PostgreSQL (connectivity, disk, failover). 2. Reconcile in-flight attempts with `pending_reconcile` status using the [provider result reconciliation runbook](provider-result-reconciliation.md). Do not resend them. 3. As a `log_operator`, `POST /api/v1/admin/evidence-gate/resume {"reason_code":"db_recovered"}`. 4. Confirm with `GET /admin/evidence-gate` that both `state` and `process_state` are `open`. Restart any worker whose process still holds an unpersisted pause |
| `usage_conflict` (warning) | Measured reports disagree for one attempt. Its tokens are excluded | Compare the raw observations in the job timeline with supplier evidence, then, as a `log_operator`, `POST /admin/attempts/{id}/usage-corrections` choosing the correct observation, or choose `unknown`. Raw rows are never edited |
| `retention_purge_failed` (warning) | A registered-content or orphan-prompt Blob delete failed | Check storage availability and rerun `log-ops retention`. Registered content receives a tombstone; an orphan keeps its `bb_prompt_blob_intents` row until deletion succeeds. Both replay safely. |
| `storage_orphan_candidates` (warning) | The bounded private-container inventory found objects without a database reference or open prompt intent | Inspect the counts and key digests from `storage-inventory scan`, confirm the relevant write path and backup, then use the explicit deletion procedure below only for old legacy snapshots. |
| `scheduled_task_failed` for `archive_retention` (warning) | Archive deletion or rewrite could not finish | Check Blob availability and the segment's lifecycle/action audit. Keep the original object and rerun `node apps/api/dist/log-archive-lifecycle.js retention`. A pending old key is safe to delete only after the new object and lifecycle row match. Escalate repeated user-deletion failures before the 30-day deadline. |
| `scheduled_task_failed` / `provider_balance_low` (critical) | Scheduled balance probe found `is_available=false` or USD balance below the configured threshold | Restore funds before authorizing another model call. The alert stores only availability and the balance band. |
| `scheduled_task_failed` / `provider_balance_probe_failed` (warning) | Balance endpoint, proxy or response validation failed | Check the egress proxy and supplier status, then retry the probe. Do not infer a healthy balance from this warning. |

## Private Blob inventory

The ops scheduler runs `storage_inventory` hourly when private Blob storage is configured. `BB_OPS_STORAGE_INVENTORY=off` disables the scheduled scan. Each pass reads at most three pages of 100 objects per known root and resumes from `bb_storage_inventory_cursors`; it never deletes. Run a manual read-only pass with:

```sh
node apps/api/dist/storage-inventory.js scan
```

The three roots are `users/`, `parse-cache/` and `log-archive/`. Recognized layouts cover project prompt snapshots, material uploads, provider results, OCR results and pages, run Word artifacts, parse cache entries, and NDJSON archives. The report groups object counts, bytes and oldest modification time by root, kind and classification. `referenced` means a direct database reference exists; OCR page objects are conservatively considered referenced when their material/version has an OCR snapshot, because individual page keys live inside the result Blob. `intent_pending` means the existing prompt intent sweeper owns cleanup. `orphan_candidate` means no reference or open intent was found; for prompt snapshots it also means the Blob modification time is strictly before the recorded `0042_m1_orphan_prompt_blobs.sql` application time. `post_0042_unregistered` means a prompt snapshot was written or modified at or after that boundary without a reference or open intent: keep it, investigate the writer that bypassed intent registration, and reconcile manually. `snapshot_provenance_unknown` means the 0042 application time or Blob modification time is unavailable: keep it and restore the missing evidence before any deletion decision. All three classes count toward the `storage_orphan_candidates` warning; only pre-0042 `orphan_candidate` snapshots can be deleted. `unrecognized` keys are never deletion candidates. Sample keys are SHA-256 digests, capped by `BB_STORAGE_INVENTORY_SAMPLE_LIMIT` (default 5); neither full paths nor contents appear in the report. A page count is a bounded pass, not the entire container total; keep running scans until the continuation flags are false after each root completes a cycle.

Deletion is limited to prompt snapshots whose Blob modification time is strictly before the `bb_schema_migrations.applied_at` recorded for 0042 and that have no reference or intent. The deletion transaction locks the reference and intent tables, locks and rereads that migration row, and rechecks the object time and references before the conditional Blob delete. A missing migration row or object time fails closed; an object at or after the boundary remains inventory-only even when older than the grace period. Other categories have write paths that may upload before reference registration, so their candidates require separate reconciliation of the writer and lifecycle before any deletion. Confirm that every active API writer uses the 0042 intent protocol; do not run deletion during a mixed-version rollout. First confirm that the `bb-backups` backup covers the affected private container and that restore access is available. Record the scan counts and digests, then run one bounded batch with:

```sh
BB_STORAGE_INVENTORY_DELETE=true node apps/api/dist/storage-inventory.js delete
```

The command enforces a grace period of at least 24 hours (`BB_STORAGE_ORPHAN_GRACE_HOURS` if larger), rechecks the reference and intent while holding their database write locks, and conditionally deletes only the exact listed Blob ETag. `BB_STORAGE_INVENTORY_MAX_DELETES` defaults to 20 and cannot exceed 100. An immutable `bb_storage_inventory_delete_attempts` row commits before Blob IO so a crash leaves an audit lead; a successful delete has an immutable receipt in `bb_storage_inventory_deletions` with the key digest, byte count, modification time and policy version. Reconcile an attempt without a receipt against the object and backup before retrying. A deletion cannot be undone in place; restore bytes from the confirmed backup under the original key, then rerun the inventory and check the reference state. If the reference is absent, investigate why it was lost before publishing restored bytes to users. Do not remove a still-open intent or edit receipts to silence an alert.

## Supplier balance and paused runs

The ops scheduler probes `GET https://api.deepseek.com/user/balance` every five minutes when `DEEPSEEK_API_KEY` is configured. `BB_OPS_PROVIDER_BALANCE=off` disables it; `BB_PROVIDER_BALANCE_THRESHOLD_USD` defaults to 1. The probe uses the configured HTTPS proxy and stores `is_available` plus a range (`negative`, `zero`, `below_threshold`, `healthy`, `unknown`), never the credential or exact amount. A failed probe is warning; unavailable or low balance is critical. Both use the existing `scheduled_task_failed` alert kind with a distinct `reason_code` detail, so no alert-schema migration is needed. [DeepSeek balance API](https://api-docs.deepseek.com/api/get-user-balance) defines `is_available` and `balance_infos[].total_balance`.

For a model attempt with `MODEL_PROVIDER_BALANCE_EXHAUSTED`, the run pauses at `provider_reconcile` with public event reason `provider_balance_exhausted`; its attempt and token usage remain pending/unknown. The same safe code and category `model_provider` appear in the restricted error diagnostics. A 402 response or the CLI's `Insufficient Balance` diagnostic establishes a rejection, but does not itself prove the supplier charged zero tokens. Confirm the balance has recovered, then run `deploy/m1/scripts/reconcile-run.sh list` and inspect the exact run and attempt. Use `resolve <run_id> <attempt_id> retry_unknown_usage balance_restored` only after checking available supplier history and authorizing an additional call. That command preserves the first attempt's unknown usage, records the operator decision, and queues a new attempt through the usual external-call gates. If retry is inappropriate, use `fail_run` with a safe reason code. See [provider result reconciliation](provider-result-reconciliation.md) for the full evidence checks. Never clear an attempt or change token counts by hand.

## Archive retention and holds

The ops scheduler runs archive cleanup only with `BB_LOG_ARCHIVE_ENABLED=1`; keep that switch disabled until archive operation is approved. `BB_LOG_ARCHIVE_RETENTION_DAYS` defaults to 180 and rejects values below 30. The command below uses the same database and private Blob settings as the scheduler:

```sh
node apps/api/dist/log-archive-lifecycle.js retention
node apps/api/dist/log-archive-lifecycle.js hold-set ACTOR_ID REASON_CODE segment SEGMENT_UUID
node apps/api/dist/log-archive-lifecycle.js hold-set ACTOR_ID REASON_CODE user USER_ID
node apps/api/dist/log-archive-lifecycle.js hold-set ACTOR_ID REASON_CODE time FROM_ISO TO_ISO
node apps/api/dist/log-archive-lifecycle.js hold-release ACTOR_ID HOLD_UUID
```

Set/release checks an active `log_operator` grant. Record the returned hold UUID in the case record. Confirm each operation in `bb_log_archive_legal_holds` and `bb_log_archive_audit`; time/user scope is recorded on the hold row, and affected segments record any skipped cleanup. For a deletion request, check `bb_users.closed_at`, then inspect `bb_log_archive_lifecycle`, `bb_log_archive_user_purges` and `bb_log_archive_audit` for remaining objects, failed rewrites, holds and `pending_old_key`. A hold intentionally postpones deletion; after release, rerun cleanup. Never delete a held object or edit an immutable receipt by hand.

For a failed rewrite, compare the current object's length and SHA-256 with `bb_log_archive_lifecycle` and rerun cleanup. The original object remains the current address until the new object has passed readback and the transaction commits. Once the row points at the new object, `pending_old_key` identifies the old object to remove on the next pass. A missing current object without a committed delete intent is an incident: preserve metadata and backups, stop cleanup for that segment, and investigate before retrying.

## Crash recovery facts

- Forwarder crash after the sink accepted a batch: leases expire, and the same `delivery_key`s are re-sent.
- With archive mode disabled, the NDJSON size cap stops new keys and leaves them in the outbox; automatic rotation is disabled. With archive mode enabled, a full active segment seals and archives, while an unavailable Blob, missing receipt or exhausted local budget stops forwarding and pauses the evidence gate. Inspect `log_sink_unavailable`/`log_backlog_stale`; preserve the active file, legacy `.1`, every `.seg.<UUID>`, `.active-id` and `.lock`. Never manually remove or rename a segment to clear the alert.
- A `bb_log_deliveries` receipt confirms the local file writer returned after fsync. It is neither a Blob archive receipt nor an external collector acknowledgement. Retire a sealed local segment only through the writer's same-lock verification of every key receipt, the independent Blob readback receipt and the local hash. A missing source observability event or mismatched receipt pauses the evidence gate; reconcile the immutable source/outbox mapping before an operator resumes it.
- NDJSON writer failure on a partial/corrupt line or unsafe file/lock permissions: forwarding stays unacknowledged and raises `log_sink_unavailable`. Preserve restricted copies of all local segments and metadata, reconcile the damaged tail and its `delivery_key` against PostgreSQL outbox/receipts, repair only with a reviewed operator action, then replay. Never replace a file with an empty one or silently discard a complete line. Keep paths and the `.lock` inode stable across retries.
- If archive mode reports a missing `.active-id`, stop **all** ops schedulers, manual forwarders and other writers before recovery. Keep the existing `.lock` inode and hold its exclusive `flock` across the entire inspection and repair. Under that lock, require exactly one `bb_log_segments` row for this sink in `state='active'`; use its existing UUID only. Verify the active NDJSON is a private regular 0600 file, every line is complete and valid with a unique `delivery_key`, and its actual byte length, SHA-256 and record count exactly match that PG row. Also check that no sealed filename already uses the active UUID. If any check or PG query fails, keep writers stopped and escalate; never guess or create a new UUID, truncate a file or clear the gate to force progress. After a full match, create a new 0600 `.active-id.<random>.tmp` with `<PG UUID>\n` using exclusive creation, fsync the temporary file, atomically rename it to `.active-id`, and fsync the containing directory while still holding the lock. Read it back and repeat the PG/file identity checks before releasing the lock; restart one writer and verify archive health before resuming the rest. Preserve a restricted incident record of the compared metadata and operator approval, without copying log contents into the report.
- API or worker crash: jobs, attempts and terminal events are committed with their outbox rows. Nothing is written only to memory.
- Grants: create them with `grantOperator` in a reviewed maintenance session (no HTTP route). Revoke with `revokeOperator`, which takes effect on the next request.
