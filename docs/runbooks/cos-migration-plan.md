# BondBuddy Azure Blob → 腾讯云 COS 迁移实施方案（草案）

## 2026-11-28 真实 COS 测试与待补权限

已使用用户在本机提供的测试子用户 CSV 临时加载 `SecretId`/`SecretKey`，未输出、复制到仓库或提交凭据。北京应用测试桶的 `HeadBucket`、`GetBucketVersioning`、`GET Bucket Object versions`、`GetBucketACL`、`GetBucket`、`PutObject`、`GetObject`（含 Range）和 `DeleteObject` 已经实际调用成功；ACL 为 `private`，版本控制未启用。普通 `If-None-Match: *` PUT 会覆盖对象；改用腾讯云官方的 `x-cos-forbid-overwrite: true` 后，第二次同名 PUT 返回 `FileAlreadyExists`，原内容保留。过期 ETag 的 `If-Match` DELETE 返回 412，表明当前桶的条件删除可用。随机探针对象均已删除，并用对象及版本列表确认无残留。依据：[PUT Object 请求头](https://cloud.tencent.com/document/product/436/7749)、[COS API 授权策略使用指引](https://cloud.tencent.com/document/product/436/31923)。防覆盖请求头在启用或暂停版本控制的桶上不作为保障，本分支的仅创建写入因此要求对应桶从未启用版本控制。

同一密钥对应用桶中的**现存**随机测试对象调用 `HeadObject` 返回 403；对备份测试桶的 `HeadBucket`、版本状态、ACL 和列表调用均返回 403。因此真实应用读回、备份恢复和完整本地 COS 集成尚不能验收。官方将 `HEAD Object` 映射为 `name/cos:HeadObject`，版本状态映射为 `cos:GetBucketVersioning`，历史版本列表映射为 `cos:GetBucketObjectVersions`；实际 CAM JSON 使用 `name/cos:` 前缀。限两桶策略候选直接交付用户，不进入 Git。该策略仅完成本地 JSON 语法检查；目前尚未证明控制台接受，也尚未证明更新后目标身份的全部 API 调用成功。必须绑定到生成此 CSV 的同一子用户并实测，不能据策略文本宣称权限已生效。

当前桶的过期 ETag 条件删除虽然通过实测，库存自动删除仍保持关闭；它还需要版本桶与并发删除的完整验收。COS 目标桶的版本策略需单独决定，不能把本次未启用版本控制的测试结果外推到正式桶。

真实测试暴露的旧 `If-None-Match` COS 写法已在日志归档和迁移复制仅创建路径改为 `x-cos-forbid-overwrite`，探针也已修正。API TypeScript 编译通过，相关定向测试 10/10 通过；完整 worker 构建、Web/API/worker 本地集成、备份恢复、1% 样本测速和生产切换仍未完成。下文早于本节的“尚未取得测试凭据/未对真实 COS 调用”等进度描述由本节覆盖。

## 目标与边界

将材料、派生文件、成果、参考库、受控日志与归档、备份及恢复全部改用 COS。数据库现有 `object_key` 保持不变；必要时增加存储提供方标识，不批量改写历史引用。上线后正常业务及定时任务不得访问 Azure Blob。Azure 源数据在核验和回滚观察期内保持只读，之后按数据保留和清退批准流程退役。应用服务器是否留在 Azure 是独立决定。

2026-11-28 用户确定目标 COS 数据放在**中国内地**，首要原因是访问速度，并非提出额外隐私驻留要求。具体 COS 地域尚未选定。数据分类、跨境传输及适用合规要求仍须独立核对，不能由迁移动机代替结论。当前执行机部署记录指向 Azure West US 2；应用与 COS 之间可能形成跨境往返。默认上传和下载由应用 API 转发，直传 COS 尚未实现，因此仅把对象放到内地不能推定用户端会更快。选桶前应从实际 API/worker 运行位置与主要用户所在网络，分别测上传、下载和生成读取的端到端延迟及吞吐；若瓶颈在跨境 API 路径，需另行决定应用是否迁入内地或实现并验收直传。测试桶可先按明确的候选地域建立，正式桶地域须以实测和合规结果固定。

同日用户补充首期用户集中在北京，因此隔离测试桶候选地域定为腾讯云标准 COS **北京 `ap-beijing`**，正式地域仍以端到端实测为准。官方[创建存储桶](https://cloud.tencent.com/document/product/436/14106)文档确认地域、名称创建后不能修改，支持私有读写、版本控制、服务端加密与单/多 AZ；[地域和访问域名](https://cloud.tencent.com/document/product/436/6224)列明北京标识。测试阶段使用两个名称不同的通用私有桶，分别用于应用对象和离机备份；先不创建正式桶、CAM 子用户或密钥。官方[授权策略指引](https://cloud.tencent.com/document/product/436/31923)将 PUT Bucket 映射为 `name/cos:PutBucket`，示例资源形如 `qcs::cos:ap-beijing:uid/<APPID>:<桶名-APPID>/*`；此处仅为官方映射记录，不是已验证的可用策略。当前控制台截图显示目标身份为腾讯云主账号，项目内尚无真实 COS 建桶或 API 成功记录；正式 CAM 策略与目标身份实际调用须另行核验。

本迁移是跨 API、worker、运维脚本和部署配置的变更。`PrivateBlobs` 只覆盖应用对象；日志归档、异地备份及恢复脚本仍直接使用 Azure SDK。出站代理的 `BB_EGRESS_ALLOW` 也需要从 Blob 主机调整到精确 COS 主机。

## 工具与校验

先核实腾讯云官方迁移服务对当前 Azure 账户、认证方式、访问层及定时增量的实际支持，再与自有流式复制工具作样本对比。需要逐对象 SHA-256、可重放清单和数据库引用核验时，优先使用可在**首次读取 Azure 的传输流中**计算哈希的脚本；不要复制完再从 Azure 全量读取一次。原对象已有可信数据库 SHA-256 时，还要比对该值。COS 侧复核从 COS 读取，不增加 Azure 出站流量。

复制清单至少记录源容器、对象键、源版本/ETag、字节数、SHA-256、内容类型、目标桶、复制时间和结果；凭据与签名 URL 不入清单。对象键完全相同，容器到桶映射明确。复制可重试、可从清单续跑，目标已存在但哈希不同必须停下调查，不能覆盖。先抽取约 1% 的分层样本（大、小对象及各访问层、各业务前缀），按实测吞吐、API 限流和失败率估算全量与最后增量耗时。报价包括 Azure 出站与解冻、COS 存储/请求/流量以及双存储观察期。

开发中的 `deploy/m1/scripts/cos-copy-cli.mjs` 已覆盖**现行对象**的逐个复制：Azure 单次读取时计算 SHA-256，先落入本地私有临时文件，核对源字节数及可信数据库哈希后才上传，COS 读回复核，逐对象同步私有 JSONL 清单；重跑会复核目标，不重复读取未变化的 Azure 对象。临时目录可由 `BB_COS_MIGRATION_SPOOL_DIR` 指定，须是只有迁移进程可访问的目录，空闲容量至少容纳最大单个对象。源 ETag 变化时，只有显式增量模式且旧 COS 对象与既有清单吻合才覆盖。可用私有键清单指定约 1% 分层样本，并用数据库导出的可信哈希清单额外核对。目标桶在整个复制期必须只由此工具写入。全量增量扫描若发现清单中已复制的源对象消失，会停下要求核对删除墓碑。此工具未覆盖历史版本、软删除或墓碑，也未在真实 COS 运行；不能据本地测试开始生产全量复制。`cos-capability-probe.mjs` 准备了隔离测试桶的条件写、条件删除、Range、版本状态和清理探针，但目前仅做语法检查，实际结果待测试桶。

## 代码改造与必测语义

1. 在 `PrivateBlobs` 后加入 COS 适配器和明确的提供方配置，覆盖有界读、流式读写、Range、一致性哈希、分页列举、对象标识及删除。所有 API/worker 入口改为统一工厂。不要把 Azure ETag 当成内容哈希或假设 COS ETag 语义相同。
2. 官方文档和 COS 实测确认 `If-Match` 条件删除是否能达到现有 `deleteIfMatch` 的并发安全语义；这是切换必测项。如果不能，**不能**采用“先 HEAD 再无条件 DELETE”，因为两次请求之间对象可能变化。需要改成对象键不可覆盖、版本化目标加精确版本删除，或在所有写入方受控的前提下通过数据库锁/状态机阻止同键重写，并以并发测试证明。
3. 直传模式单独核对 COS 签名 URL、有效期、权限、浏览器 CORS、成功状态码与上传完成后的服务端大小/SHA-256 核验。默认同源上传仍须通过回归。
4. 日志归档、参考库、备份上传、保留清理、恢复演练、监控与运维脚本全部替换 Azure 直连。生产备份放在独立账号或其他故障域；先完成恢复演练再切换。
5. 测试分两层：先在本机用隔离 PostgreSQL、测试账号和存储测试替身验证业务链路与 `PrivateBlobs` 契约；现有 Azurite 只能验证 Azure 路径，不能证明 COS 行为。随后使用独立的真实 COS 测试桶验证签名直传、条件删除、Range、跨域、版本控制、加密、出站代理及备份恢复。两层都覆盖上传重试、旧任务读取、生成/复核/下载、暂停续跑、清理和跨用户隔离；只使用合成或获授权测试数据。模型调用和生产账务边界按现有集成测试规范记录。

初步适配器使用 `cos-nodejs-sdk-v5` 3.0.0。该版 SDK 已不支持路径式访问；本地协议测试采用 SDK 的虚拟主机请求格式。SDK 的 `DeleteObjectParams` 未声明 `If-Match` 条件删除，适配器不提供 `deleteIfMatch`；依赖它的库存自动删除仍拒绝启用。材料生命周期清理使用数据库对象锁与墓碑状态，并逐版本物理删除，合成测试不能替代真实 COS 并发验证。直传签名尚未实现或验证。

开发进度：API、主 worker 和运维调度器已接入 `BB_STORAGE_PROVIDER=azure|cos` 的显式选择；默认仍为 Azure。COS 模式要求 `BB_COS_SECRET_ID`、`BB_COS_SECRET_KEY`、`BB_COS_BUCKET`、`BB_COS_REGION` 同时存在，缺项即拒绝启动，不回退 Azure；`BB_DIRECT_BLOB_UPLOADS=1` 也拒绝启动。Compose 已传递主对象及备份 COS 变量；配置展开和定向合成测试通过。归档、备份保留和清理已有 COS 代码路径，但完整本地业务链路、真实 COS 调用、恢复演练和用户验收仍未完成，不能部署为 COS 生产配置。配置值属于私密环境文件，不提交凭据。

安全边界补充：日志归档、保留处理和用户清理入口按所选存储提供方工作，不在 COS 模式回退 Azure。对象盘点 CLI 支持 COS 只读扫描；库存自动删除仍要求原子条件删除，COS 模式明确拒绝。这些代码路径仍需真实 COS 和完整本地集成验收。

离机备份上传/下载、保留清理和应用对象快照导出/导入已有 COS 代码路径：主对象使用 `BB_COS_BUCKET`，离机备份必须另设 `BB_COS_BACKUP_BUCKET`，可使用独立的 `BB_COS_BACKUP_SECRET_ID`/`BB_COS_BACKUP_SECRET_KEY` 身份和 `BB_COS_BACKUP_REGION`。备份文件与恢复对象都做读回 SHA-256 校验；合成闭环已通过。保留任务保护最新一份带完成清单的备份，按版本删除旧对象，完成清单最后删除。实际恢复演练、真实 COS 私有权限、版本控制、加密、对象锁及费用尚未验证。

## 保留与安全对照

| Azure 现状 | COS 目标 | 验证 |
| --- | --- | --- |
| 生命周期规则（按容器/前缀/天数） | COS 生命周期规则 | 每条规则的适用前缀、期限和转储/删除结果逐项核对 |
| 软删除及恢复期限 | COS 版本控制及恢复方案 | 删除后恢复、过期版本清理演练 |
| 不可变存储或法律保留（若实际启用） | COS 对象锁定等经官方确认的能力 | 保留期内不能删除/覆盖，期满行为实测 |
| 账户/容器访问控制 | 私有桶和最小权限身份 | 匿名、跨用户、服务间访问测试 |
| 服务端加密与密钥管理 | SSE-COS 或 SSE-KMS，按合规结论选定 | 密钥权限、恢复与轮换演练 |

上述是核对项，不代表两家产品功能天然等价。迁移凭据采用专用身份并限定范围和有效期；若官方服务确实要求 Azure 账户密钥，需记录该限制、保护传递过程并在迁移后轮换。正式 CAM 策略须先核验官方权限映射、资源范围、目标身份与实际 API 调用，不凭接口名称猜写。

## 复制、切换与回滚

先全量复制，随后多轮增量追平。每轮核对清单、COS 对象和数据库引用，记录删除墓碑及未完成上传。最终切换使用短暂写入栅栏：停止新上传/生成和清理任务，等待或安全暂停在途任务，取得数据库与源对象一致的时间点，跑最后增量并完成“数据库有引用、COS 无对象”检查。通过后 API、worker、运维任务和备份同时切 COS，检查历史下载、新上传、在途恢复、归档及恢复点，再恢复写入。

可评估过渡期 COS 未命中回读 Azure，但它会延长 Azure 依赖、改变缺失对象语义，必须有精确的只读范围、监控、截止日期和禁用门槛；不能以它代替全量校验。

切换前回滚是撤销新配置。切换后若 COS 出现新对象或数据库状态变化，先冻结写入，对账并回迁新增对象，再恢复旧版；不得只改连接字符串。保留 Azure 只读副本至观察期和恢复演练通过，随后按批准流程轮换/撤销迁移凭据、删除临时身份、清退 Azure Blob 数据。生产执行由指定发布 chat 按固定版本、用户验收和该批上线授权进行。

- 完整本地集成测试、用户验收、备份恢复演练、停写与回滚演练。
- 切换后 Azure Blob 调用为零的运行时证据，以及 Azure 退役记录。

## 暂定排期与决策门槛

| 阶段 | 暂定工作量 | 进入下一阶段的条件 |
| --- | --- | --- |

| 应用和运维适配 | 5–10 个工作日 | API、worker、归档、备份、恢复和脚本在隔离环境通过定向测试 |
