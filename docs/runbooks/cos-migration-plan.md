# BondBuddy Azure Blob → 腾讯云 COS 迁移实施方案（草案）

状态：开发方案；未进行生产迁移、切换或用户验收。基线：`development/v1.0.0` 的 `8665e561680ecd6ac067dc2b001ae13e0312bd2a`。

## 目标与边界

将材料、派生文件、成果、参考库、受控日志与归档、备份及恢复全部改用 COS。数据库现有 `object_key` 保持不变；必要时增加存储提供方标识，不批量改写历史引用。上线后正常业务及定时任务不得访问 Azure Blob。Azure 源数据在核验和回滚观察期内保持只读，之后按数据保留和清退批准流程退役。应用服务器是否留在 Azure 是独立决定。

本迁移是跨 API、worker、运维脚本和部署配置的变更。`PrivateBlobs` 只覆盖应用对象；日志归档、异地备份及恢复脚本仍直接使用 Azure SDK。出站代理的 `BB_EGRESS_ALLOW` 也需要从 Blob 主机调整到精确 COS 主机。

## 迁移前盘点

从实际生产配置取得所有应用容器及备份容器的对象数、字节数、访问层、最大对象、近 7/30 天新增与改写量。清点数据库中全部 `object_key`、对象 SHA-256、内容类型、版本与保留约束，核对无引用对象及缺失对象。统计 Azure 生命周期、版本控制、软删除、不可变策略和实际备份覆盖范围。确认 Azure 与 COS 地域、数据分类、跨境要求、加密方式、密钥管理责任、目标 RPO/RTO 和可接受停写窗口。

2026-11-26 从运行中的 API 容器以现有 Azure SDK 只读列举了**当前配置涉及的现行对象**，未下载对象内容：

| Azure 容器 | 对象数 | 字节数 | GiB | 列举到的访问层 |
| --- | ---: | ---: | ---: | --- |
| `bondbuddy-private` | 20,086 | 11,158,656,016 | 10.39 | Hot |
| `bb-backups` | 31,023 | 40,115,408,650 | 37.36 | Hot |
| 合计 | 51,109 | 51,274,064,666 | 47.75 | Hot |

备份容器有 29 组一级前缀，其中 25 组符合日期命名，4 组不符合，必须单独判断保留用途。此清单不包括软删除对象、历史版本、快照或未配置在运行环境中的其他容器，不能当作 Azure 账户全量或最终迁移字节数。账户级容器列举曾遇到响应中断；实施前需补齐账户范围核验。当前本机 Azure CLI 登录的唯一可见订阅未列出存储账户，生产 Blob 的地域与账户级策略尚未核实。COS 目标地域与身份也尚未核实。

任何 Azure Archive 层对象须先解冻并计入等待时间与费用；不能把解冻中的对象算作可直接复制。盘点结果只保存汇总和内部校验清单，不公开对象键或客户内容。

## 工具与校验

先核实腾讯云官方迁移服务对当前 Azure 账户、认证方式、访问层及定时增量的实际支持，再与自有流式复制工具作样本对比。需要逐对象 SHA-256、可重放清单和数据库引用核验时，优先使用可在**首次读取 Azure 的传输流中**计算哈希的脚本；不要复制完再从 Azure 全量读取一次。原对象已有可信数据库 SHA-256 时，还要比对该值。COS 侧复核从 COS 读取，不增加 Azure 出站流量。

复制清单至少记录源容器、对象键、源版本/ETag、字节数、SHA-256、内容类型、目标桶、复制时间和结果；凭据与签名 URL 不入清单。对象键完全相同，容器到桶映射明确。复制可重试、可从清单续跑，目标已存在但哈希不同必须停下调查，不能覆盖。先抽取约 1% 的分层样本（大、小对象及各访问层、各业务前缀），按实测吞吐、API 限流和失败率估算全量与最后增量耗时。报价包括 Azure 出站与解冻、COS 存储/请求/流量以及双存储观察期。

## 代码改造与必测语义

1. 在 `PrivateBlobs` 后加入 COS 适配器和明确的提供方配置，覆盖有界读、流式读写、Range、一致性哈希、分页列举、对象标识及删除。所有 API/worker 入口改为统一工厂。不要把 Azure ETag 当成内容哈希或假设 COS ETag 语义相同。
2. 官方文档和 COS 实测确认 `If-Match` 条件删除是否能达到现有 `deleteIfMatch` 的并发安全语义；这是切换必测项。如果不能，**不能**采用“先 HEAD 再无条件 DELETE”，因为两次请求之间对象可能变化。需要改成对象键不可覆盖、版本化目标加精确版本删除，或在所有写入方受控的前提下通过数据库锁/状态机阻止同键重写，并以并发测试证明。
3. 直传模式单独核对 COS 签名 URL、有效期、权限、浏览器 CORS、成功状态码与上传完成后的服务端大小/SHA-256 核验。默认同源上传仍须通过回归。
4. 日志归档、参考库、备份上传、保留清理、恢复演练、监控与运维脚本全部替换 Azure 直连。生产备份放在独立账号或其他故障域；先完成恢复演练再切换。
5. 测试分两层：先在本机用隔离 PostgreSQL、测试账号和存储测试替身验证业务链路与 `PrivateBlobs` 契约；现有 Azurite 只能验证 Azure 路径，不能证明 COS 行为。随后使用独立的真实 COS 测试桶验证签名直传、条件删除、Range、跨域、版本控制、加密、出站代理及备份恢复。两层都覆盖上传重试、旧任务读取、生成/复核/下载、暂停续跑、清理和跨用户隔离；只使用合成或获授权测试数据。模型调用和生产账务边界按现有集成测试规范记录。

初步适配器使用 `cos-nodejs-sdk-v5` 3.0.0。该版 SDK 已不支持路径式访问；本地协议测试采用 SDK 的虚拟主机请求格式。SDK 的 `DeleteObjectParams` 未声明 `If-Match` 条件删除，适配器目前不提供 `deleteIfMatch`，依赖它的清理流程会拒绝启用。此处是代码接口检查，不替代真实 COS 服务对条件请求的验证。直传签名也尚未实现或验证。

开发进度：API 和主 worker 入口已接入 `BB_STORAGE_PROVIDER=azure|cos` 的显式选择；默认仍为 Azure。COS 模式要求 `BB_COS_SECRET_ID`、`BB_COS_SECRET_KEY`、`BB_COS_BUCKET`、`BB_COS_REGION` 同时存在，缺项即拒绝启动，不回退 Azure；`BB_DIRECT_BLOB_UPLOADS=1` 也拒绝启动。运维调度器的归档和备份尚未适配，在 COS 模式下明确拒绝启动。因此这只是主对象链路的开发切片，当前 Compose、归档、备份、恢复和清理仍不能用于完整 COS 切换，不能部署为 COS 生产配置。配置值属于私密环境文件，不提交凭据。

安全边界补充：现有 Azure 专用的日志归档、保留处理、离机备份、对象快照、清理及盘点入口在 COS 模式下拒绝运行，防止配置切换后仍无意读写 Azure。这些拒绝检查不是 COS 功能实现；必须在对应能力迁移并验证后逐项替换。

## 保留与安全对照

| Azure 现状 | COS 目标 | 验证 |
| --- | --- | --- |
| 生命周期规则（按容器/前缀/天数） | COS 生命周期规则 | 每条规则的适用前缀、期限和转储/删除结果逐项核对 |
| 软删除及恢复期限 | COS 版本控制及恢复方案 | 删除后恢复、过期版本清理演练 |
| 不可变存储或法律保留（若实际启用） | COS 对象锁定等经官方确认的能力 | 保留期内不能删除/覆盖，期满行为实测 |
| 账户/容器访问控制 | 私有桶和最小权限身份 | 匿名、跨用户、服务间访问测试 |
| 服务端加密与密钥管理 | SSE-COS 或 SSE-KMS，按合规结论选定 | 密钥权限、恢复与轮换演练 |

上述是核对项，不代表两家产品功能天然等价。迁移凭据采用专用身份并限定范围和有效期；若官方服务确实要求 Azure 账户密钥，需记录该限制、保护传递过程并在迁移后轮换。正式 CAM 策略须先核验官方权限映射、资源范围、目标身份与实际 API 调用，不凭接口名称猜写。

## 复制、切换与回滚

先全量复制，随后多轮增量追平。每轮核对清单、COS 对象和数据库引用，记录删除墓碑及未完成上传。最终切换使用短暂写入栅栏：停止新上传/生成和清理任务，等待或安全暂停在途任务，取得数据库与源对象一致的时间点，跑最后增量并完成“数据库有引用、COS 无对象”检查。通过后 API、worker、运维任务和备份同时切 COS，检查历史下载、新上传、在途恢复、归档及恢复点，再恢复写入。

可评估过渡期 COS 未命中回读 Azure，但它会延长 Azure 依赖、改变缺失对象语义，必须有精确的只读范围、监控、截止日期和禁用门槛；不能以它代替全量校验。

切换前回滚是撤销新配置。切换后若 COS 出现新对象或数据库状态变化，先冻结写入，对账并回迁新增对象，再恢复旧版；不得只改连接字符串。保留 Azure 只读副本至观察期和恢复演练通过，随后按批准流程轮换/撤销迁移凭据、删除临时身份、清退 Azure Blob 数据。生产执行由指定发布 chat 按固定版本、用户验收和该批上线授权进行。

## 必须交付的证据

- 生产容器与访问层清单、数据库引用核对、1% 样本吞吐与费用/工期估算。
- 官方工具/凭据/条件删除能力核验及 COS 实测结果。
- 全量与增量复制清单、每对象字节数及 SHA-256 校验、缺口处理记录。
- 完整本地集成测试、用户验收、备份恢复演练、停写与回滚演练。
- 切换后 Azure Blob 调用为零的运行时证据，以及 Azure 退役记录。

## 暂定排期与决策门槛

| 阶段 | 暂定工作量 | 进入下一阶段的条件 |
| --- | --- | --- |
| 真实清单、官方能力及合规核对 | 1–3 个工作日 | 对象/访问层、地域、保留规则、认证方式及条件删除结论齐全 |
| 应用和运维适配 | 5–10 个工作日 | API、worker、归档、备份、恢复和脚本在隔离环境通过定向测试 |
| 1% 分层样本及全量/增量复制 | 由实测吞吐决定 | SHA-256 清单、失败重试和数据库引用核验无未解释缺口 |
| 固定版本本地集成与用户验收 | 2–5 个工作日，视缺陷修复而定 | 用户确认实际链路和回滚演练 |
| 生产切换与观察 | 停写窗口由最后增量实测决定；观察建议至少 7 天 | COS 读写、归档、备份恢复正常且 Azure 调用为零 |

这些是排期假设，不是已承诺的迁移完成日期。归档层解冻、合规审批、账号权限和样本吞吐可能改变工期；取得实际清单和样本结果后更新固定计划。

本机测试阶段无需开通 COS 或购买容量包。进入真实 COS 兼容性与约 1% 样本测速阶段前，才需要可访问的独立 COS 测试桶及费用预算；测试流量、存储和请求可能产生按量费用。不得以本地测试替身的通过结果代替真实 COS 实测。
